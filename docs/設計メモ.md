# ボイスインカムアプリ 設計書

Oct 7, 2026 · @大樹

音声配信は LiveKit、翻訳と文字起こしは OpenAI、履歴とメディアは AWS サーバーレスで構築する。

## 概要と決定事項

ボイスインカムアプリを、React の管理コンソール、React の Web 版クライアント、React Native のモバイル版クライアント(iOS / Android)で構築する。Web 版を先に作り、モバイル版は後から作る(「クライアントを React にそろえる」)。ルーム内では、PTT または発話検知の間だけ音声を配信し、テキスト入力は読み上げ音声とテキストの両方で届ける。チャットでは画像と動画を送れる。音声のやり取りはリアルタイムに文字起こしし、ユーザーが希望する言語に翻訳して配信する。

| 前提 | 内容 |
| --- | --- |
| ルーム規模 | 基本は少人数、最大100人程度 |
| 遅延 | 元の音声は300ms程度。翻訳・字幕は数秒の遅れを許容 |
| 録音 | 必要 |

| 領域 | 決定 |
| --- | --- |
| 音声配信 | LiveKit。まず LiveKit Cloud で作り、運用が見えた段階でセルフホストを検討する |
| 翻訳音声 | OpenAI gpt-realtime-translate。話者ごと・翻訳先の言語ごとにセッションを作る |
| 原文の文字起こし | OpenAI gpt-realtime-whisper。話者ごとに1本 |
| バックエンド | AWS サーバーレス(API Gateway + Lambda、DynamoDB、S3 + CloudFront) |
| 録音 | Agent が話者ごと・発話ごとに Ogg/Opus にして S3 へ(Egress は使わない。「録音の方式」を参照) |
| クライアント | 管理コンソールと Web 版は Vite + React、モバイル版は React Native。画面に依らない処理は共有のパッケージに置く(2026-10-16 に Flutter から転換)。見た目は自前のデザインシステム(トークンを共有し、Tailwind のクラスで書く) |
| 比較検討の記録 | [技術選定メモ](https://claude.ai/code/artifact/800896cc-8702-467f-a745-5b8b40b62536)(Gemini など不採用の選択肢を含む) |

## クライアントを React にそろえる(2026-10-16)

**決定(利用者): Flutter 版のアプリは捨てて、まず Web 版を React で作る。ある程度できたら、モバイル版を React Native で作る。** アプリは管理コンソール(React)、Web 版クライアント(React)、モバイル版クライアント(React Native)の3つになる。

- **理由:** Web なら開発が速く回る(シミュレーターやビルドを待たない。ブラウザの開発ツールで WebRTC を見られる)。Flutter 版では iOS シミュレーターの音声が固まる問題に時間を取られ、本物の音声は実機が要った(利用者は iPhone を持っていない)。3つとも React にすると、処理を共有しやすい。
- **共有の形:** 画面を持たない TypeScript のパッケージに、API の呼び出し、ルームの状態、字幕、テキスト入力の送り直し、メディアの送受信と削除の扱いを置く。画面と、端末に依るところ(メディアの選び方と動画の変換、push 通知、バックグラウンド、ログインのリダイレクト)は各アプリに置き、インターフェースで差し替える。React Native の LiveKit の SDK は JS の SDK(`livekit-client`)をもとにしているので、ルームの処理はほぼそのまま共有できる見込み(推測。モバイル版に入る前に確かめる)。
- **Flutter 版:** タグ `flutter-final` に残す。移植するときは `git show flutter-final:apps/mobile/...` で参照する。Flutter 版で決めた仕様(字幕の受け方、履歴で確かめてから表示する、送り直し、削除の表示、マルチパートの並列数と上限)はそのまま引き継ぐ。
- **この文書の Flutter の記述:** 下の節の Flutter・Dart・iOS ネイティブに関わる記述は、Flutter 版で調べて決めた記録として残す。サーバーと LiveKit の振る舞いの記録は今も有効。クライアントの SDK に依る記録(送信元の参加者が null になる条件など)は、JS の SDK で確かめ直す。
- **Dart の生成をやめた:** proto と OpenAPI からの Dart の生成物(`packages/schema/dart`、`packages/api-client/dart`)は消した。サーバーの、生成した Dart のクライアントのための工夫(event_id をクエリで受けるなど)は、そのまま残す。

### ルーティングと共有のパッケージ(2026-10-16)

- **決定(利用者): Next.js は使わない。** SSR の利点が無く(ログインの後にしか使わない画面で、検索エンジンに載せない)、配信の手間(サーバーか Lambda)が増えるため。静的なファイルを置くだけで配信できる SPA にする。
- **決定(利用者): ルーティングは React Router の framework モードを SPA(`ssr: false`)として使い、ファイルでルートを書く(`@react-router/fs-routes` の `flatRoutes`)。** 画面が増えてもルートの表を手で直さずに済み、ルートごとの型(`react-router typegen`)も作れる。管理コンソールも同じ形に移した。ビルドのときに Node でルートのモジュールを読み込む(`index.html` を作る)ので、モジュールの読み込みで `window` を触らない。
- **共有のパッケージ `packages/client-core`:** Flutter 版の `lib/room` と `lib/media` のうち、端末に依らない処理を `livekit-client` を前提に移した(ルームの状態、購読、字幕、テキスト入力の送り直し、画像・動画の受け取りと削除、マルチパートのアップロード、REST API の呼び出し)。Flutter 版の単体テストも Vitest に移した。
  - **端末に依るところはインターフェースにする:** 音声の出し方とバックグラウンド(`RoomPlatform`)、画像・動画の整え方(`MediaPreparer`)、署名付き URL への PUT(`SignedPut`)、アクセストークン(`getAccessToken`)。ログインのリダイレクトは各アプリで持ち、トークンを返す関数だけを渡す。
  - **DOM の API を使わない:** React Native(`@livekit/react-native`)でも使えるよう、`tsconfig.json` の `lib` に DOM を入れず、ブラウザと React Native の両方にあるもの(`setTimeout`、`console`、`crypto.getRandomValues`)だけを宣言した。React Native では `crypto.getRandomValues` を足す必要がある。
  - **画面への知らせ:** React には依らせず、`subscribe` と変わった回数(`version`)だけを持つ(`Observable`)。React では `useSyncExternalStore` で描き直す。
  - **送信元の参加者:** `livekit-client`(2.22.3)も、データの送信元を `remoteParticipants` から identity で引き、知らない参加者・サーバーからのものは `undefined` にする(SDK のソースで確かめた)。Flutter 版と同じ前提なので、字幕は Agent の参加者のものだけを読み、画像・動画と削除の知らせは履歴で確かめてから出す取り決めをそのまま使う。実際のルームでの振る舞い(入った直後の約3秒)は、JS の SDK ではまだ確かめていない。

- **決定(利用者): Cognito のアプリクライアントは、Web 版用(`web`)を管理コンソールと分ける。** ローカルの開発サーバーは `http://localhost:5174`。リフレッシュトークンはモバイルと同じ30日(管理コンソールは1日)。

### Web 版の動画の変換(2026-10-18)

**決定: Web 版は、選んだ動画をブラウザの WebCodecs で H.264 の MP4 にしてから送る。** iPhone の HEVC の MOV などが、ブラウザによって再生できないため。仕様は Flutter 版で決めたもの(「動画の解像度とビットレート」「幅・高さ・動画の長さ」「端末での圧縮」)を引き継ぐ。

- **決め方は共有のパッケージに移した:** Flutter 版の `video_plan.dart` を `packages/client-core` の `media/videoPlan.ts` に移した(目標のビットレート、そのまま送る・入れ直す・符号化し直すの決め方、大きさの見積もり、箱の並びの読み方。単体テストも移した)。モバイル版も同じ決め方を使う。読む・書く・符号化するところは端末に依るので、`MediaPreparer` の実装(Web 版は `apps/web/src/video`)に置く。
  - 元の解像度・フレームレート・回転のまま、幅 × 高さ × 実効のフレームレート × 0.1 の H.264 にする(元の映像のビットレートは超えない)。元が H.264 で、音声が AAC か無く、ビットレートが目標の 1.25 倍以下なら符号化し直さず、`moov` が先頭の MP4 ならそのまま送り、MOV や `moov` が末尾の MP4 は MP4 に入れ直す。
  - 音声は、AAC の 2 チャンネルまでならそのまま入れ、それ以外(Opus、5.1ch など)は AAC の 2 チャンネル(1 チャンネルあたり 96kbps、2ch で 192kbps)にする。符号化する前に、目標のビットレートと長さ(音声は 192kbps で数える)で大きさを見積もり、10GB を超えそうなら止める(送れないと出す)。
  - 変換したら、ファイル名の拡張子を `.mp4` にし、`video/mp4` で送る。幅・高さ・長さとサムネイルは、変換した後の本体を `<video>` で測る。
- **ライブラリ: Mediabunny 1.61.1**(MPL-2.0。2026-10-03 公開の固定の版)で MP4 / MOV を読み書きする。選んだ理由:
  - 読む(MP4・MOV)・WebCodecs での復号と符号化・書く(MP4)を1つで持ち、`Conversion` で「映像だけ符号化し直し、音声はそのまま入れる」「符号化せずに入れ直す」を書ける。ビットレートを bps で指定できる。実行時の依存のパッケージが無く(型だけ)、Worker で動く。
  - `moov` を先頭に置く方法を選べる。`fastStart: "reserve"`(先頭に `moov` の場所を取っておき、最後に書く)なら、出力をメモリに溜めずに `WritableStream` へ順に書ける。10GB までの動画を扱うので、出力全体をメモリに持つ方法(`"in-memory"`)は使えない。
  - 比べたもの: ffmpeg.wasm は符号化がソフトウェア(x264 は GPL)で遅く、WebAssembly のメモリ(32 ビットで最大 4GB)にファイルを置くので 10GB を扱えない。mp4box.js は読み書きはできるが、復号・符号化の流れと `moov` を先頭に置く処理を自前で書くことになる。同じ作者の mp4-muxer(書くだけ)は deprecated で、Mediabunny に移るよう案内している。
  - 注意: MPL-2.0 はファイル単位のコピーレフト。手を入れずに依存として使う分には、アプリのコードに及ばない。
  - ブラウザに AAC の符号化器が無いとき(この devContainer の Chromium で無かった。ブラウザと OS による)は、同じ作者の `@mediabunny/aac-encoder` 1.61.1(MPL-2.0、libavcodec の WebAssembly)を使う。約 1MB あるので、音声を符号化し直すときだけ読み込む(Vite の `worker.format` を `es` にして、別のチャンクに分けた)。
- **メインスレッドを固めない:** 読み書きと符号化は Worker(`videoConvert.worker.ts`)で行う。出力は OPFS(Origin Private File System)の一時ファイルに `createSyncAccessHandle` で書き、送るときはそのファイルを `Blob.slice` で読む(10GB でもメモリに載せない)。送り終えたか諦めたら `MediaPreparer.release` で消す。前の変換の残り(タブを閉じたなど)は、作ってから1日たったら次の変換のときに消す。
  - `moov` の場所を取るには、トラックごとのパケットの数の上限が要る。映像は元のパケットの数(フレームレートを変えないので同じ)、音声は元の数と、長さを 96kHz の AAC で割った数の大きいほうに、どちらも 2 割と 100 個を足す(`reservedPacketCount`)。Mediabunny の `Conversion` にはトラックの設定を渡す口が無いので、出力の `addVideoTrack`・`addAudioTrack` を包んで上限を書き足している(Mediabunny を上げるときに、まだ動くか確かめる)。
- **変換できないときは元のまま送る(今までと同じ):** WebCodecs・Worker・OPFS が無い、動画として読めない、復号できない、H.264(か AAC)の符号化器が無い、映像か音声のトラックを落とすことになる、一時ファイルを置く空き容量(`navigator.storage.estimate`)が足りない、変換の途中で失敗した。どれも console に理由を出す。
- **進み具合と取りやめ:** 変換の間は「変換中 n%」と進み具合の棒を出す(アップロードの「送信中 n%」と同じ出し方)。変換中とアップロード中は「取りやめる」で止められる(`MediaUploader.cancel`。`MediaPreparer.prepare` と `SignedPut.putFile` に `AbortSignal` を渡す)。取りやめると、Worker に止めさせて作りかけの一時ファイルを消し、送信中の一覧から外す。マルチパートで送り終えたパートは残るが、S3 のライフサイクルルール(1日)が消す。保存中(complete の後)は、保存されたかもしれないので取りやめない。ルームを出たときも、変換とアップロードを止める。
  - `client-core` は DOM の型を入れていないので、`AbortController`・`AbortSignal` の使う部分だけを `host.d.ts` で宣言した(React Native にもある)。

確かめたこと(2026-10-18、devContainer の Playwright の Chromium 141(arm64)):

- この Chromium は H.264 と AAC の復号器・符号化器を持たない(オープンソースの Chromium の制約)。そのため、本物の H.264 への変換は確かめられていない。
- H.264 の符号化器が無いときに元のまま送ること: 1080p・20秒の VP9 / Opus の MP4(32MB、`moov` が末尾)を、ローカルの全体(`mise run livekit`・`api`・`web`)の Web 版のルームで送ると、`no_encodable_target_codec` で元のまま、マルチパートで送れた。一時ファイルは残らなかった。
- 流れそのもの(Worker、OPFS への書き込み、`fastStart: "reserve"` と書き足したパケットの数の上限、進み具合、取りやめ、一時ファイルの後始末): Worker の `avc`・`aac` を `vp9`・`opus` に置き換えたものを一時的に使って確かめた。
  - 1080p・30fps・20秒・12.8Mbps の VP9 を、目標の 6.2Mbps で符号化し直し、11.4MB(約 4.5Mbps)の MP4 になった。Web 版の画面に「変換中 n%」が 4% から 99% まで出て、送った後は一時ファイルが消えた。履歴の名前は `.mp4`、幅・高さ・長さは変換した後のもの。
  - 変換の途中(26%)で「取りやめる」を押すと、送らずに一覧から消え、一時ファイルも残らなかった。
  - 縦向き(回転 90)の 720p の動画は、回転のメタデータのまま、`moov` が先頭、パケットの数も元と同じになった。符号化し直さない(入れ直す)ときは、ビットレートも元と同じだった。
  - 1080p・6秒を符号化し直す約 2.3 秒の間、メインスレッドの 10ms のタイマーの遅れは最大 13ms だった(固まっていない)。

確かめていないこと:

- 実際の H.264・AAC での変換(Google Chrome、Safari、Firefox)。H.264 の符号化器がどの解像度・フレームレートまで受けるか(4K60 を受けない符号化器では、変換できずに元のまま送る)。かかる時間。
- iPhone の HEVC の MOV(HDR の HLG・Dolby Vision を含む)。Flutter 版は HDR を BT.709 の SDR にしたが、Web 版は WebCodecs と Mediabunny に任せていて、色が浅くなる・崩れるかを確かめていない(HDR かどうかは console に出す)。
- Safari の OPFS の `createSyncAccessHandle` と WebCodecs の組み合わせ、Safari のプライベートブラウズ(OPFS が使えないなら元のまま送る作り)。
- 10GB に近い動画(OPFS の容量の上限、`moov` の場所の見積もりの余裕)。

### ログイン画面(2026-10-17)

**決定(利用者): Cognito のログイン画面を、クラシックの Hosted UI からマネージドログインに切り替え、見た目をデザインシステムに揃える。** ログインは今までどおり標準の OIDC(認可コード + PKCE)で、アプリは Cognito の API を直に呼ばない。

- **見た目はデザイントークンから作る:** `packages/design-tokens` の `mise run gen:tokens` が、トークンの色と角丸を Cognito のブランディングの設定(`generated/cognito-branding.json`)に写し、Terraform がクライアント(`mobile`・`web`・`admin`)ごとに当てる。部品の配色は ui-web の部品に揃える。明暗は OS の設定で切り替える(`DYNAMIC`)。書体は Cognito のものから変えられない。ロゴはまだ無いので出さない。
- **言語:** マネージドログインは `lang` が無いと英語で出す。Web 版はブラウザの言語の好み(`navigator.languages`)から、Cognito が訳している言語(12)を選んで `/oauth2/authorize` に付ける(`client-core` の `loginLanguage`)。訳が無い言語は英語。モバイル版も端末の言語で同じ関数を使う。管理コンソールは画面が日本語なので `ja` に固定する。
- **プラン:** マネージドログインは ESSENTIALS 以上で使える。今のプラン(ESSENTIALS)のままでよい。
- **切り替えの影響:** Cognito の文書では、切り替えるとセッションを引き継がず(ログインし直しになる)、新しい画面になるまで最大4分かかる。リフレッシュトークンで続いているアプリのログインまで切れるかは、まだ確かめていない。

### 1つのタイムライン(2026-10-16)

**決定(利用者): 履歴の画面は分けない。** 新しく届いたものも、古い履歴を読み込んだものも、ルームの画面の1つのタイムラインで同じように見せる(Flutter 版はルームの画面と履歴の画面を分けていた)。

- **字幕と履歴の行を1つにする:** Agent は字幕の `segment_id` を履歴の `source_id`(`event_id` の `#` の後ろ)にして保存する(発話もテキスト入力も)。履歴に同じ区切りの行があれば行を出し、無いうちは字幕を出す。行は訳がそろってから保存されるので、届いたばかりの字幕は字幕のまま出し、入り直したときや古いほうを読んだときは行で出る。
- **読み方:** 入室とつなぎ直しで最新の1ページ(50件)。つないでいなかった間が1ページを超えれば、知っている行に届くまで古いほうへ読む(5ページまで。超えた分の抜けは埋めない)。上へ戻ると古いほうを1ページずつ読み足す。
- **並び:** 行は `occurred_at`(サーバーの時刻)、字幕は届いた時刻。端末の時計がずれていれば前後しうる(Flutter 版と同じ)。
- **作り:** `packages/client-core` の `RoomTimeline`(行を event_id で持ち、墓石で置き換え、字幕と合わせて並べる)。`RoomSession.entries` が画面に出す並び。`MediaFeed` はこれに入れ替えた。

### ファイルの送信(2026-10-16)

**決定(利用者): 画像・動画のほかに、どんな形式のファイルも送れるようにする。上限は同じ 1ファイル 10GB。**

- **決定(利用者): ファイルはダウンロードだけにする。** `Content-Disposition: attachment`(元のファイル名つき)でオブジェクトを置く。画像・動画と同じく CloudFront の署名なしの URL で配信するので、HTML や SVG をブラウザで開かせると、配信のドメインで任意のページを見せられてしまうため。署名付きの URL にする案は、CloudFront の鍵と発行の API が要り作業が大きいので取らなかった。
- **決定(利用者): 形式は問わない。** 実行ファイルなどを断る案は、拡張子を変えれば送れるので取らなかった。ダウンロードだけなので、開かれずに保存される。
- **決定(利用者): ウイルス検査は今はしない。** ルームのメンバーだけが送受信する前提。必要になったら S3 の GuardDuty Malware Protection などを足す。
- **種類の決め方:** `image/jpeg`、`image/png`、`image/webp`、`image/heic` は画像、`video/*` は動画(Web 版は、変換できないときに MOV なども元のまま送るため)、それ以外はファイル。API が `media_type` として返し、アプリはそれで表示を分ける。GIF はアプリが表示しない形式なのでファイルになる。
- **API の変更:** `content_type` を MIME タイプなら何でも受け付け、`file_name` を足した。1回の PUT は Content-Disposition を署名に含め、値を応答の `content_disposition` で返す(クライアントはそのまま付ける)。マルチパートは CreateMultipartUpload で付ける。履歴の media に `media_type` と `file_name`、`MediaMessage` に `file_name`(15)、墓石の `media_type` に `file`、push 通知に「ファイルを送りました」を足した。
- **S3 の CORS:** ブラウザから Content-Disposition を付けて PUT するので、許すヘッダーに足した。ローカルの SeaweedFS(4.48)も Content-Disposition を保存して配信の応答に付け、署名と違う値の PUT は 403 にした(2026-10-16 に確かめた)。

### 管理コンソールにルームの履歴を出さない(2026-10-16)

**決定(利用者): 管理コンソールからルームの履歴の画面を消した。** 管理コンソールではルームの中身を扱わない方針(「送ったものの削除」で管理者も消せないのと同じ)。ルームの作成・メンバーの編集・ユーザーの一覧だけを残す。API の `GET /rooms/{room_id}/timeline` は、今も管理者に読ませている(画面からは呼ばない)。→ 2026-10-23 に、管理者もメンバーでなければ読めないようにした(「テナントとルームの種別」)。

### Agent の scale to zero(2026-10-16)

**決定(利用者): dev の Agent は、使っていない間 0 台にする(B 案: 入室で自動で起動し、使われなくなったら自動で止める)。** dev で使っていない間も料金がかかるのは Agent(ECS Fargate、1 vCPU・2GB で月に約 30 USD と公開 IP の分。概算)だけで、ほかは使った分だけの課金のため。手で上げ下げする A 案は、止め忘れと使う前の手間があるので取らなかった。

- **起こす(API):** `POST /livekit/token` で、Agent の ECS のサービスの台数が 0 なら 1 にする。Lambda から ECS の API を1〜2回呼ぶだけで、失敗してもトークンは出す。
- **割り当て直す(Agent):** LiveKit は、Agent が1台も登録していないときに作られたルームの割り当て(トークンの RoomAgentDispatch)を、後から登録した Agent に渡さない。ローカルの livekit-server 1.13.9 で、入室の 90 秒後に Agent を起動しても入らず、割り当ては jobs が空のまま残った。`CreateDispatch` を後から出すと、約 2 秒で入った。そこで Agent は登録した後に、人がいて Agent のいないルームを探して割り当て直す。割り当てに jobs があるルーム(ほかの Agent が受けた)は除く。LiveKit Cloud でも同じかは、dev で確かめる。
- **止める(Agent):** ジョブの無い状態が 15 分続き、LiveKit にも人のいるルームが無ければ、自分のサービスの台数を 0 にする。止めた直後に入った人のルームは Agent がいないままになるが、入り直せば起こし直す(dev なので、この隙間は許す)。
- **オートスケールは使わない:** 0 台からは CPU の指標が出ず、ターゲット追跡では増えないため。dev は 0 台と 1 台だけにする。prod は今までどおり最小 1 台のオートスケール。
- **起動を待つ間:** 起動と LiveKit への登録に 1〜2 分かかる。アプリは「翻訳の準備中」と、起動に時間がかかることがあると出す。テキスト入力は Agent を待つ間は送り直しの回数に数えず、3 分まで待つ(前は約 12 秒で諦めていた)。

### データストアは DynamoDB のままにする(2026-10-16)

**決定(利用者): Aurora Serverless v2 などの RDB は入れない。** 今の読み書きは、どれもキーの決まった形で足りるため。

- **トランザクションが要らない理由:** 書き込みはほぼすべてが1件の項目で済み、二重の作成や同時の呼び出しは条件付きの書き込みで防いでいる(ルームの作成、墓石、push 通知の間引き)。複数の項目をまとめて書く必要が出ても、DynamoDB の `TransactWriteItems`(1回100件まで)がある。
- **読み方:** 履歴はルームごとに時刻の順の Query、ルームとユーザーはキーで1件、自分のルームは GSI の Query(下の「ルームのメンバーを別のテーブルにする」)。結合や自由な条件での検索は無い。
- **RDB を入れたときの負担:** Lambda を VPC に入れるか Data API を使う、接続数の管理(RDS Proxy)、スキーマのマイグレーションが増える。最小 0 ACU で止められるが、止まった後の最初の接続は再開を待つので API の応答には向かない。履歴を DynamoDB、マスタを RDB と分けると、2つの間の整合も取ることになる。
- **考え直すとき:** 管理コンソールで条件を自由に組んで検索・集計したくなったとき(利用時間の集計、組織ごとのレポートなど)、または組織・部署・役割のような関係の多い権限が入ったとき。それでも、まずは DynamoDB の S3 へのエクスポート(か Streams)と Athena、全文検索なら OpenSearch を足す形を先に考える。

#### ルームのメンバーを別のテーブルにする

**決定(利用者): メンバーを rooms の行の `member_ids` から、room_members テーブル(1人1行、`room_id` × `user_id`)に移し、GSI(`user_id-index`)で「自分がメンバーのルーム」を引く。** 前は rooms テーブル全体を Scan して `member_ids` で絞っていて、ルームの数に比例して遅く、費用も増えるため。

- **メンバーの置き場所は room_members だけにする。** rooms の行にも持たせると2か所を揃え続ける必要があり、`TransactWriteItems` は1回100件までなので、100人のルームを一度に入れ替えられない。ルームの取得は GetItem と、room_id の Query(強い整合)の2回になる。
- **書き換えはトランザクションにしない。** 今ある行との差分だけを BatchWriteItem で書く。途中で失敗すると一部だけが変わるが、同じ内容で PATCH し直せば揃う。ルームを消すときも、先に rooms の行を消してからメンバーの行を消す。行が残っても、一覧は rooms に無いルームを出さず、同じ room_id で作り直せば消える。
- **GSI は結果整合。** 足した直後は、その人の一覧に1秒ほど出ないことがある。外した直後に GSI に残っていても、ルームのメンバー(強い整合)で確かめてから返す。入室の権限(トークンの発行)は、もとから room_id で読むので GSI の遅れを受けない。
- **並び:** `member_ids` は user_id の順で返す(前は登録した順だった)。
- **前のルームの移し方:** `services/api` の `migrate_room_members.py` を1回実行する(README の「ローカル環境」と、ファイルの先頭のコメント)。`member_ids` の人を room_members に足してから、rooms の行の `member_ids` を消す。何度実行してもよい。
- 管理者の一覧(すべてのルーム)は、rooms と room_members の Scan のまま(すべてを返すので)。

#### メンバーを外したとき・ルームを消したときの後始末

**決定: メンバーを外したら LiveKit のルームから出し、ルームを消したら LiveKit のルームを消して、履歴とメディアも消す。** 入室の権限はトークンを出すときにしか確かめず、接続中のトークンは LiveKit サーバーが更新し続けるので、DB を変えただけでは外した人が出るまで聞き・話し続けられる。また、同じ room_id で作り直せる(上)ので、履歴とメディアが残ると、新しいメンバーに前のルームの履歴と URL が見えてしまう。`services/api` の `room_cleanup.py`。

- **外した人:** PATCH で外した user_id のうち、今ルームにいる人(`ListParticipants`)を `RemoveParticipant` で出す。LiveKit の identity からは管理者か分からないので、メンバーから外した管理者も出す(管理者は入り直せる)。
- **ルームを消す:** `DeleteRoom` で全員(Agent も)を切ってから、timeline テーブルの3つのパーティション(履歴、アップロード中の仮の行、push 通知の時刻)を Query と BatchWriteItem で、S3 の `rooms/<room_id>/` を ListObjectsV2 と DeleteObjects で消し(途中のマルチパートは先に取りやめる)、CloudFront を `/rooms/<room_id>/*` の1パスで無効にする。録音(管理者しか読めない)は消さない。
- **Lambda の timeout(15秒)に収める:** LiveKit の呼び出しは1回2秒で打ち切り、履歴とメディアの削除は6秒で打ち切る。大きなルームで消しきれなければ、残りは同じ room_id でルームを作るとき(POST /rooms でも毎回消す。消すものが無ければ数回の Query と List で終わる)か、DELETE のやり直し(404 でも後始末は行う)で消す。非同期のジョブ(SQS や Step Functions)に分けるほどの量ではないと考え、メンバーの行と同じく「作り直すときに消える」形にした。
- **失敗しても応答は成功にする:** DB はもう変わっているので、後始末の失敗はログに残すだけにする。
- **残ること:** 出した人が、出す前に受け取ったトークン(15分)を使って入り直すことは止められない(アプリは入り直さない)。消した後に、発行済みの署名付き URL(1時間)で PUT されたオブジェクトは、どの履歴からも指されず、作り直すときに消える。

### デザインシステム(2026-10-16)

**決定(利用者): 管理コンソール・Web 版・モバイル版の見た目をそろえるため、自前のデザインシステムを作る。** 既製のもの(melta UI など)は使わず、AI に守らせる仕組み(機械で読める決まりと、違反を返す検査)だけを取り入れる。

- **アイコン:** Lucide(Web は `lucide-react`、React Native は `lucide-react-native`。名前が同じ)。
- **ダイアログ(2026-10-18):** 確認のダイアログ `ConfirmDialog` を `ui-web` に足し、`window.confirm`(ブラウザの見た目で、デザインがそろわず、文言も選べない)を置き換えた。下敷きは Radix の AlertDialog(`@radix-ui/react-alert-dialog` 1.1.23)。フォーカスを中に閉じ込める、Esc で閉じる、`role="alertdialog"` と題・本文の結び付け、後ろの要素を読み上げから外す、を任せる。Radix は Trigger を使わないと閉じたときにフォーカスを戻さないので、開く前の要素に戻すところだけ自前で書いた。props(`open`、`title`、`description`、`confirmLabel`、`cancelLabel`、`tone`、`onConfirm`、`onCancel`)は、React Native の `Modal`(`visible`、`onRequestClose`)で同じ名前のまま作れる形にした。後ろの幕は `overlay` のトークンを使う。
- **まだ入れていないもの:** メニュー(ドロップダウン)、ダイアログの中で入力させる形(名前を打って削除を確かめるなど)。要るようになったら、同じく Radix などの見た目を持たない部品を下敷きにして `ui-web` に足す。

### 管理コンソールと Web 版の配信(2026-10-18)

**決定(利用者): 管理コンソールと Web 版は、S3(非公開。CloudFront からだけ OAC で読む)+ CloudFront で静的に配信する。** SPA なのでサーバーは要らない(「ルーティングと共有のパッケージ」)。モジュールは `infra/modules/spa`、デプロイは `mise run deploy:web dev`・`deploy:admin dev`(README の「管理コンソールと Web 版の配信」)。

- **アプリごとに分ける:** バケットとディストリビューションをアプリごとに作る。1つにまとめてパスで分ける(`/admin/` など)と、React Router の `basename` と Vite の `base` を合わせる手間が増え、キャッシュの無効化も分けられないため。オリジンが分かれるので、ログインの保存(`localStorage`)も混ざらない。
- **知らないパスに `index.html` を返す:** CloudFront Function(viewer-request)で、最後の区切りに拡張子の無いパスを `/index.html` に書き換える。S3 の 403・404 をエラーレスポンスで `index.html`(200)に替える方法は取らない。無い JS や CSS にも HTML を返してしまい、壊れ方が分かりにくいため。ルームの ID などは `.` を使わない(`RoomId` の pattern)ので、拡張子で見分けられる。Function は月 200 万回まで無料。
- **キャッシュ:** `assets/` の下は名前にハッシュが付くので1年(`immutable`)、`index.html` は `no-cache` で置き、デプロイの後に `/*` を無効にする。
- **設定はビルドに埋め込む:** `VITE_` の環境変数を、デプロイのたびに `terraform output` から作る。実行時に読む設定ファイル(`config.json`)にはしない。環境が dev だけで、ビルドし直す手間が小さいため。prod を作るときに、同じビルドを使い回したくなれば見直す。
- **ドメイン:** 当面は CloudFront の既定のドメイン(`*.cloudfront.net`)を使う。HTTPS なので、マイクも使える。Cognito の `web`・`admin` クライアントの戻り先と、API・画像と動画のバケットの CORS に、このオリジンを足した。
- **まだ入れていないもの:** CSP(つなぐ先が環境で変わる)、独自のドメイン、prod の配信(prod にはまだ Cognito と API が無い)。

### Web 版のタブを裏に回したとき・画面を消したときの音声(2026-10-18)

**決定(利用者): 案 B。** 見えている間だけ使う前提で、裏から戻ったときを固める。下は、作ったものと、選ぶ前に調べたこと・案。

#### 作ったもの

- **`RoomKeeper`(`packages/client-core/src/room/roomKeeper.ts`):** 入室を保つ処理。端末に依るところはインターフェースにして各アプリから差し込む。画面の見え方は `AppPresence`(`inactive`・`hidden`・`visible` の3つ)、画面を消させないのは `ScreenAwake`。Web 版の実装は `apps/web/src/roomPlatform.ts`。モバイル版は `AppState`(`inactive`・`background`・`active`)と画面を消させない仕組みで同じものを作れば、フォアグラウンドに戻ったときの入り直しに使える。
- **① PTT を離す:** `inactive`・`hidden` のどちらでも、押しているかによらず `setPressing(false)` を呼ぶ。Web 版は `blur`(→ `inactive`)、`visibilitychange` の hidden と `pagehide`(→ `hidden`)を聞くので、マウスで押したままのタブの切り替え、画面を消す、bfcache に入る、のどれでも離れる。ミュートを外している途中でも、操作は順に行うので最後はミュートにそろう。戻っても押した状態は戻さない。
- **② 戻ったら入り直す:** `visible`(Web 版は `visibilitychange` の visible と、bfcache から戻った `pageshow`)で、切断されていれば新しいトークンを取り、同じ `Room` で入り直す(`RoomSession.rejoin`)。マイクのトラックは作り直してミュートのまま publish し、履歴を読み直して切れていた間の行を埋める(つなぎ直しと同じ `syncHistory`)。字幕は画面に残る。同じ人がほかで入室した(`DUPLICATE_IDENTITY`。入り直すと追い出し合う)、退室させられた、ルームが消された、のときは入り直さない。見えたまま切断されたときは、誤りの知らせの「入り直す」から入り直せる。戻ったときに音が止められていないかも確かめ直し(`room.canPlaybackAudio`)、止められていれば「音を出す」を出す。
- **③ 画面を消させない:** 入室中で見えている間だけ Screen Wake Lock を取る。隠れたら放し(ブラウザも外す)、戻ったら取り直す。使えないブラウザ・断られたとき(省電力のモードなど)は何もせず、放すまで求め直さない。
- **④ 知らせ:** 入室中に5秒以上隠れていた、または隠れている間に切断されていたら、戻ったときに「画面を離れていた間の声は、聞こえていなかったかもしれません。字幕と履歴で追えます。」を、知らせの欄に小さく(`text-fg-muted`)出す。「閉じる」で消える。
- **確かめたこと:** Vitest(`roomKeeper.test.ts`)で ①〜④ を確かめた。ローカル(`mise run dev`)の Chromium(Playwright)で、マウスで押したまま別のページを前に出す(`blur`)と離れること、`visibilitychange` の hidden・`pagehide` で離れること、`freeze`・`pagehide` で livekit-client が切断した後に visible・`pageshow` で入り直すことを確かめた。ただし devContainer の Xvfb ではタブの切り替えで `visibilityState` が変わらず、`visibilityState` の差し替えとイベントを送って確かめた。Wake Lock は自動操作の Chromium では断られ、取れることは確かめていない。

#### 調べたこと

Web 版は「開いている間だけ使う」(上の「Web 版で決めたこと」)が、開いたままタブを切り替える、PC で別のウィンドウに移る、スマートフォンで画面を消す・ホームに戻る、は普通に起きる。そのときの受信(ほかの人の声と翻訳の音声)・送信(PTT)・接続がどうなるかを調べた。**確かめたこと**は文書・ソースで裏を取ったもの、**推測**は実機で確かめていないもの。

#### B を入れる前のつくり(調べたとき)

- 受信は、購読した音声トラックを `track.attach()` の `<audio>` に付けて鳴らす(`apps/web/src/roomPlatform.ts`)。`webAudioMix` と `adaptiveStream` は使っていない(`new Room({ adaptiveStream: false, dynacast: false })`)。
- マイクは入室時にミュートのまま publish し、PTT の間だけミュートを外す。ミュートは `MediaStreamTrack.enabled = false` で、トラックは止めない(マイクを掴んだまま)。
- PTT は、Space を押したままタブを離れたら `window` の `blur` で離したことにする。ボタンは `setPointerCapture` と `pointerup`・`pointercancel` で離す。`visibilitychange` は見ていない。
- 自動再生で止められたら(`RoomEvent.AudioPlaybackStatusChanged`)、「音が止められています」と出し、押すと `startAudio()` を呼ぶ。PTT を押したときにも `startAudio()` を呼ぶ。
- 切断されたら(`RoomEvent.Disconnected`)誤りを出すだけで、自動では入り直さない。

#### livekit-client(2.22.3)の振る舞い(ソースで確かめた)

- **`freeze` で切断する。** `Room` は接続すると `window` の `freeze`(Page Lifecycle API。Chrome だけにある)を常に聞き、来たら `disconnect()` する。`disconnectOnPageLeave`(既定は true)のときは `pagehide` と `beforeunload` でも切断する。タブを切り替えただけでは `pagehide` は来ない。
- **見えなくなっても受信の音は止めない。** `Track` は `visibilitychange` を聞くが、見えるようになったときに動画の要素を `play()` し直すだけ。音声の要素には何もしない(`adaptiveStream` の動画の購読の一時停止とは別)。
- **iOS では無音の `<audio>` を鳴らし続ける。** `startAudio()` は iOS で、空の音声トラックを付けた見えない `<audio>`(`livekit-dummy-audio-el`)を置く。コメントには「iOS は、自分で音声を publish しておらず、ほかに鳴っている音もなければ、`<audio>` の再生を止める」とある。ページが隠れると、ロック画面に再生の操作が出ないよう、この要素の `srcObject` を外す。見えるようになると戻して `startAudio()` を呼び直す。
- **戻ったときのマイクの取り直し。** モバイル(`isMobile()`)では、見えるようになったときに、マイクのトラックが止まっていれば(`readyState` が `ended`、OS にミュートされている、など)取り直す。ただし**ミュート中のトラックは対象外**。代わりに `unmute()` が、トラックが `ended` なら取り直してからミュートを外す。つまり、裏でマイクが止まっても、次に PTT を押したときに取り直す(その分、最初の声が遅れる)。
- **OS がマイクをミュートしたとき。** トラックの `mute` イベントから5秒たっても戻らなければ、送信を止める(`pauseUpstream`)。`unmute` イベントで戻す。

#### ブラウザの振る舞い(文書で確かめた)

- **Chrome の freeze(PC):** Chrome 133 から、省エネ(Energy Saver)が有効なとき、5分を超えて隠れていて音も出ておらず、CPU を多く使うタブを凍結する。ただし**マイク・カメラ・画面の取り込み、WebRTC の接続を使うタブは対象外**。凍結されたページでは、タイマーも fetch のコールバックも動かない。
- **Chrome のタイマーの間引き:** 隠れたタブのタイマーは1秒に1回にまとめられる。5分を超えて隠れ、30秒以上音が出ていないページは1分に1回まで間引かれるが、**WebRTC を使っている(データチャネルが開いている、生きたメディアのトラックがある)ページは対象外**。
- **捨てられないもの:** 隠れたページでも、音を鳴らしている・WebRTC を使っているページは、資源がひどく足りないときを除いて捨てない(Page Lifecycle API の説明)。
- **自動再生:** 利用者がそのサイトを操作した後なら、音の出る再生を許す(ブラウザごとに細部が違う)。止められたかは `play()` の拒否(`NotAllowedError`)で分かる。`navigator.getAutoplayPolicy()` は Firefox にしかない。
- **iOS Safari の WebRTC(WebKit の bug と Apple の開発者フォーラム):** WebKit の技術者は「マイクを取り込んでいるページは裏に回っても止められない(通信も描画も続く)。ただし電話がかかると取り込みが止まり、トラックはミュートされ、ページは止められうる」と書いている(bug 204681)。一方で、裏に回して30秒ほどでマイクのトラックが `ended` になる報告(同じ bug、iOS 13。未解決のまま)、画面を消す・裏に回すと WebRTC と Web Audio が止まるという報告(2025年2月の開発者フォーラム。返答なし)もある。**ホーム画面に置いた Web アプリでは、裏に回す・画面を消すとマイクを失う**報告がある(bug 239602。Safari のタブでは保たれる、とある)。
- **使える API と対応(MDN の互換データ 6.1.0):**

  | API | 使いどころ | Chrome(Android) | Safari(iOS) | 備考 |
  | --- | --- | --- | --- | --- |
  | Screen Wake Lock(`navigator.wakeLock.request("screen")`) | 入室中は画面を消さない | 84 | 16.4(ホーム画面の Web アプリは 18.4) | 安全な文脈(HTTPS)だけ。**ページが隠れると自動で外れる**ので、見えるようになったら取り直す。省電力のモードでは断られることがある |
  | Audio Session(`navigator.audioSession.type = "play-and-record"`) | 通話として扱わせる(出力の経路、ほかのアプリの音に割り込まれない) | なし | 16.4 | 実験的。`state` が `interrupted` になるのを見て、電話などでの中断を知れる |
  | Media Session(`navigator.mediaSession`) | ロック画面・通知に「入室中」と出す、操作のボタン | 57 | 15 | 再生中の media 要素があるときに出る。livekit-client はロック画面の操作を出さないよう、裏では無音の要素を外している |
  | Page Lifecycle の `freeze` / `resume` | 凍結を知る | 68 | なし | Safari は `pagehide` / `visibilitychange` だけ |

#### 推測(実機で確かめていない)

- **PC(Chrome・Edge・Firefox・Safari)でタブを裏に回す:** 受信の音は鳴り続ける。WebRTC の接続があるので、Chrome の凍結とタイマーの強い間引きの対象にならず、接続も保たれる。ミュート中のマイクのトラックも「生きたメディアのトラック」なので、話していない間も対象外になるはず。
- **Android Chrome で画面を消す・ホームに戻る:** Chrome はタブがマイクを使っている間、通知を出し続ける仕組み(`MediaCaptureNotificationService`)を持つので、受信も送信も続く見込み。ただし端末の省電力(メーカーごとの独自の制限を含む)で Chrome ごと止められることがある。
- **iOS Safari で画面を消す・ホームに戻る:** 報告が割れていて、**受信が続くとは当てにできない**。ミュートしてもマイクのトラックは止めていないので、「取り込み中のページ」として止められずに済む可能性はあるが、`enabled = false` のトラックを WebKit が取り込み中と見るかは確かめていない。止められた場合、戻ったときに livekit-client が自分でつなぎ直す(ICE の再接続)か、`Disconnected` になる。電話の着信では確実に止まる。
- **PTT を押したまま画面を消す(スマートフォン):** タッチは `pointercancel` で終わる見込み(今の処理で離せる)。来なければ、押したままの状態が残る。
- **PTT を押したまま別のタブに移る(PC):** Space のときは `blur` で離せる。マウスで押したまま Ctrl+Tab などで移ると、`pointerup` が来ずに押したままになりうる(`blur` は `window` のフォーカスが外れたときに来るので、タブの切り替えでも来る見込みだが、`visibilitychange` の方が確か)。

#### 案

| 案 | 中身 | 良い点 | 悪い点 |
| --- | --- | --- | --- |
| A. 今のまま | 何も足さない | 手間がない | iOS では画面を消すと聞こえなくなりうる。切断されても戻ったときに入り直さない。PTT が押したままになる隙が残る |
| B. 見えている間だけ使う前提で、裏から戻ったときを固める | ① 隠れたら(`visibilitychange` の hidden、`pagehide`、`blur`)必ず PTT を離す。戻っても押した状態は戻さない。② 戻ったら状態を確かめる: 切断されていれば自動で入り直し、履歴を埋める(つなぎ直しと同じ処理)。音が止められていれば「音を出す」を出す。③ 入室中は Screen Wake Lock を取り、画面が勝手に消えないようにする(戻ったら取り直す)。④ 隠れていた間の声は聞けていないかもしれないので、字幕と履歴で追えることを画面に書く | 確実に効く範囲だけで作れる。プライバシー(押したまま送り続ける)を守れる。手間が小さい | 画面を自分で消した・ホームに戻ったときの受信は、端末とブラウザ任せのまま |
| C. B に加えて、裏でも受信を保つよう手を尽くす | B に加え、Safari では `navigator.audioSession.type = "play-and-record"`、Media Session に「〇〇 に入室中」と出す。iOS では受信を Web Audio にまとめる(`webAudioMix`)ことも試す | 裏でも聞こえる機会が増える(推測) | 効くかは iOS の版で変わりうり、実機で確かめる手間が大きい。ロック画面に操作が出るなどの副作用がある。ホーム画面の Web アプリではマイクを失う報告がある |
| D. 隠れたら自分から退室する | 隠れたら切断(マイクも放す)し、戻ったら入り直す | 振る舞いが端末によらず一定。マイクの表示もすぐ消える | PC で別のウィンドウを見ながら聞く使い方ができない。出入りが頻繁になり、入室の待ち時間が毎回かかる |

**推奨: B(利用者が選んだ)。** Web 版は「開いている間だけ使う」と決めていて、裏や画面を消した後も確実に聞く必要がある人にはモバイル版(バックグラウンドの音声を作る。「通知とバックグラウンド音声」)を案内する。B のうち ① はプライバシーに関わるので先に入れる。② の自動の入り直しは、`RoomSession` のつなぎ直しの処理を使い回して `packages/client-core` に置く(モバイル版のフォアグラウンド復帰でも使える)。C は、利用者から「iPhone のブラウザで画面を消しても聞きたい」と要望が出たら、iOS の実機で小さく試してから決める。

**実機で確かめること(B を入れたので、まだ):** iPhone(Safari のタブ、ホーム画面の Web アプリ)・Android(Chrome)・PC(Chrome、Safari)で、① タブの切り替え、② ホームに戻る、③ 画面を消す、④ 電話の着信、のそれぞれで、受信の音が続くか、何秒で止まるか、戻ったときに `Disconnected` か自動のつなぎ直しか、PTT を押したままにした場合に離れるか、を記録する。

### テナントとルームの種別(2026-10-23)

**決定(利用者): テナントを入れ、ルームに種別(Public・Private・Connect)、オーナー、アーカイブを足す。** 利用者の言葉では次のとおり。

- **Public:** テナントの中の誰でも、好きに参加できる。
- **Private:** 管理者かルームのオーナーに招待された人だけが参加できる。
- **Connect:** ほかのテナントの人と混ざれる。招待された人だけが参加できる。
- **オーナー:** ルームの役割。複数人を割り当てられる。ルームは誰でも好きに抜けられるが、最後のオーナーは抜けられない(抜ける代わりにアーカイブする)。アーカイブは、ほかにメンバーがいてもできる。

#### テナントと管理する人

- **決定(利用者): 運営者とテナントの管理者を分ける。** 運営者(Cognito の `operator` グループ)がテナントを作り、ユーザーをテナントに入れる。運営者はルームの中身を扱わない。今までの管理者(`admin` グループ)は、自分のテナントの中だけを管理する(ルーム、メンバー、ユーザーの一覧、Connect の申請)。グループは今までどおり Cognito で付ける。
- **テナントの持ち方:** tenants テーブル(`tenant_id`、`name`)。`tenant_id` は運営者が付ける、英小文字・数字・ハイフンの 2〜32 文字。Connect の申請で相手に伝えるので、人が読める ID にした。
- **ユーザーの所属:** users の行に `tenant_id` を持つ(1人1テナント)。Cognito の属性にしてトークンに入れる案は、トークン生成の Lambda が要り、所属を変えてもトークンを取り直すまで効かないので取らなかった。API はリクエストのたびに users の行を1件読む(GetItem)。所属の無い人は、プロフィールの登録だけができる。運営者は、プロフィールを登録した人の一覧(所属の無い人を含む)から所属を決める。
- **すべてをテナントで分ける:** ルームの一覧、作成、招待できるユーザー、管理者の権限は、どれも自分のテナントの中だけ。Connect だけが、2つのテナントにまたがる。

#### ルームの種別と権限

- **ルームは誰でも作れる(決定: 利用者)。** 作った人がオーナーになる。種別は Public か Private を選ぶ(後から2つの間で変えられる)。Connect は、下の申請でしか作れない。
- **room_id はサーバーが作る:** 前は管理者が打っていたが、誰でも作れるようにしたので、テナントをまたいで重ならないよう乱数(12 文字)にした。LiveKit のルーム名にもそのまま使う。
- **招待はすぐに反映する(決定: 利用者):** オーナーか管理者がメンバーに足すと、承諾を待たずにメンバーになる。嫌なら抜ければよい。
- **権限の表:**

  | 操作 | 誰が |
  | --- | --- |
  | Public に参加する | 同じテナントの誰でも |
  | 抜ける | 自分で。最後のオーナーは抜けられない(409) |
  | メンバーを足す・外す、オーナーにする・戻す | ルームのオーナーか、ルームに関わるテナントの管理者。相手は**自分のテナントの人だけ** |
  | 名前・種別(Public と Private の間)を変える | オーナーか管理者 |
  | アーカイブする・戻す | オーナーか管理者 |
  | ルームを消す | ルームを作ったテナントの管理者 |
  | 入る(LiveKit のトークン)・履歴を読む | メンバーだけ |

- **最後のオーナー:** オーナーが1人だけのとき、その人を抜けさせる・外す・メンバーに戻す操作は、誰がしても 409 にする。先にほかの人をオーナーにするか、アーカイブする。移した前のルームにはオーナーがいない(管理者が管理する)が、それは許す。2人のオーナーがまったく同時に抜けると、0 人になりうる(読んでから書くので)。そのときも管理者が管理できるので、条件付きの書き込みにはしなかった。
- **管理者もメンバーでなければ入れない:** 前は管理者はどのルームにも入れ、履歴も読めた。テナントをまたぐ Connect があり、「管理コンソールではルームの中身を扱わない」(上の節)とも揃うので、メンバーだけにした。管理者は自分をメンバーに足せる。
- **アーカイブ:** 読むだけのルームにする。メンバーは一覧の「アーカイブ」で履歴を読めるが、入れず(トークンを出さない)、送れず、消せない。アーカイブしたら LiveKit のルームを消して全員を切る。オーナーか管理者が戻せる。メンバーは抜けられる(最後のオーナーの決まりは同じ)。

#### Connect の申請

**決定(利用者): テナント A の管理者が、テナント B の ID を打って Connect を申請する。B の管理者には申請が届いていることが分かり、受けると Connect のルームが1つできる。** オーナーは申請した A の管理者と受けた B の管理者で、それぞれが自分のテナントのメンバーを出し入れする。

- **申請中のルームとして持つ:** 申請は、rooms の行に `kind: connect`、`connect_status: pending`、`tenant_id`(A)、`connect_tenant_id`(B)を持たせて作る。受けたら `active` にし、受けた人をオーナーに足す。断る・取り下げると、行を消す。別のテーブルを作らず、ルームの一覧と同じ索引で引ける。申請中は、メンバーの一覧に出さず、入れない。
- **索引:** rooms に GSI を2つ足す(`tenant_id-index` と、Connect の相手の `connect_tenant_id-index`)。「テナントのルーム」は2つを Query してまとめる。Public の一覧(参加できるルーム)も `tenant_id-index` から引く。
- **Connect のルームのメンバーの行には、その人のテナントを持たせる**(`tenant_id`)。オーナーと管理者は、自分のテナントの行だけを変えられる。
- **2つのテナントだけ:** 3つ以上のテナントで混ざることは、今は作らない。要るようになったら、`connect_tenant_id` を別の行に分ける。

#### ユーザーの3つの状態の表し方

利用者から「ユーザーのルームに関する状態が増える(入っていない・入っているがマイクとスピーカーは使っていない・使っている)が、分かりにくくしたくない」と相談があり、次を提案して採った。

- **言葉を2つに分け、「入室」という言葉はやめる。** 「入室」は、メンバーになることにも、音声をつなぐことにも取れるため。
  - メンバーかどうか: **参加する / 抜ける**。一覧と設定に置く(たまにしかしない操作)。
  - 音声: **音声をつなぐ / 切る**(ヘッドセットのアイコン)。ルームの画面の真ん中に置く。マイクとスピーカーは1つにまとめる(PTT なので、マイクは押している間しか使わない)。
- **3つの状態の見え方:**

  | 状態 | 見え方 |
  | --- | --- |
  | 1. 参加していない | 一覧の「参加できるルーム」(Public だけ)に「参加する」で出る |
  | 2. メンバー(音声なし) | 一覧の「自分のルーム」に出る。ルームの画面ではタイムラインを見て、テキストと画像を送れる。下の PTT の場所に「音声をつなぐ」 |
  | 3. 音声中 | 下に PTT。どの画面にいても、画面の下に「音声中」の帯を出す。一覧の行に「音声中」の印 |

  Slack のチャンネルとハドル、Discord のテキストと音声のチャンネルと同じ考え方で、慣れている人が多い。

- **状態 2 もリアルタイムで見る・書ける(決定: 利用者):** ルームの画面を開いている間は、LiveKit にデータだけでつなぐ(マイクを publish せず、音声のトラックを購読しない)。字幕・テキスト・画像はすぐ届き、テキストも送れる。画面を離れたら切る(音声中なら切らない)。
  - **Agent への知らせ方:** 参加者の属性 `audio`(`on` / `off`)。Agent は、翻訳の音声と読み上げは `audio` が `on` の人の言語にだけ作り、訳の字幕はルームにいる全員の言語に作る。属性が無い参加者(前のアプリ)は `on` とみなす。
  - **属性を変えるのは API:** 入るときはトークンに入れ、つないだまま切り替えるときは `PUT /rooms/{room_id}/audio` で、API が LiveKit の UpdateParticipant を呼ぶ。参加者が自分の属性を変えられる権限(`canUpdateOwnMetadata`)は、表示名や言語まで変えられてしまうので渡さない。
  - **費用:** 状態 2 の人も LiveKit の参加者の分数に数えられる。音声を購読しないので、帯域はほぼ掛からない。push 通知は今までどおり、LiveKit にいない人にだけ送る(状態 2 で画面を開いている人には送らない)。
- **音声は複数のルームに同時につなげる(決定: 利用者)。** PTT は、ふだんは音声をつないでいるルームの全部に届く。画面の下の帯にルームごとの PTT を置き、そこから押せばそのルームだけに届く。
  - 主の PTT(ルームの画面の下と、帯)は「全部のルーム」と分かるよう、2つ以上つないでいるときはルームの数を出す。
  - Agent はルームごとにいるので、全部に話すと、それぞれのルームで書き起こし・翻訳・保存される(費用もルームの数だけ掛かる)。
  - **マイクは1本を分けて使う:** ルームごとに `getUserMedia` を呼ぶと、iOS の Safari では前に取ったマイクのトラックがミュートされる(推測。WebKit の振る舞いとして知られているが、この版で確かめていない)。そこで、1本のマイクのトラックを `clone()` してルームごとに publish する。ミュートはトラックごとなので、ルームごとの PTT ができる。
  - タブを裏に回したときの決まり(上の案 B)は、音声中のルームのすべてに当てる(PTT は全部で離す、戻ったら全部で入り直す)。画面を消させないのは、音声中のルームが1つでもある間だけ。

#### 前のデータの移し方

`services/api` の `migrate_tenants.py` を1回実行する(README の「ローカル環境」)。テナントを1つ作り、所属の無いユーザーをそこに入れ、`tenant_id` の無いルームを Private にしてそのテナントに入れ、メンバーの行に役割(`member`)とテナントを書く。オーナーは決めない(管理者が決める)。何度実行してもよい。

音声・チャット・字幕の配信は LiveKit に集約し、履歴・メディア・トークン発行は AWS サーバーレス、翻訳と文字起こしは Agent から OpenAI に任せる。

クライアントは LiveKit に音声とチャットを送り、Agent が各話者の音声を購読して OpenAI に渡す。翻訳音声と字幕は LiveKit に戻して配信し、履歴・画像・動画・録音は AWS 側で持つ。

## 採用技術

サーバーレスにするのは AWS 側の API・履歴・メディアで、常時接続が要る LiveKit と Agent はサーバーレスにならない。

## 処理の流れ

入力は音声でもテキストでも LiveKit に送り、Agent が処理して、翻訳前と後のテキスト・音声を LiveKit で配信する。画像・動画だけは LiveKit を通さず、AWS 側で処理する。

&#91;embedded content: 処理の流れ · 音声とテキストの2経路\]

| 入力 | 翻訳前テキスト | 翻訳前音声 | 翻訳後テキスト | 翻訳後音声 |
| --- | --- | --- | --- | --- |
| 音声 | STT で作る | 入力した音声をそのまま使う | 翻訳前テキストをテキスト翻訳で作る | STS が作る |
| テキスト | 入力したテキストをそのまま使う | TTS で作る | テキスト翻訳で作る | 翻訳後のテキストを TTS で作る |

翻訳後のテキストと音声は、翻訳先の言語がルームにあるときだけ作る。

### 音声(PTT / 発話検知)

1. アプリが API Gateway + Lambda から LiveKit のトークンを取得し、ルームに入る。
2. 音声トラックは入室時に publish しておき、ボタンを押している間(または発話検知の間)だけミュートを外す。方式は PoC で確定する。
3. Agent が話者のトラックを1回だけ購読する。
4. 翻訳前のテキストを STT(gpt-realtime-whisper、話者ごとに1本)で作り、データチャネルで配信する。元の音声はそのまま配信する。
5. 翻訳先の言語がルームにあれば、言語ごとに STS セッション(gpt-realtime-translate)へ流し、翻訳後の音声(言語別のトラック)を配信する。翻訳後のテキストは、翻訳前のテキストを言語ごとにテキスト翻訳(gpt-6-luna)で作り、データチャネルで配信する(「構成の案」の B。PoC で STS の翻訳テキストより質が高かった)。
6. 聞き手は、自分の言語のトラックを購読する。話者と同じ言語の聞き手には翻訳を作らない。
7. 録音は Agent が話者ごと・発話ごとに S3 に保存する。テキストは、Agent が API 経由で DynamoDB に保存する。

### テキスト入力

1. アプリがテキストを LiveKit に送る(データチャネル)。
2. Agent が受け取り、翻訳前のテキストをそのまま配信する。
3. 翻訳前のテキストを TTS で読み上げ、翻訳前の音声として配信する。
4. 翻訳先の言語がルームにあれば、言語ごとにテキストを翻訳して配信し、翻訳後のテキストを TTS で読み上げて、翻訳後の音声として配信する。
5. テキストは、Agent が API 経由で DynamoDB に保存する。
6. 読み上げ音声(翻訳前・翻訳後)は、Agent が LiveKit のトラックとして配信する。言語ごとに別のトラックにして、聞き手は自分の言語のトラックを購読する。

### 画像・動画

1. アプリが Lambda に署名付き URL を要求し、S3 へ直接アップロードする。
2. アップロード後、アプリが complete を呼ぶ。API がメディアの URL をチャットメッセージとして DynamoDB に保存し、LiveKit の Server API でルームに配信する(「画像・動画のルームへの配信」を参照)。
3. 受信側は CloudFront の URL で表示・再生する。

## 翻訳・文字起こしの設計

翻訳セッションは「話者のトラック × 翻訳先の言語」ごとに1本作り、Agent が LiveKit と OpenAI の間を中継する。仕様は [OpenAI の公式ガイド](https://developers.openai.com/api/docs/guides/realtime-translation)に基づく。

| 項目 | 設計 |
| --- | --- |
| セッション数 | 同時に話している話者数 × 翻訳先の言語数。例: 2人が同時に話し、聞き手の言語が4種類なら8セッション |
| 接続 | Agent から WebSocket で `/v1/realtime/translations?model=gpt-realtime-translate` に接続する。API キーは Agent に置き、アプリには渡さない |
| 入力音声 | 24kHz、PCM16、モノラルを base64 にして `session.input_audio_buffer.append` で送る。LiveKit の 48kHz からリサンプリングする |
| 翻訳先の言語 | `session.update` で `session.audio.output.language` を指定する |
| 受信するイベント | `session.output_audio.delta`(翻訳音声)、`session.output_transcript.delta`(翻訳テキスト)。翻訳テキストは追記専用の断片で、連結時に空白を挟まない。配信する字幕には使わない(B を採用。ログや比較には残す) |
| 翻訳音声の形式 | 24kHz、PCM16、モノラル(公式に記載がなく、実測で判断。`session.audio.output.format` は `unknown_parameter` になり、指定できない)。1チャンク 9600 サンプル(0.4秒)が話している間は約0.4秒ごとに届き、話していない間も無音(ほぼ0)のチャンクが届き続ける。LiveKit のトラック(48kHz)にはリサンプルして流す。当初は 48kHz と誤って判断していた(「翻訳音声のサンプルレート」) |
| 原文のテキスト | 翻訳セッションとは別に、話者ごとに1本の gpt-realtime-whisper で作る。翻訳セッションごとに有効にすると、言語数ぶん重複して課金される可能性があるため。接続先は `/v1/realtime?intent=transcription` で、`session.update` に `type: "transcription"` を指定する(PoC で動作を確認) |
| 話者の分離 | 話者ごとに別トラックで渡す。混ぜない(OpenAI の公式推奨) |
| 話者と同じ言語の聞き手 | 翻訳セッションを作らない。話者の言語はユーザープロフィールで判定する |
| 遅延の扱い | 元音声はすぐ流し、翻訳音声と字幕は数秒遅れて届く別チャンネルとして扱う |

### 選べる翻訳言語

ユーザーが選べる翻訳言語は、OpenAI の出力言語13言語。スペイン語、ポルトガル語、フランス語、日本語、ロシア語、中国語、ドイツ語、韓国語、ヒンディー語、インドネシア語、ベトナム語、イタリア語、英語。入力は70以上の言語から自動で検出される。[OpenAI の公式クックブック](https://developers.openai.com/cookbook/examples/voice_solutions/realtime_translation_guide)で確認した。

### 公式に書かれている制約

- **翻訳先と同じ言語は訳されない。** 翻訳先の言語の音声は、翻訳されず無音になることがある。言語を混ぜて話す話者では、翻訳先に含まれる言語の部分が欠ける。元の音声は残し、翻訳音声が流れている間は小さくする(完全には消さない)。
- **用語集やプロンプトは使えない。** カスタムプロンプト、用語集、読みの指定、声の選択はできない。固有名詞や専門用語を誤ることがあるため、評価用の用語セットで確認する。
- **声は話者に追従する。** 翻訳音声は、話者の声の調子・高さ・話し方に合わせて作られる。話者ごとにセッションを分けるので、声はその話者のものになる。
- **ノイズ低減を選べる。** `near_field`(ヘッドセットなどの近接マイク)と `far_field`(ノート PC や会議室のマイク)から選ぶ。既定は無効。PoC では、`near_field` が小さい声や質の悪い録音を消し、訳が出なくなることがあった(「データセットでの評価」を参照)。当面は無効にし、雑音のある実機の録音で比べてから決める。

### 利用上限

- 上限は「1分あたりに処理できる音声の分数」で決まり、利用ティアごとに Tier 1 が 50、Tier 2 が 200、Tier 3 が 400、Tier 4 が 650、Tier 5 が 850。無料枠では使えない。([モデルページ](https://developers.openai.com/api/docs/models/gpt-realtime-translate))
- 1つのセッションが毎分1分ぶんの音声を使うと考えると、Tier 5 で同時に850セッション。8セッションのルーム(2話者 × 4言語)なら、約100ルームが同時に使える目安(試算)。
- 無音を送り続ける分も課金される(PoC で実測。「翻訳の PoC の結果」を参照)。上限の消費も同じ数え方だと考えられるが、上限のほうは未確認。

### セッションの寿命と遅延(追加調査)

- **課金:** 公式は「音声の長さ」で課金されるとだけ書く。PoC の実測では、送った入力音声の長さ(無音を含む)で課金され、セッション単位の切り上げはなかった。
- **接続時間:** 最大接続時間、アイドルタイムアウト、再接続の手順は記載がない。通常の Realtime には60分の上限があるという投稿があるが、翻訳に当てはまるかは不明。Agent 側で再接続し、長時間のルームではセッションを作り直す前提にする。
- **遅延:** 出力は0.4秒刻みで届く(翻訳テキストの `elapsed_ms` は200ms刻み)。公式の遅延の数値はない。第三者の計測(LiveLingo)では、日本語の音声で約3.3秒の遅れが一定だった。通訳型で文の動詞を待つため、語順が違う日英では長くなる可能性がある(推測)。
- **重なり・短い発話・末尾の欠け:** 記載がない。話者ごとの別ストリームは公式の推奨。末尾の欠けは、ボタンを離した後に数百ms の無音を送ってから `session.close` を送る案がある(推測)。PoC で確かめる。
- **セッションの使い回し:** 記載がない。無音も課金されるため、入室中ずっと無音を送り続けて維持する方式は取らない(「PTT の運用」を参照)。

### 翻訳の PoC の結果(2026-10-08)

`services/agent/poc/translate_bench.py` で、WAV を実時間のペースで送って測った。入力は macOS の `say` で作った読み上げ音声(日本語5文、英語4文)で、人の声ではまだ試していない。

| 項目 | 結果 |
| --- | --- |
| 翻訳テキストの初回 | 発話の開始から 0.6〜5.0秒。多くは 1.2〜2.4秒 |
| 翻訳音声の初回 | 発話の開始から 1.4〜5.5秒。多くは 1.8〜2.5秒で、第三者の計測(約3.3秒)より短い。ただし回によって 3.5秒以上になる(同じ文の10回中4回) |
| 日→英と英→日 | 差は見えなかった |
| 翻訳音声の最後 | 発話の終了から 0.8〜4.3秒 |
| `session.closed` | `session.close` から 4〜6秒後。翻訳音声が終わった後も数秒待つ |
| 末尾の欠け | 無音を足さずに `session.close` を送っても、ほとんどの回で最後まで届いた(同じ文で5回中5回)。最初の1回だけ、翻訳音声が 0.8秒分しか届かなかった(原因は不明。当時は 48kHz とみなして 0.4秒分と書いていた) |
| whisper | 最初の文字は発話の開始から約1.0〜1.3秒。`input_audio_buffer.commit` から約0.6秒で確定(`completed`) |
| 無音だけの長いセッション | 無音を5分送り続けても切断されず、`session.closed` まで正常に終わった |
| 送信を止めたとき(2026-10-09) | 翻訳テキストも翻訳音声も止まる。出力は入力の音声が届くのに合わせて進み、続きは次に音声を送り始めたときに届く。止めたまま時間を置いてから `session.close` を送ると、テキストは残りが届くが、翻訳音声はほとんど届かない(3回中3回。0〜0.8秒分。当時は 48kHz とみなして 0〜0.4秒分と書いていた) |
| 使い回し(2026-10-09) | 発話の後に無音を3秒送ってから止めると、翻訳はその間にほぼ出きる。ただし1チャンク(0.4秒分)の翻訳音声が残り、次の発話を送り始めたときに流れた。2回目の発話の初回の字は 4.2秒で、1回目(1.0秒)より遅かった(1回だけの計測) |
| 短い発話 | 「はい」「Copy that.」は、翻訳テキストも翻訳音声も出なかった(3回中3回)。whisper は文字にできた |

訳の誤り(数字・固有名詞・聞き間違い・付け足し)が目立った。

- 数字: 「250 units」を「200台」と訳した(同じ文の6回中4回)。元にない「1月17日」を足したこともある。
- 固有名詞: 「品川」が「Hina River」「Shinigawa」になった。「三番ゲート」が「BANG BANG GATE」になった。
- 聞き間違い: 「すみません」が「To Sumire」になった。
- 付け足し: 元の文にない「なんとか間に合わせましょう」「Got it?」「Yes」が付いた。
- 同じ文でも、回ごとに訳と遅延が変わる。

設計への反映(案):

- 翻訳音声は LiveKit のトラックの 48kHz にリサンプルして流す(当初は 48kHz のまま流すとしていたが誤り。「翻訳音声のサンプルレート」)。翻訳音声の無音のチャンクも届き続けるので、遅延の計測やログでは無音を除いて扱う。
- 翻訳は誤りうる前提で、聞き手の画面では原文の字幕(whisper)を併記する。数字や固有名詞は原文を見れば確かめられるようにする。
- 「はい」のような短い応答は翻訳されないことがある。元の音声を小さくしすぎない(「公式に書かれている制約」の方針を保つ)。
- PTT を離したら `session.close` を送り、`session.closed` まで最大10秒ほど受信を続ける。無音を足すかは、人の声で再確認してから決める。

課金(2026-10-08 に実測): 送った入力音声の長さで課金され、無音も含む。

- 計測の全体(翻訳29セッション、whisper 11セッション)で、送った音声の長さから出した試算 0.14 USD に対し、請求は 0.15 USD だった。接続時間で数えた試算(0.23 USD)より少なく、`session.close` から `session.closed` までの待ちは課金されていない。セッションごとに1分へ切り上げる課金でもない(それなら1 USD を超える)。
- 翻訳セッション1本に無音だけを5分送ったところ、請求が 0.17 USD(5分 × 0.034 USD)増えた。
- whisper の無音を単独では測っていない。全体の請求が送った音声の試算と合うので、同じ数え方だと推定する。

接続だけを保つ(2026-10-09): 発話を1回送った後、音声を送らずに20分つないだままにしても切断されなかった。`session.close` から `session.closed` までは35秒かかった(ふだんは4〜6秒)。この20分は課金されなかった(下記)。

### データセットでの評価(2026-10-09)

人の読み上げ音声で、遅延と訳の質を測った。データは FLEURS(validation、1文7〜20秒、ja と en を各20文)と CoVoST 2(test、1文2〜15秒、ja→en と en→ja を各30文)。訳の質は、正解の訳に対する chrF(文字 n-gram の一致度)で見た。手順は `services/agent/poc/README.md` にある。

ノイズ低減の有無で比べた。ほかの条件は同じだが、ノイズ低減なしの回では `session.updated` を待ってから音声を送るように直している(訳が出ない問題には効かなかったことを確かめた)。

| データ | 訳が出なかった(`near_field` → なし) | chrF(`near_field` → なし) |
| --- | --- | --- |
| CoVoST 2 ja→en(30文) | 1 → 0 | 28.9 → 37.9 |
| CoVoST 2 en→ja(30文) | 6 → 3 | 15.2 → 19.9 |
| FLEURS ja→en(20文) | 0 → 0 | 43.4 → 45.5 |
| FLEURS en→ja(20文) | 4 → 0 | 18.9 → 27.5 |

遅延(ノイズ低減なし。秒):

| データ | 初回の字(中央値 / p90) | 初回の声(中央値 / p90) | 最後の声(発話の終了から。中央値 / p90) |
| --- | --- | --- | --- |
| CoVoST 2 ja→en | 2.2 / 4.3 | 2.9 / 5.0 | 1.0 / 1.5 |
| CoVoST 2 en→ja | 2.3 / 4.6 | 2.7 / 5.0 | 0.8 / 1.5 |
| FLEURS ja→en | 3.6 / 6.2 | 4.3 / 7.4 | 0.6 / 1.4 |
| FLEURS en→ja | 2.4 / 3.0 | 3.1 / 4.0 | 0.9 / 1.8 |

whisper の文字起こしは、原文に対する chrF の中央値が 88〜100 で、最初の文字は発話の開始から 1.2〜2.4秒(中央値)だった。

分かったこと:

- `near_field` のノイズ低減は、小さい声を消す。訳が出なかった CoVoST 2 en→ja の6文は、多くが音量の小さい録音(RMS が 16〜238。訳が出た文の多くは 800 以上)だった。同じ6文で、ノイズ低減なしなら5文、音量を正規化して `near_field` なら3文に訳が出た。訳が出なかった残りの文は、whisper も文字にできない質の悪い録音だった。
- 訳の質は、ja→en は意味が通る訳が多い。en→ja は、chrF は低いが、言い換えで点が下がっている訳が多い(例:「湖や池、小川の縁や沼地に生えます」が 12.7)。chrF は日本語の訳の評価に向かないので、言語モデルによる採点か、人の目で見る評価を足す。
- 意味を取り違える誤りもある。「大使館」が「First exam hall」、「took the lead in singing」が「歌うのやめた」、「two phases」が「二つの拠点」になった。原文の字幕を併記する方針(上記)を保つ。
- 長い文(FLEURS の日本語、1文13秒前後)は、初回の声が 4秒を超えることが多い。日本語は文末まで聞かないと訳しにくいためと考えられる。PTT の短い発話では、CoVoST 2 の 2〜3秒が目安になる。
- Common Voice 由来の CoVoST 2 には、読み間違いや質の悪い録音が混ざる。訳が出ない原因を調べるときは、whisper の結果と音量を合わせて見る。

言語モデルによる採点(2026-10-09): chrF は日本語の言い換えを低く見るため、gpt-6.1-sol に、意味が伝わるかを1〜5点で採点させた(基準は原文。正解の訳は一例として渡す。5=意味が完全に伝わる、4=細部のずれのみで用件は伝わる、3=聞き手が誤解しうる)。正解の訳そのものを採点させると平均 4.87〜5.00 で、採点は妥当と見なした。ノイズ低減なしの回を採点した。

| --- | --- | --- | --- |
| CoVoST 2 ja→en(30文) | 3.80 | 53% | 誤訳 14 |
| CoVoST 2 en→ja(30文) | 3.07(録音の良い22文では 3.59) | 43%(59%) | 誤訳 18、欠け 6、訳なし 3 |
| FLEURS ja→en(20文) | 3.65 | 40% | 誤訳 11、数字・固有名詞 5 |
| FLEURS en→ja(20文) | 3.85 | 65% | 誤訳 10 |

- 用件が正しく伝わる訳(4点以上)は、4〜6割にとどまる。誤りの多くは意味の取り違えで、聞き取りの誤り(「大使館」→「First exam hall」)から別の文を作ってしまう型が目立つ。
- 評価の文は、前後の文脈がない1文で、インカムの発話とは中身が違う。ただし、インカムの発話も短く文脈が少ないので、条件は近い。
- 原文の字幕(whisper)の併記は必須と考える。whisper は英語の原文では chrF の中央値 89〜100 で、翻訳より確かだった。

書き起こしのテキスト翻訳との比較(2026-10-09): 同じ音声の whisper の書き起こしを gpt-6-luna(reasoning effort: none)で翻訳し、同じ方法で採点した。書き起こしの聞き取り誤りも含めた比較になる。

| --- | --- | --- | --- |
| CoVoST 2 ja→en | 3.80 → 4.53 | 53% → 87% | 1.15 / 1.55 |
| CoVoST 2 en→ja | 3.07 → 3.73 | 43% → 60% | 1.17 / 1.50 |

- 4つのデータすべてで、テキスト翻訳のほうが訳の質が高い。残る誤りは、書き起こしの聞き取り誤りと、数字・固有名詞(FLEURS ja→en で major 7件)が多い。
- 遅延の性質が違う。gpt-realtime-translate は話している途中から訳が出る(初回の字は発話の開始から約2.3秒、最後の声は発話の終了から約0.9秒)。テキスト翻訳は、発話が終わってから whisper の確定(約0.6秒)と翻訳(最初の文字まで約1.2秒、完了まで約1.5秒)を待つので、訳文は発話の終了から約1.8秒で出始め、約2.1秒でそろう。PTT の短い発話(2〜5秒)なら、訳がそろう時刻の差は約1秒。

構成の案:

| 案 | 翻訳テキスト | 翻訳音声 | 長所 | 短所 |
| --- | --- | --- | --- | --- |
| A(現在の設計) | gpt-realtime-translate | gpt-realtime-translate | 話している途中から訳が出る。声が話者に似る | 用件が伝わる訳が4〜6割 |
| B | whisper + テキスト翻訳 | gpt-realtime-translate | 字幕の質が上がる。費用は A とほぼ同じ | 字幕と翻訳音声の中身が食い違うことがある |
| C | whisper + テキスト翻訳 | テキスト翻訳を TTS で読み上げ | 字幕と音声が一致し、質も高い。翻訳先の言語ごとの音声の課金が TTS の分だけになる | 音声は発話の終了から数秒遅れ、話者の声ではなくなる。テキスト入力の読み上げと同じ仕組みにまとめられる |

**決定(2026-10-09): B にする。** 翻訳音声は gpt-realtime-translate のまま、話している途中から流す。翻訳テキスト(字幕)は、whisper の書き起こしを gpt-6-luna で翻訳して作る。字幕の質が上がり、費用はほぼ変わらない。C は、長い発話で読み上げが話者に追いつかなくなるため採らない(端末で読み上げる形でも見直したが、採らなかった。「端末の音声 API で費用を抑える案」)。

B で決めること:

- **長い発話の字幕の区切り。** 書き起こしを確定させるまで翻訳できないので、PTT を離すまで字幕が出ない。区切りの候補は、whisper の書き起こしの文末(「。」「?」)、Agent 側の VAD で見つけた息継ぎ、その組み合わせ。gpt-realtime-whisper の自動区切り(turn_detection)が使えるかは未確認。区切りが細かすぎると訳の質が下がる。PoC で、短い文をつなげた30秒程度の音声を使って決める。
  - 決めたこと(2026-10-10。値は実機の PoC で見直す): gpt-realtime-whisper は自動区切りに対応していない(公式のリファレンスに「turn detection must be set to null; VAD is not supported」とある)。Agent が区切りを決め、発話の途中でも `input_audio_buffer.commit` を送る。区切りは、音量で見つけた無音と書き起こしの文末の組み合わせにする。区切りが4秒に届くまでは区切らず、文末の後に0.4秒、文末でなくても1秒の無音で区切る(15秒を超えたら文末でなくても0.4秒で区切る)。値は環境変数で変えられる。
  - 字幕は区切りごとに別の `segment_id` にし、`Caption` に `utterance_id`(発話の単位)と `segment_index`(発話の中の順番)を足した。同じ `segment_id` で確定を何回も出すと、古いアプリでは字幕が壊れるため。古いアプリは区切りを別々の字幕として表示する。手順と見るべき点は `services/agent/README.md` の「字幕の区切りを確かめる」にある。
  - 実際の OpenAI と LiveKit で確かめた(2026-10-10。「Agent の結合確認」)。発話の途中の commit の後も同じセッションで書き起こしが続き、`item_id` と区切りの対応は崩れなかった。値は変えない。
- **字幕と翻訳音声の食い違い。** 両者は別々に訳すので、中身が違うことがある。字幕を正とし、画面では字幕を主に見せる。区切りを待つ間は、STS の翻訳テキストを仮の字幕として出し、テキスト翻訳ができたら置き換える案もある(画面のちらつきとの兼ね合い)。

接続だけの時間の課金(2026-10-09): 2日間の請求は 2.52 USD だった。送った音声の長さからの試算(1.50 USD)に、採点とテキスト翻訳の費用(約 0.82 USD)を足すと 2.32 USD。20分の待機も課金されるなら 3.00 USD になるので、接続だけの時間は課金されないと判断した(差の 0.2 USD は、請求の反映の遅れか試算の漏れと考える)。

未確認のまま残っていること: 雑音のある実機の録音での結果(`far_field` を含む)、セッションの最大接続時間(20分は保てた)。

### 端末の音声 API で費用を抑える案(2026-10-16。翻訳音声は採らない。テキスト入力の読み上げは検討中)

ブラウザ、iOS、Android の標準の API で STT、TTS、翻訳をして、OpenAI の費用を抑えられないかを検討した。

**決定(2026-10-23、利用者): 音声の翻訳音声は gpt-realtime-translate のままにし、端末の TTS には置き換えない(構成 B)。** 費用の大半は gpt-realtime-translate(翻訳先の言語ごとに 0.034 USD/分)で、端末で読み上げれば翻訳先が3言語のとき約7分の1になる。それでも、話している途中から話者に似た声で訳が聞こえるほうが、使う人の体験が良いと判断した。端末の読み上げは、短い発話でも聞き終わるまで約4秒遅れ、声が話者のものでなくなり、鳴るかどうかが端末とブラウザに左右される。費用が問題になったら、下の検討から再開する。

**テキスト入力の読み上げ(原文と訳文)は、まだ候補に残す。** 今はサーバーの gpt-realtime-2.1-mini で読み上げて、言語別のトラックで流している(「テキスト入力の翻訳と読み上げ」)。テキストには話者の声がなく、読み上げは届いた全文を読むだけなので、翻訳音声で問題になった遅れと声の違いは小さい。端末の TTS でするかは、声の質、読み上げの許可、PTT 中の漏れ(AEC)、バックグラウンドでの鳴り方を確かめてから決める(下の「端末で読み上げるときの注意」「古いアプリとの互換」はそのまま当てはまる)。

#### 標準の API の対応状況

手元の知識(2026年半ば時点)によるもので、Web で最新の状況は確かめていない。

| | STT | TTS | 翻訳 |
| --- | --- | --- | --- |
| ブラウザ | Web Speech API の `SpeechRecognition`。Chrome、Edge、Safari で使える(`webkit` の接頭辞付きのことが多い)。Firefox では実質使えない。Chrome は基本的に Google のサーバーで認識する(端末内で認識するモードも入りつつある)。基本はマイクの入力だけで、WebRTC で受けた音声などは渡せない | `speechSynthesis`。主要なブラウザすべてで使える。声は OS によって違う。出力をストリームとして取り出せず、スピーカーで鳴らすだけ。利用者の操作を経ないと鳴らない(Chrome は M71 から、ユーザーの操作の前の `speak()` を無視する。iOS の Safari も、最初の `speak()` は操作の中で呼ぶ必要がある) | Translator API と Language Detector API。デスクトップ版の Chrome(138 から)だけ。Safari、Firefox、Android 版の Chrome では使えないとみなす |

| Android | `android.speech.SpeechRecognizer`。実体は Google アプリなどの認識サービスで、端末によって挙動が違う。API 31 以上なら `createOnDeviceSpeechRecognizer` で端末内で認識できる | `TextToSpeech`。ファイルに書き出せる | OS 標準の API はない。ML Kit Translation(Google のライブラリで、端末内で動き、無料)を使うのが定番 |

React Native から使うにはネイティブモジュールが要る。TTS は `expo-speech`、STT はコミュニティ製の `expo-speech-recognition` などがある。翻訳は、iOS の Translation framework と Android の ML Kit を包む自作のモジュールが要りそう。

#### 出てきた案と評価

案: 発話者の端末で STT(テキスト入力なら TTS)をして、音声とテキストの両方を LiveKit に送る。受信者は、翻訳したいときだけ端末でテキストを翻訳し、TTS で翻訳後の音声を作る。

費用の大半は、翻訳先の言語ごとにかかる gpt-realtime-translate(話者の数 × 言語の数 × 0.034 USD/分)にある。whisper は話者ごとに 0.017 USD/分、gpt-6-luna のテキスト翻訳は1発話あたり 0.0001 USD 未満(「コストの目安」と「データセットでの評価」を参照)。この費用の内訳から、案の部分ごとに次のように評価した。

| 部分 | 評価 | 理由 |
| --- | --- | --- |
| 受信者の端末で TTS する | 候補にする(遅れと端末の制約を試してから決める) | 言語ごとの翻訳音声の課金がなくなる。案 C を端末で行う形になる。ただし、翻訳音声は短い発話でも数秒遅れる(下の「案 C を却下した理由の見直し」)。端末の制約(下の「端末で読み上げるときの注意」)と、古いアプリとの互換(下の「古いアプリとの互換」)も要る |
| 受信者の端末で翻訳する | サーバーのままにする | 安くなる額がほぼない。端末の翻訳は gpt-6-luna より質が落ちる見込み(推測。比べていない)。ブラウザではデスクトップ版の Chrome でしか使えない。履歴に訳が残らないか、受信者ごとに同じ訳を作り直すことになる。サーバーなら言語ごとに1回訳せば済む |
| 発話者の端末で STT する | サーバーのままにする | whisper の分は減るが、字幕の質が送り手の環境で決まる(Firefox では使えず、精度も句読点もそろわない)。字幕はルームの全員が見て履歴にも残る。字幕は Agent の参加者のものだけを読む取り決め(「字幕の送信元」)が崩れ、音声と違う字幕を送れてしまう。認識の誤りは訳の誤りになる。モバイルではバッテリーを使い、バックグラウンドでの認識にも制約がある(未確認) |
| テキスト入力の読み上げを発話者の端末で作って送る | 採らない | ブラウザの `speechSynthesis` は出力を取り出せないので、Web 版から送れない。テキストが届けば、受信者が端末で読み上げれば済む |

今の見立て: 移すなら、STT は whisper、翻訳テキストは gpt-6-luna のままサーバーで作り、**読み上げ(翻訳音声とテキスト入力の読み上げ)だけを受信者の端末に移す**。残る課金は、話者ごとの whisper と、ほぼかからないテキスト翻訳になる。翻訳音声を聞きたい人だけが端末で読み上げ、字幕で足りる人は読み上げない、という使い分けもできる。代わりに、翻訳音声は今より数秒遅れる。費用と遅れのどちらを取るかは、下の検証の後に決める。→ 翻訳音声は移さないことにした(上の決定)。残る候補は、テキスト入力の読み上げを移すことだけ。

#### 案 C を却下した理由の見直し

案 C は「長い発話で読み上げが話者に追いつかなくなる」ために採らなかった(「データセットでの評価」の決定)。遅れは2つに分けて考える。

1. **訳文ができるまでの遅れ。** 区切りの確定と翻訳で、区切りの終わりから約2秒かかる。区切りは4秒に届くまで切らない(15秒を超えることもある。「B で決めること」)ので、長い発話の最初の読み上げは、発話の開始から早くても約6秒(4秒 + 約2秒)後になる。gpt-realtime-translate の初回の声(発話の開始から約2.3秒)より、4秒ほど遅い。結合確認では、最初の訳の確定は発話の開始から 8.8秒だった(「Agent の結合確認」)。読み上げを速くしても縮まない。
2. **読み上げがたまっていく遅れ。** 話者が話し続けると、読み上げ待ちが積み上がる。却下した主な理由はこちらで、読み上げを速くすれば解ける。

端末の TTS は、どれも標準の API で話す速さを変えられる。

| | API | 範囲 |
| --- | --- | --- |
| ブラウザ | `SpeechSynthesisUtterance.rate` | 仕様では 0.1〜10(1 が普通)。実際に効く上限は声によって違い、2倍前後で頭打ちになる |
| iOS | `AVSpeechUtterance.rate` | 0.0〜1.0(既定は 0.5)。倍率で指定する値ではないので、何倍に当たるかは測る |
| Android | `TextToSpeech.setSpeechRate()` | 1.0 が普通、2.0 で2倍。上限は TTS のエンジンによる |

`expo-speech` も `rate` を受け付ける。

追いつく方法の案:

- 字幕の区切り(`utterance_id`、`segment_index`)ごとに読み上げる。PTT を離すまで待たずに読み始められる。
- 読み上げ待ちの量(残りの文字数から見積もった秒数)を見て、たまっていなければ1.0倍、たまってきたら1.2〜1.5倍に上げる。自分の言語で聞くので1.3〜1.5倍までは聞き取れる見込み(推測。試す)。
  - 速さは、読み上げを TTS に渡すときに決まる。`speechSynthesis` も `AVSpeechSynthesizer` も、渡した後(待ち行列にあるもの、読んでいるもの)の速さは変えられない。そのため、TTS には1区切りずつ渡し、待ち行列はアプリで持つ。前の区切りを読み終えたら、その時点の待ちの量で次の速さを決めて渡す。読んでいる途中で速くしたいなら、止めて残りを渡し直すしかない(どこまで読んだかは、ブラウザの `boundary` や iOS の `willSpeakRangeOfSpeechString` で取れるが、声によっては届かない)。
- それでも一定より遅れたら、古い区切りを飛ばして字幕だけにする。インカムでは古い内容を聞く意味が薄い。

注意すること:

- 訳文の長さは言語で変わる。英語から日本語に訳すと、読み上げが長くなりやすい(推測)。速さを変えて吸収する。
- Chrome の Google の声は、長い文を読むと途中で止まる不具合が知られている。区切りごとに短く読めば避けやすい。読み終わるまでの長さは前もって分からないので、文字数から見積もる。
- PTT の短い発話(2〜5秒)でも、翻訳音声の遅れは数秒増える。上の「約1秒」は訳文(字幕)がそろう時刻の差で、音声の比較ではない。gpt-realtime-translate は話している途中から声が出るが、端末の TTS は訳文がそろってから読み始め、発話と同じくらいの長さをかけて読む。3秒の発話の例では、gpt-realtime-translate の声は発話の終了から約0.9秒で終わる。端末の TTS は、発話の終了から約2.1秒で訳文がそろい、それから約3秒読むので、終わるのは発話の終了から約5秒後になる。聞き終わるまでの差は約4秒で、発話が長いほど開く。読み始めも、gpt-realtime-translate(発話の開始から約2.3秒、話している途中)に対し、発話の開始から約5秒(発話の終了から約2.1秒)になる。

こうすれば、案 C を却下した主な理由のうち「読み上げがたまっていく」ことは弱まる。一方で、遅れそのものは短い発話でも数秒増え、長い発話では最初の声まで約6秒以上かかる。残るのは「翻訳音声が数秒遅れる」と「話者の声ではなくなる」の2点で、言語ごとの音声の課金がなくなることと比べて決める。インカムとして数秒の遅れを受け入れられるかは、使う人の判断が要る。決める前に、端末の TTS の13言語での声の質と、速さを上げたときの聞き取りやすさ、実際の遅れを試す。

#### 端末で読み上げるときの注意

- **読み上げの許可(ブラウザ)。** `speechSynthesis.speak()` は、利用者の操作を経ないと鳴らない(Chrome は M71 から。iOS の Safari も同じ制約がある)。字幕はデータチャネルで届くので、届いた時点で `speak()` を呼んでも黙って鳴らないことがある。入室のボタンを押したときなどの操作の中で、空の文を一度 `speak()` して解除しておく。解除が切れた(タブを切り替えた後など)ときに気づけるよう、鳴らなかったことを検知できるかも確かめる。
- **エコーキャンセルが効かないことがある。** 今の翻訳音声は WebRTC で再生するので、エコーキャンセル(AEC)が効く。`speechSynthesis` や `AVSpeechSynthesizer` の音は WebRTC の再生を通らないので、AEC が消さないことがある。聞き手が読み上げの最中に PTT を押すと、読み上げの声がマイクに入り、whisper がそれを書き起こして、誤った字幕と履歴ができる(翻訳されて、ほかの人にも読み上げられる)。PTT を押している間は読み上げを止める(または音量を下げる)。止めた区切りは、離した後に続きから読むか飛ばすかを決める。
- **バックグラウンドとオーディオセッション。** 入室中はバックグラウンドでも音声を保つ方針(iOS は audio mode、のちに PushToTalk。Android はフォアグラウンドサービス。「バックグラウンドでの音声」)。端末の TTS をバックグラウンドやロック中に JS から呼んで鳴るかは確かめていない。ブラウザは、裏のタブやロック中に読み上げを止めることがある。iOS の `AVSpeechSynthesizer` は既定でアプリのオーディオセッションを使うので、LiveKit が playAndRecord(voiceChat)にしていると、受話口から小さく鳴ることがある。PushToTalk を入れると、セッションを自分で有効にできないので、読み上げをいつ鳴らせるかも制約を受ける。Android も、`TextToSpeech` の出力の種類(`setAudioAttributes`)と、通話中の音の経路が合うかを確かめる。
- **声がない言語。** 13言語すべての声が、どの OS・ブラウザにもあるとは限らない。ブラウザは `getVoices()` の中身が OS とブラウザで違い、iOS は声を後からダウンロードすることがあり、Android は TTS のエンジンと、入れてある言語のデータによる。声がないときの扱いを決める。字幕だけにするか、その聞き手にはサーバーの読み上げ(今の翻訳トラック)を流すか。後者は、下の互換の仕組みと同じ形でできる。

#### 古いアプリとの互換

今の Agent は、翻訳音声とテキスト入力の読み上げを、言語別のトラック `translation-<言語>` で流す(`services/agent/src/voice_intercom_agent/output.py`)。古いアプリはこのトラックを鳴らすだけなので、Agent がトラックを流すのをやめると、古いアプリでは翻訳音声もテキスト入力の読み上げも聞こえなくなる。古いアプリは使われ続けるので、いきなりは止めない。

- 端末で読み上げられるアプリは、参加者の属性(例: `local_tts`)で知らせる。属性を見るだけなので、proto は変えずに済む。
- Agent は、その言語の聞き手の中に、属性のない参加者(古いアプリ、または声がない端末)が1人でもいれば、今までどおりその言語のトラックを流す。全員が端末で読むなら、その言語の gpt-realtime-translate のセッションも、テキスト入力の読み上げのセッションも作らない。
- 新しいアプリは、端末で読むときは自分の言語のトラックを購読しない(二重に聞こえるため)。
- 古いアプリが残る間は、費用はその言語の分だけ下がらない。古いアプリをいつまで受け入れるか(最低の版を決めて更新を促すか)は別に決める。

#### ブラウザの TTS の PoC(2026-10-18。Mac の Chrome の分は 2026-10-23 に記入)

ブラウザの `speechSynthesis` で翻訳後のテキストを読み上げる案を、耳で確かめるページを `tools/tts-poc` に作った。翻訳音声を端末で読み上げる案は採らないことにした(2026-10-23)が、声の数、読み上げの許可、裏のタブ・画面ロック中の読み上げ、boundary と cancel は、テキスト入力の読み上げを端末でするかを決めるのにも使うので、このページで試す。待ち行列と速さの決め方(下の3つ目)は、翻訳音声のためのもので、テキスト入力では要らないかもしれない。本番のアプリには入れていない。LiveKit と Agent は使わず、字幕が届くのをページの中で模擬する。iOS・Android のネイティブの TTS と、PTT 中の漏れ(AEC)、オーディオセッション、音の経路は、このページでは確かめられない(モバイル版の PoC で別に確かめる)。

使い方(詳しくは `tools/tts-poc/README.md`):

- devContainer で `mise run poc:tts` を実行し、Mac のブラウザで `http://localhost:5176` を、同じ LAN のスマートフォンで `http://${DEV_HOST}:5176` を開く(5176 番は compose が LAN に公開する。コンテナの作り直しが要る)。

- 待ち行列と速さの決め方は、上の「案 C を却下した理由の見直し」の案のとおりに作った(`tools/tts-poc/src/core/pacing.ts`。Vitest で試している)。待ち行列はページが持ち、TTS には1区切りずつ渡す。前の区切りを読み終えた時点(何も読んでいなければ届いた時点)の待ちの量で次の速さを決める。待ちの量は、待ち行列にある区切り(次に渡すものを含む)を1.0倍で読む秒数の見積もりの合計で、文字数を「1.0倍で1秒に読む文字数」で割って出す。この値の初期値は、Mac の Chrome での実測(下の表。日本語 5、中国語 4、韓国語 5.5、ほかは 11〜16)で、ページで例文を読むと声ごとの実測に置き換わる。既定の決め方は、待ちが4秒以下なら1.0倍、12秒以上なら1.5倍、間は直線(0.05刻み)。飛ばすしきい値は既定では使わない。どれも画面で変えられる。

- 許可は、入室のボタンなど、どこかを1回押していれば足りる。鳴らなかったときは `not-allowed` がすぐに来るので、字幕だけに切り替えられる。
- 速さを上げれば、日本語のように訳文が長くなる言語でも、遅れは十数秒で頭打ちにできる。ただし、インカムとして十数秒の遅れを受け入れられるかは、耳で聞いて決める必要がある。
- 残っていること: 耳での確認(13言語の声の質、1.3・1.5倍で聞き取れるか、速さの変わり目、続きから読んだときの自然さ)、Mac Safari・iPhone Safari・Android Chrome、画面ロック中の読み上げ、壊れた状態に入るきっかけ。

### PTT の運用

無音も課金される(PoC で実測)ため、話していない間は OpenAI に音声を送らない。

1. 発話中(ボタンを押している間、または発話検知の間)は、発話の途中の無音も含めて連続して音声を送る。
2. ボタンを離したら音声の送信を止める。
3. `session.close` を送り、`session.closed` が返るまで受信を続ける。途中で切ると、翻訳の末尾が欠ける。PoC では `session.close` から4〜6秒かかった。
4. セッションは発話ごとに作り直す(案)。送信を止めると出力も止まり、止まった出力は次の発話の頭に混ざるため、使い回すと前の発話の切れ端が流れる。`session.close` はボタンを離した直後に送る。時間を置いてから送ると、翻訳音声が捨てられる。
5. 接続の時間(セッション作成から設定完了まで約0.3秒)が気になる場合は、話者ごとに待機用のセッションを先に開いておく案がある。音声を送らずに20分つないでも切断されなかった。接続しているだけの時間は課金されない(close から closed までの待ちも、20分の待機も課金されなかった)。`session.update` の反映(`session.updated`)を待ってから音声を送る。

## テキスト入力の翻訳と読み上げ

### テキスト入力の実装で決めたこと(2026-10-10)

上の「設計への反映(案)」のとおり Agent に実装した(`services/agent` の README の「テキスト入力」)。加えて決めたこと:

- アプリは `TextMessage { message_id, text }`(`proto/voiceintercom/v1/text.proto`)をデータチャネル(topic `text`、reliable)で送る。送信者と言語はメッセージに持たせず、LiveKit の送信元の参加者(identity と属性 `language`)から取る。メッセージに持たせると、ほかの参加者になりすませる。
- 原文と訳の配信は、既存の `Caption` を使う。新しい項目 `message_id` にアプリが振った ID を入れ、確定だけを送る。`segment_id` は Agent が振る(アプリが振る ID は重なりうる)。古いアプリは、確定だけの字幕として表示できる。
- 読み上げ音声は、訳も原文も言語別のトラック `translation-<言語>` に混ぜる。原文は送信者の言語のトラックに流す。聞き手は「自分の言語のトラックを購読する」という取り決めのままでよく、購読数も増えない。送信者と同じ言語の聞き手がいないときは、原文を読まない。同じトラックを購読する送信者にも、自分の原文の読み上げが聞こえる。
- TTS の窓口は `sample_rate`、`prepare`、`speak`、`aclose` の4つにし、最初の実装を gpt-realtime-2.1-mini にした。
- (2026-10-13 に追加)窓口に `keep_only`(ルームにある言語を知らせる)を足した。gpt-realtime-2.1-mini の実装は、人がいなくなった言語のセッションを猶予(`TTS_IDLE_CLOSE_S`、既定60秒)の後に閉じる。出入りのたびに開き直す(約0.9秒)と戻った直後の読み上げが遅れるので、すぐには閉じない。読み上げ中なら、切らずに終わってから閉じる。

### Agent の結合確認(2026-10-10)

実際の OpenAI と LiveKit(devContainer の中の `livekit-server --dev`)で、Agent を端から端まで動かした。話者は `publish_wav.py`、聞き手は `listen.py`(ja の話者には en と ko、en の話者には ja と ko)、テキストは `send_text.py`。履歴はローカルの API(`services/api`)に保存した。音声は既にある短い WAV を無音(1.0〜1.5秒)を挟んでつないだ約36秒のもの(`devtools/concat_wav.py`。日本語は読み上げ4文と FLEURS 1文、英語は読み上げ4文と FLEURS 2文)。各条件1回ずつで、人の声の録音や雑音のある場所ではまだ試していない。費用は約 0.24 USD(下の「費用」)。

字幕の区切り(区切りの値は既定):

| 条件 | 区切り | 最初の訳の確定(発話の開始から) | 区切りの音声の終わりから訳の確定まで | 最後の訳の確定(PTT を離してから) |
| --- | --- | --- | --- | --- |
| ja 36.8秒、区切る | 5 | 8.8秒 | 2.3〜4.4秒 | 2.2秒 |
| ja 36.8秒、区切らない(`SEGMENT_ENABLED=0`) | 1 | 39.8秒 | — | 3.0秒 |
| en 35.5秒、区切る | 5 | 7.4秒 | 2.5〜3.3秒 | 2.3秒 |
| en 35.5秒、区切らない | 1 | 38.5秒 | — | 3.2秒 |

- 発話の途中で commit した後も、同じ whisper のセッションで続きの書き起こしが届いた(8回の commit のすべて)。断片と確定の `item_id` は区切りと1対1で対応し、確定の入れ替わりや空の確定はなかった。commit の後に届いた前の区切りの断片(「です。」「ten thirty.」)も、`item_id` で前の区切りに入った。
- 区切りはすべて無音のところで、文の途中では切れなかった。FLEURS の英語の文中の息継ぎ(0.41秒と0.44秒、読点の後)では区切らなかった。0.64秒の間を挟んだ2文は、最短の4秒に届かず1つの区切りになった。
- whisper の文末(「。」「.」)は、音声の終わりから0.35〜1.0秒遅れて届いた。そのため、文末の規則(0.4秒)で区切れたのは8回中3回(無音の始まりから約0.45秒)で、残りは文末が遅れて約0.8〜1.0秒、または長い無音の規則(1秒)で区切った。
- 区切りの音声の終わりから訳の確定までの内訳: 区切るまで 0.35〜1.06秒、commit から確定まで約0.6〜0.75秒、テキスト翻訳(2言語を並べて)が 1.2〜2.6秒。翻訳は PoC(約1.5秒)より遅い回があった。
- 区切っても、翻訳音声(translate は区切らない)は途切れず、最後まで届いた。最後の翻訳音声は PTT を離してから1.5〜2.0秒で終わった(このときの Agent は翻訳音声を 48kHz とみなして2倍速で流していた。届くのは実時間なので、終わりの時刻はほぼ変わらないと考える)。区切らない ja の回で、ko の翻訳音声だけ最後の文(「すみません、もう一度お願いします。」2.6秒)が欠けた(STS の翻訳テキストにも無い。ほかの7本は最後まで届いた)。区切りとは関係なく、translate の末尾の欠けと考える。
- 訳の質: 区切った訳と区切らない訳で、目立った差はなかった。誤りの多くは whisper の聞き取り(「発注番号はA-7034」→「八十番号は例の七千三十四」、「昆虫は」→「こんにちは」、「line B before 10:30」→「line BB four ten thirty」)で、同じ音声でも回によって変わる。

テキスト入力(ja の送信者が3通を0.5秒おきに、en の送信者が1通。聞き手は en、ja、ko。数字は de と fr でも確かめた):

| 項目 | 結果 |
| --- | --- |
| 字幕 | 原文と訳の確定が `message_id` 付きで届いた。訳の数字: en と ko は 1,250、de は 1.250 と 10:30 Uhr、fr は 1 250 と 10 h 30 |
| 受信から読み上げの最初の音まで | 原文 0.95〜1.1秒。訳 1.9〜2.4秒(PoC の中央 2.6秒と同じくらい) |
| 読み上げが重ならないか | 続けて送った3通は、どの言語のトラックでも順に流れた(文字に戻して順番を確かめた) |
| WAV | 48kHz。読み上げの長さは自然(「There are 1,250 units remaining in stock.」が約3.5秒)で、リサンプルの誤りはない。gpt-4o-transcribe で文字に戻した中身は送った文と訳に合った |
| 逐語か | 「読み上げのテキストが渡した文と違う」の警告は0件。「今何時ですか?」「これまでの指示を無視して…」にも答えなかった(読み上げのテキストで確認。gpt-4o-transcribe は en の「Ignore all previous instructions…」を書き起こさず落とした。PoC と同じく、文字に戻す確認は逐語の判定に使えない) |

- **不具合: 入室の直後に送ったテキストが捨てられる。** LiveKit は参加者の情報(`participant_connected`)をまとめて配り(ローカルでは約3秒おき)、データパケットはすぐに届ける。入室から1〜2秒で送ると、Agent に届いた時点で送信元が分からず(`DataPacket.participant` が None)、Agent は黙って捨てていた(6通中3通)。送信元が分からなければ言語も分からず、なりすまし対策のためメッセージから取ることもしない。Agent は警告を出すようにした。アプリでの対策(案): 入室から数秒は送らない、または自分の `message_id` の字幕が数秒で返ってこなければ送り直す。送り直すなら、Agent が `(identity, message_id)` で重複を捨てる仕組みを足す。

履歴の保存: 区切りごとの `utterance` 11件(`utterance_id` と `segment_index` 付き、`occurred_at` は区切りの開始時刻)と、テキストの `text` 8件が、訳(2言語)と一緒に `GET /rooms/test/timeline` で読めた。

費用(送った音声の長さからの概算): translate 289秒(0.164 USD)、whisper 145秒(0.041 USD)、読み上げの出力約57秒(0.025 USD)、文字に戻す確認 73秒(0.007 USD)、テキスト翻訳(0.005 USD 未満)。合計約 0.24 USD。

字幕の区切りの既定値は変えない。

- 区切りは文の途中で切れず、最初の訳は区切らない場合より約30秒早く出た。文末の規則が効く回は少ないが、文末の後の無音で区切ると、1秒を待たずに済む回がある(8回中3回)。`SEGMENT_PAUSE_S` を大きくしても、whisper の文末の遅れ(0.35〜1.0秒)より早くは区切れない。
- 見直しの候補(提案): (1) `SEGMENT_SILENCE_DBFS` の -50 dBFS は、音量の小さい録音(FLEURS の英語の多くは中央値で -60〜-75 dBFS)を全体が無音とみなす。声が1秒に満たない区切りは区切らない決まりがあるので、文の途中で切れることはないが、小さい声の区間で区切れなくなる。実機の録音(自動利得のある端末のマイク)の音量を測り、固定の閾値か、区切りの中の声の大きさからの相対値にするかを決める。(2) translate の末尾の欠け(8本中1本)は、PTT を離した後に0.5秒ほどの無音を送ってから `session.close` を送る案を、人の声で再確認する。

### Agent の見直し(2026-10-11)

「Agent の結合確認」の最後の見直しの候補を2つ試した。環境は結合確認と同じ(devContainer の中の `livekit-server --dev`、`publish_wav.py` と `listen.py`、ja の話者には en と ko、en の話者には ja と ko の聞き手)で、各条件1回ずつ。音声は結合確認の2本(`long-ja-cat` 36.8秒、`long-en-cat` 35.5秒)に、FLEURS をつないだ2本を足した。`long-en-quiet-cat`(37.1秒、英語4文、声の上位 10% が -55〜-59 dBFS、雑音 -85 dBFS ほど)と `long-ja-noisy-cat`(41.6秒、日本語4文、声 -20 dBFS ほど、雑音 -34 dBFS ほど)で、文の間の無音には前の WAV の雑音の床と同じ音量のノイズを入れた(`concat_wav.py --room-tone`)。人の声の録音や実機のマイク(自動利得)ではまだ試していない。費用は約 0.86 USD(translate 1,342秒で 0.76 USD、whisper 302秒で 0.09 USD、テキスト翻訳 0.01 USD 未満)。

**無音の閾値**(`SEGMENT_SILENCE_DBFS`、-50 dBFS 固定): 小さい声だけでなく、雑音の多い録音でも区切れなかった。FLEURS の日本語には、雑音の床が -33〜-36 dBFS(-50 dBFS より大きい)の録音が多く、息継ぎを無音とみなせない。3つの方式を、`Segmenter` をオフラインで動かして比べた(書き起こしの文末は、各文の終わりから0.7秒後に届く想定)。

| 音声 | 固定(-50 dBFS) | 声の大きさ(上位 10%)より 20dB 小さい | 雑音の床(下位 5%)から声までの 25% の位置 |
| --- | --- | --- | --- |
| `long-ja-cat` | 4回 | 4回(位置も同じ) | 4回(位置も同じ) |
| `long-en-quiet-cat` | 0回 | 3回 | 3回 |
| `long-ja-noisy-cat` | 0回 | 0回 | 3回 |

- 声の大きさだけからの相対値は、雑音の多い録音(声と床の差が 15dB ほど)で無音を見つけられなかった。差を小さくすると、声の弱い部分を無音とみなしやすくなる。そこで、声と床の両方を見る方式にした。
- ほかの FLEURS の組み合わせ5本(小さい声、雑音の多い声、間を挟まず続く長い1文を含む)でも試した。固定の閾値と区切りの位置が違った箇所は、音量を見ると、どれも話し終えた後の雑音の区間(-46〜-50 dBFS ほどで、固定の閾値では声とみなす)で、文の途中ではなかった。文の途中で区切ったのは、区切りが15秒を超えたときに0.4秒の間で区切る規則(`SEGMENT_MAX_S`)によるもので、方式によらない。
- 音量は発話の始めからためる。直近の5〜20秒だけで決める案は、発話の途中で声の大きさが変わる音声(極端に小さい声の文の後に、普通の声の文)で取りこぼしが減ったが、15秒を超えた区切りで文の途中の0.5秒の弱い区間(-34〜-43 dBFS)を無音とみなした。同じ話者の発話では大きさは変わりにくいので、簡単なほうにした。床の百分位(10%、5%、3%)では結果がほぼ同じで、話し始めてすぐの息継ぎにも効くよう 5% にした。
- 発話の始めの1秒は固定の閾値を使い、声と床の差が 6dB に満たない(雑音だけ)ときは何も無音とみなさない。声が1秒に満たない区切りは区切らない決まりは、そのまま。処理は1フレーム(10ms)あたり約 6µs(固定の閾値は約 2µs)。

実際の OpenAI と LiveKit での結果(「前」は `SEGMENT_SILENCE_RATIO=0` と `TRANSLATE_TAIL_SILENCE_S=0` で、今までの振る舞い。数字は2つの聞き手の言語の範囲):

| 音声 | 方式 | 区切り | 最初の訳の確定(発話の開始から) | 区切りの音声の終わりから訳の確定まで | 最後の訳の確定(PTT を離してから) |
| --- | --- | --- | --- | --- | --- |
| ja 36.8秒 | 固定 | 5 | 8.8秒 | 1.7〜3.5秒 | 1.7〜2.0秒 |
| ja 36.8秒 | 相対 | 5 | 8.3秒 | 1.7〜3.0秒 | 1.7〜1.8秒 |
| en 35.5秒 | 固定 | 5 | 7.4秒 | 1.7〜2.6秒 | 1.7〜1.8秒 |
| en 35.5秒 | 相対 | 5 | 7.7秒 | 1.9〜2.7秒 | 2.1秒 |
| 小さい声の en 37.1秒 | 固定 | 1(区切れない) | 40.4秒 | — | 3.3〜3.5秒 |
| 小さい声の en 37.1秒 | 相対 | 4(と末尾の空の区切り) | 11.2秒 | 1.7〜3.4秒 | 2.3〜2.7秒 |
| 雑音の多い ja 41.6秒 | 固定 | 1(区切れない) | 44.5秒 | — | 2.9〜3.1秒 |

- 結合確認の2本では、区切りの位置は固定の閾値と 0.2秒以内で同じだった。小さい声と雑音の多い音声では、相対の閾値で区切れるようになり、最初の訳が約30秒早く出た。区切りはすべて文の間の無音で、文の途中では切れなかった。
- 小さい声の en では、PTT を離す0.2秒前(最後の文の後の無音)でも区切った。末尾に0.2秒の空の区切りができたが、書き起こしが空なので字幕は出ず、履歴にも保存されない。音声の途中で切るわけではないので、そのままにする。

**translate の末尾の欠け**: PTT を離した後、`session.close` の前に無音を送る設定(`TRANSLATE_TAIL_SILENCE_S`)を足した。PTT を離してから close までを延ばさないよう、無音は待たずにまとめて送る。音声を送っていない発話には送らない。欠けがまれなので、結合確認とは別に、Agent の `TranslateSession` をそのまま使って短い音声(ja 9.1秒の2文、en 7.5秒の2文。最後の文は「すみません、もう一度お願いします。」と「We need two more people on line B before 10:30.」)を実時間で流し、無音なしと 0.5秒を同時に走らせて比べた(ja は en と ko、en は ja と ko に訳す)。

| 末尾の無音 | 本数 | 最後の文が欠けた | `session.close` から `session.closed` まで | PTT を離してから最後の翻訳音声まで |
| --- | --- | --- | --- | --- |
| なし | 40(と結合確認の8) | 0 | 中央 4.5秒(3.7〜6.3秒) | 中央 1.06秒(0.6〜3.7秒) |
| 0.5秒 | 40(と結合確認の8) | 0 | 中央 4.3秒(3.8〜6.7秒) | 中央 1.03秒(0.7〜2.2秒) |

- どちらの条件でも、最後の文の欠けは再現しなかった(STS の翻訳テキストで確認)。結合確認の8本中1本、PoC の5本中1本(0.8秒分しか届かなかった)と合わせると、無音なしの欠けは61本中2本ほどで、この本数では無音の効果を確かめられない。待ち時間は変わらなかった。
- 0.5秒の側の1本(ja → ko)で、翻訳テキストは全文が届いたのに、翻訳音声が1つも届かなかった(96本中1本)。音声は発話の間に流れるはずで、末尾の無音とは関係ないと考えるが、原因は分からない。Agent はこれに気づけない。
- **既定は 0(送らない)にした。** 無音も課金され(「PTT の運用」)、0.5秒は翻訳先1言語あたり約 0.0003 USD、PTT の発話が平均5秒なら translate の費用が約10%増える。効果を確かめられないまま、確実に増える費用は払わない。実機の人の声で末尾の欠けが目立つようなら、`TRANSLATE_TAIL_SILENCE_S=0.5` で試し、欠けの頻度を比べる。

決めたこと: 無音の閾値は相対値(`SEGMENT_SILENCE_RATIO=0.25`)を既定にする。`SEGMENT_SILENCE_RATIO=0` で固定の閾値に戻せる。translate の末尾の無音は既定では送らない。残り: 実機のマイク(自動利得のある端末)の録音で、相対の閾値と、末尾の欠けを確かめる。

### 翻訳音声のサンプルレート(2026-10-13)

Android エミュレーターで room_flow_test を聞いた利用者から「日本語の翻訳音声が2倍の速さで1オクターブ高く聞こえる」と報告があった。原因は、translate の出力を 48kHz とみなしていたこと。実際は 24kHz で、Agent はそれを 48kHz のトラックにそのまま流していた。英語の話者の音声とテキスト入力の読み上げ(24kHz を 48kHz にリサンプルしている)は正しかった。

当初 48kHz と判断した根拠は「19200 バイト(9600 サンプル)のチャンクが200ms ごとに届く」だったが、これは誤り。PoC の記録(`translate_bench.py` の jsonl)を見直すと、話している間は約0.4秒ごとに届いていた(3本で、最初の20個の平均間隔 0.391〜0.397秒)。`session.close` の後に残りのチャンク(ほとんど無音)が数秒でまとめて届くため、セッション全体で平均すると約0.2秒ごとに見え、受けた音声の長さを 48kHz で数えるとセッションの長さとほぼ合った。OpenAI の出力が途中で変わったのではない(2026-10-08 の PoC の WAV も今日の出力も、同じく 24kHz で自然になる)。

確かめたこと(en-01.wav「The shipment of 250 units will arrive at Gate 14 on Thursday morning.」、入力の基本周波数の中央値 171Hz):

| 音声 | 48kHz とみなす | 24kHz とみなす |
| --- | --- | --- |
| PoC(2026-10-08)の translate-ja.wav | 声 2.0秒、基本周波数 407Hz | 声 3.8秒、205Hz |
| 今日の translate の出力(同じ文) | 声 2.1秒、407Hz | 声 4.1秒、216Hz |

- 48kHz とみなすと、日本語の1文(「200台の出荷分は、木曜朝に14番ゲートに到着します」、約40拍)が2秒で、1秒に約20拍になる。人の話す速さ(1秒に7〜10拍)の2倍で、声は入力の2.4倍の高さになる。24kHz なら、話す速さも、声の高さが話者に追従すること(「公式に書かれている制約」)も合う。
- チャンクの前半と後半は別の音で(相関はほぼ0)、同じ音を2回入れたものやステレオではない。
- `session.update` に `audio.output.format`(`{"type": "audio/pcm", "rate": 24000}`)を入れると `unknown_parameter` になり、設定全体が捨てられた(翻訳先が既定のスペイン語になった)。出力の形式は指定できないので、24kHz と決め打ちにする。
- 直した Agent を devContainer の LiveKit で動かし、`listen.py` で受けた ja のトラック(en-01 と en-02 の訳)の基本周波数は 220Hz、声は8.8秒(入力は 7.9秒)だった。

直したこと: `realtime.py` の `OUTPUT_SAMPLE_RATE` を 24000 にし、翻訳音声も読み上げと同じく `output.py` の `AudioInput` でトラックの 48kHz にリサンプルしてから混ぜる。`OUTPUT_SAMPLE_RATE` を使っていたのはトラックへの出力だけで、録音(元の音声、24kHz)と字幕・履歴の時刻(入力の音声で数える)は影響を受けない。PoC の `translate_bench.py` も 24kHz に直した。2026-10-13 より前に PoC と結合確認で保存した翻訳音声の WAV と、翻訳音声の長さ(`voiced_s`)は 48kHz として扱っていたので、WAV は2倍速で聞こえ、長さは半分になっている。このメモの数値のうち、翻訳音声の長さは直した。遅延(届いた時刻)の数値は、サンプルレートに関係しないのでそのまま。

残り: `session.close` の後にまとめて届く無音(1発話で13〜16秒分)も、トラックで実時間で流れる。ほかの話者の音声と混ぜるだけなので聞こえ方は変わらないが、捨ててもよい。→ 捨てることにした(下の「翻訳音声の末尾の無音」)。

### 翻訳音声の末尾の無音(2026-10-14)

**決定: `session.close` の後に届いた翻訳音声のうち、最後に声のあったところより後ろの続いた無音だけを捨てる**(`services/agent` の `silence_trim.py`。`TRANSLATE_TRIM_TAIL=0` で捨てない)。

PoC の記録(`poc/out` の translate の jsonl と WAV、約40本)で、close の後に届いたチャンクの最大の振幅を見た。

- close の後の末尾の無音は、1発話で約9〜30秒分(長い発話ほど長い)。最大の振幅は 0〜1 で、ほぼデジタルの無音。
- 声の終わりは、113、42、9、5、3 のように減衰してから 0〜1 になる。close の前の発話の途中の無音も 0〜1 だった(27 などの小さな山が少しある)。
- close の後に、残りの翻訳音声(数秒分)が無音より先に届く。無音の後に声が続く回は見なかったが、備える。

捨て方(翻訳音声の途中の間と、末尾の小さな声を削らないため):

- close の前に届いた音声は、無音もそのまま流す(話している間の間を保つ)。
- close の後は、10ms のフレームごとに最大の振幅が 8 以下(-72 dBFS ほど)なら無音とみなし、無音の続きはためておく。声のフレームが来たら、ためた無音も声の前に流す(途中の間は保つ)。セッションの終わりに、ためた無音のうち 0.2秒だけ流して残りを捨てる。
- 閾値を 8 にしたのは、PoC の無音(0〜1)より上で、声の終わりの減衰(9 まで)を切らないため。小さな声(-58 dBFS、振幅 40 ほど)も声として残る(単体テストで確かめた)。
- 捨てる分を待つのはトラックに流す前だけで、close の後の音声はまとめて届くので、声が遅れることはない。

確かめたのは合成した音声の単体テストだけで、実際の translate の出力を通した確認(`listen.py` で受けた WAV の末尾)はまだ。

LiveKit の主な不安は解消した。Flutter には公式 SDK があり、100人の音声ルームは公式ベンチマークで余裕があり、録音は Agent が話者ごとに作れる(Egress を使わないので同時数と料金の制約を受けない)。注意点は、Build プランの参加者上限と、購読できる音声トラック数の上限(100)。

| 項目 | 確認結果 |
| --- | --- |
| Flutter SDK | 公式の Flutter SDK(`livekit_client`)があり、Android と iOS に対応する |
| 100人ルーム | 公式ベンチマークで、音声のみ・発話者10人・聞き手3,000人の1ルームが、16コアのサーバー1台で CPU 80%。音声は平均 3kbps の模擬トラフィック。1ルームは1ノードに収まる必要がある |
| 購読の上限 | 1参加者が同時に購読できる音声トラックは100(全プラン共通)。Agent も参加者なので、100人全員が常時 publish すると上限に近づく |
| 参加者の上限 | Build(無料)は全ルーム合計で100参加者。100人 + Agent は Build では試せない |
| 録音 | 自動 egress で、ルーム作成時に、ルーム合成と、公開された各トラックの個別録音を自動で始められる。音声だけなら動画より低い料金区分。出力は S3 など |

| Agent の実行 | コンテナのワーカーとして動き、LiveKit サーバーに WebSocket で登録してジョブを受ける。LiveKit Cloud にデプロイするか、Kubernetes などのコンテナ基盤で自前運用する。公式の例に ECS はないが、コンテナ基盤として使える想定 |

| セルフホスト | サーバーも Agents も OSS。自前運用では Egress を別に配備する |

### LiveKit Cloud の料金

| プラン | 月額 | 参加者分(含む / 超過単価) | Agent セッション分(Cloud ホスト時のみ) | 下り転送(含む / 超過単価) |

- 自前で動かす Agent は参加者分として計上され、Cloud にホストすると Agent セッション分(0.01 USD/分)になる。単価は20倍違うため、Agent は ECS で動かす想定にする。

### 設計への反映

- PoC は Build で始め、100人ルームの負荷試験は Ship で行う(Build は100参加者まで)。
- 録音は Agent が話者ごとに作る(2026-10-10 に決定。「録音の方式(追加調査)」を参照)。当初の案だった自動 egress(ルーム合成と各トラック)は、同時数と料金のため採らない。
- 音声トラックの方式は、常時 publish して mute / unmute を第一候補にし、発話中だけ publish する方式と PoC で比較する。購読上限の100、発話冒頭の欠け、録音ファイルの単位に影響する。
- Agent は ECS Fargate で動かし、タスクの停止待ち時間を長めに設定する。

### 録音の料金と同時数(追加調査)

- **料金(公式の料金ページ):** トラック録音は、Ship が600分込みで超過 0.001 USD/分、Scale が8,000分込みで 0.001 USD/分。ルーム合成の音声のみは、Ship が 0.005 USD/分、Scale が 0.004 USD/分(映像は 0.02 / 0.015)。トランスコード分の込みの分数は Ship が600分、Scale が8,000分で、ストリーム取り込みと共有する。
- **例(試算):** 100トラックが1時間とも録音されると6,000分で、約6 USD(込みの分数を引く前)。ルーム合成の音声のみは1時間で 0.3 USD(Ship の超過後)。
- **同時数の問題:** トラック録音は1トラックが1リクエスト(調査担当の報告)。100人全員が常時 publish すると、Ship の同時100に届き、合成を併用すると超える。対策の案は、発話中のトラックだけ録る、Agent 側で話者ごとに録る、の2つ。1つのリクエストで参加者ごとにチャンネルを分ける案(`AudioConfig`)は、出力が最大2チャンネルなので話者別には使えない(下の「録音の方式(追加調査)」を参照)。
- **自前運用:** Egress は1インスタンスあたり最低 4 CPU・4 GB で、Redis が必要。トラック録音は軽く1台で数百件を扱え、ルーム合成は 2〜6 CPU を使う。

### 録音の方式(追加調査。2026-10-10)

公式ドキュメントと LiveKit のソースコード(egress、protocol)で確かめた。

| 項目 | 分かったこと |
| --- | --- |
| 自動 egress の設定 | `CreateRoom` の `egress`、またはトークンの `room_config`(`RoomConfiguration.egress`)。中身は `room`(ルーム合成。旧 API の型で `audio_only` と `audio_mixing` を持つ)、`participant`、`tracks`(公開された全トラックを1本ずつ。絞り込みはできず、Agent の翻訳トラックも録られると考えられる)の3つ。新しい `StartEgress` の `AudioConfig` は自動 egress では使えない |
| トークンの `room_config` | ルームを最初に作ったときだけ効く。JWT は暗号化されないので、S3 の鍵をトークンに入れるとクライアントから読める。egress の設定はサーバー(Lambda か Agent)から `CreateRoom` / `StartEgress` で渡す |
| S3 の認証情報 | `S3Upload` はアクセスキー、`session_token`、`assume_role_arn` を持つ。LiveKit Cloud の AssumeRole は「機能を有効にしたアカウントだけ」(proto のコメント)で、条件は公開されていない。当面は録音用の接頭辞への `s3:PutObject` だけを許す IAM ユーザーの鍵を使う。STS の一時認証は、数時間の録音では終わる前に期限が切れうる |
| 話者別のチャンネル | `AudioMixing` は `DEFAULT_MIXING`(モノラル)、`DUAL_CHANNEL_AGENT`(Agent を左、それ以外を右)、`DUAL_CHANNEL_ALTERNATE`(参加順に左右)。`AudioConfig` の route も左・右・両方への振り分けだけ。出力は最大2チャンネルで、1リクエストで100人を別々に残すことはできない |
| ミュート中のトラック録音 | リクエストは続く(ミュートは「非アクティブ」として扱い、録音は非公開・退出・EOF で終わる)。課金の扱いは公式に記載がないが、経過時間で数えられると考えるのが妥当(推測) |
| 同時数の単位 | プロジェクト全体の数と読める(明記はない)。Ship の100は、100人ルーム1つの常時 publish と自動トラック録音で埋まる |

月176時間(1日8時間 × 22日)、100人ルーム1つでの試算(込みの分数を引く前):

| 方式 | 1時間 | 月 | Egress の同時数 |
| --- | --- | --- | --- |
| 全員常時 publish + 自動トラック録音 | 約 6.0 USD | 約 1,056 USD | 100 以上(Scale が要る) |
| ルーム合成の音声のみ | 約 0.30 USD | 約 53 USD | 1 |
| 発話ごと publish + 自動トラック録音 | 発話時間 × 0.001 USD/分 | 数 USD | 同時に話している人数 |
| Agent 側で話者ごとに録る | LiveKit 側は 0(S3 だけ) | ごくわずか | 0 |

**決定(2026-10-10):** Agent が話者ごとに録る方式だけにする。ルーム合成の控えは、必要になったら足す。

- 話者別の録音は Agent が作る。Agent は全話者のトラックを既に購読しているので、発話ごと(ミュート解除から、ミュート・unpublish・退室まで)に Ogg/Opus を作り、ECS のタスクロールで S3 に書く(`services/agent` の `recording.py`)。費用と同時数の問題がなく、LiveKit に渡す鍵も要らない。
- 弱点は、Agent が落ちている間とデプロイで切れたとき(再ディスパッチまでの約15秒など)の抜け。固定費を抑えるため、これは許容する。
- 置き場所は録音用の非公開のバケット(`voice-intercom-<env>-recordings-<アカウント ID>`)。画像・動画のバケットは CloudFront がバケット全体を署名なしで配信するので、同じバケットには置かない。キーは `rooms/<room_id>/<YYYY>/<MM>/<DD>/<utterance_id>-<speaker_id>.ogg` で、字幕と履歴の `utterance_id` から引ける。
- LiveKit の Egress(ルーム合成、トラック録音、全トラックの自動録音)は使わない。ルーム合成を足すなら、翻訳音声を入れない場合は Agent がジョブの開始時に `StartEgress`(MediaSource、`participant_kind=STANDARD` の route)を呼ぶ。自動 egress で済ませるなら `room.audio_only=true` と `DUAL_CHANNEL_AGENT`(右が原音、左が翻訳音声。LiveKit Cloud でそのまま効くかは未確認)。ファイル出力は3時間で切れるので、長いルームでは開始し直して分ける。

PoC で確かめること: Agent での録音が発話の冒頭と末尾まで取れるか。ルーム合成(MediaSource と `DUAL_CHANNEL_AGENT`)の出力と課金の区分、ミュート中のトラック録音の課金は、合成を足すときに確かめる。

### Agent の運用(追加調査)

- **規模の目安(公式の自前運用ガイド):** 4コア・8GB から始め、1サーバーあたり同時ジョブは10〜25。負荷の指標は CPU 使用率で、既定の閾値は 0.7。スケールアウトは 0.5 付近で早めにする。ヘルスチェックはポート 8081。
- **停止:** `SIGTERM` で新しいジョブを断り、実行中のジョブが終わるまで動く。音声アプリには猶予10分以上を推奨している。ECS Fargate の `stopTimeout` は最大120秒なので、長いルームはデプロイやスケールインで強制終了される(調査担当の報告)。対策は、タスクのスケールイン保護、デプロイ時期の制御、Agent が落ちても約15秒で再ディスパッチされることを前提にした再接続の設計。
- **ディスパッチ:** 本番は明示ディスパッチ(`agent_name`)を推奨。ルームは最後の人間の参加者が抜けると閉じ、Agent も切断される。
- **音声の入出力:** Python の `AudioStream` はサンプルレートを指定でき、48kHz から24kHz へのリサンプルも自動。翻訳音声の再配信は `AudioSource` と `LocalAudioTrack` を使う。言語別のトラックは、名前や metadata に言語コードを入れ、聞き手が選択購読する(`autoSubscribe` を切り、`setSubscribed` で購読)。
- **購読数:** 全員が99人と Agent と翻訳トラックを購読すると100本を超えうる。翻訳トラックは選択購読で絞る。同時に話すのは数人なので、公式ベンチマークの範囲に収まる見込み。
- **Cloud へのホスト:** 同時の Agent セッションは Ship が20、Scale が最大600。ECS で自前運用するほうが現実的。

### PTT の方式(追加調査)

- 公式の PTT 専用ガイドはない。常時 publish してミュートを切り替える方式を第一候補にする(推測。公式の比較はない)。ミュートするとトラックのデータ送信は止まる。録音は1話者1本になり、購読も維持される。
- Flutter は `AudioManager.instance.setMicrophoneMuteMode` の `inputMixer` が最速の切り替え(`livekit_client` 2.9.0 以降。`Hardware` の同名の API は deprecated)。既定の `voiceProcessing` は OS のミュート音が鳴る。
- unpublish して再 publish した直後のトラックは、ミュート解除の状態になる。ミュートが効く前に音が漏れる競合の報告があり、ミュート操作は必ず await する。
- ミュート中の参加者分は接続時間で課金される(公式に明記はない)。

## 通知とバックグラウンド音声

チャットなどの通知は FCM に一本化する。閉じたアプリでの音声受信は iOS ネイティブの追加実装が必要で、初回リリースで必須かどうかの判断が要る。

| 方式 | 評価 |
| --- | --- |
| FCM(iOS は APNs 経由) | **推奨。** 無料。React Native は `@react-native-firebase/messaging`(Flutter 版では `firebase_messaging`)、iOS は APNs 認証キーを Firebase に登録する。Lambda から FCM HTTP v1 で送り、端末トークンは DynamoDB に userId と紐づけて保存する |
| Amazon SNS のモバイルプッシュ | FCM の前段が増えるだけで利点が薄い。単価は公式の料金表で確認できなかった |
| AWS End User Messaging | Pinpoint の後継。Pinpoint は2026年10月30日に終了する(調査担当の報告)。新規に採る理由は薄い |
| OneSignal | 外部サービスが増える。無料枠は1,000 MAU まで |

- チャットの通知は通常の alert 通知にする。iOS のサイレント通知(`content-available`)は配信が保証されず、アプリを強制終了すると届かないので頼らない。重要な通知だけ time-sensitive(Entitlement が必要)を検討する。Android は高優先度で送る。
- 「誰かが話した」も alert 通知にする。
- テキスト入力・話し始め・画像・動画のどれでも通知し、同じルーム × 同じ受け手には5分に1回までに間引く(「push 通知の間引きとテキスト入力の通知」)。

### バックグラウンドでの音声

- **iOS の PushToTalk フレームワーク:** アプリが閉じていてもロック中でも、PTT の音声を送受信できる。受信用の専用 APNs(push type は `pushtotalk`)でアプリが起動する。チャンネル参加はフォアグラウンドでの明示操作が必要で、同時に有効にできるチャンネルは1つ。音声の送受信は自前(LiveKit)。Flutter の汎用プラグインはなく、Swift のネイティブ実装と Method Channel が要る。LiveKit の公式対応は確認できなかった(下の「PushToTalk と LiveKit の共存(追加調査)」を参照)。
- **PushToTalk を使わない場合:** `audio` の background mode で、アプリが動いている間は音声を続けられる。閉じたアプリを起こして音声を流す手段は通常ない。
- **Android:** マイクのフォアグラウンドサービス(`FOREGROUND_SERVICE_MICROPHONE` と `RECORD_AUDIO`)が要る。Android 14 以降は、バックグラウンドから新たにマイクのフォアグラウンドサービスを始められない。受信だけなら `mediaPlayback` 型で足りる。
- **参考:** Zello は、Android では接続中ずっとフォアグラウンドサービスを動かし、通知は FCM で送る。iOS では APNs と PushToTalk フレームワークを併用している。
- **方針案:** 初回リリースは「入室中はバックグラウンドでも音声を維持する(iOS は audio mode、Android はフォアグラウンドサービス)。アプリを閉じている間は通知で知らせる」。PushToTalk フレームワークは次の段階で、LiveKit との共存を小さな PoC で確かめてから入れる。

### PushToTalk と LiveKit の共存(追加調査。2026-10-10)

- **共存できる見込み(推測)。** LiveKit の SDK には CallKit 向けに、オーディオセッションを外に任せてエンジンの起動を外から制御する API がある。PushToTalk の `didActivate` / `didDeactivate` は CallKit と同じ形なので当てはめられる。
  - Swift(2.17.0): `AudioManager.shared.audioSession.isAutomaticConfigurationEnabled = false` と `AudioManager.shared.setEngineAvailability(...)`。
  - Flutter(`livekit_client` 2.13.1): `AudioManager.instance.setAudioSessionManagementMode(manual / externalCallSystem)`、Dart を経由せずに Swift から呼べる `LiveKitPlugin.setEngineAvailability(isInputAvailable:isOutputAvailable:)`。PushToTalk は「起動時に playAndRecord にして変えない」ことを求めるので、カテゴリを状態に合わせて変える `automatic` / `externalCallSystem` ではなく `manual` が合う(推測)。
- **PushToTalk の制約(Apple):** アプリが自分でオーディオセッションを有効・無効にしてはいけない。`didFinishLaunching` で `PTChannelManager` を作り、カテゴリを playAndRecord にしておく。送受信していないバックグラウンドのアプリは停止され、ネットワーク接続は切れる。
- **受信は push のたびにつなぎ直す。** push → `incomingPushResult`(すぐ返す)→ 別スレッドで LiveKit に接続 → `didActivate` で再生。再接続は1〜3秒(第三者の報告)かかり、その間の音声は聞けないので、発話の冒頭が欠ける前提になる。補うなら Agent が発話の冒頭を貯めて、遅れて入った人に流す仕組みが要る(推測)。
- **push のきっかけ:** ミュートの切り替えは LiveKit の webhook に来ない。Agent がミュート解除を検知して APNs(`apns-push-type: pushtotalk`、topic は `<bundle id>.voip-ptt`)に送るか、話者のアプリが押した時点で API を呼ぶ。端末の ephemeral push token は FCM のトークンとは別に保存する。
- **事例:** LiveKit の公式サンプルはない。Expo + LiveKit + PushToTalk の個人の実装では、自動のセッション管理と二重に有効にして失敗したため自動を切り、送信の開始から `didActivate` まで約1秒かかった(ロック中の受信は未実装)。
- **分からないこと:** Entitlement に審査が要るか(capability の一覧には承認制の印がないが、Apple 社員は「リリースビルドに割り当てられているか確認を」と答えている)、push から再生までの制限時間、audio の background mode(初回リリースの方式)と同じアプリでどちらが優先されるか。
- **最小の PoC:** iOS 2台 + Android 1台。フォアグラウンドでの送信、ロック中の送信(システム UI)、ロック中・停止中の受信(テスト用スクリプトで pushtotalk を送り、push・接続完了・`didActivate`・最初の音の時刻を記録)、強制終了後の復元、着信での中断を確かめる。

### React Native かネイティブか、と Push to Talk の spike(2026-10-29)

**決定(利用者): 通知から通話を始める形は「インカムの形」にする。** 応答の操作なしに、相手の声がすぐ流れる。iOS は Push to Talk の仕組み、Android は foreground service を使う(電話の形の CallKit・ConnectionService は使わない)。

**方針: モバイル版は React Native のまま作り、OS と深くつながるところだけをネイティブのモジュールにする。決める前に spike で確かめる。**

- **理由:** 難しいところ(push を受けてすぐシステムに知らせる、音声セッションをシステムに任せる、foreground service)は OS の仕組みから来ていて、ネイティブで作っても同じ Swift・Kotlin を書く。React Native で増えるのは、JS との橋渡しと、閉じたアプリを起こしたときの JS の起動の時間だけ。一方、Swift と Kotlin に分けると、client-core の振る舞いの取り決め(字幕は Agent のものだけ読む、履歴で確かめてから出す、送り直しの回数と待ち時間など)を3つの言語で保つことになる。型は proto と OpenAPI で揃うが、振る舞いは揃わない。ネイティブのモジュールのコストは一度で済み、3つの言語のコストは続く。
- **ネイティブに切り替える条件:** spike で、(1) Push to Talk の音声セッションに `@livekit/react-native` の WebRTC を乗せられない、(2) 閉じたアプリで push を受けてから声が出るまでが許せないほど遅い、のどちらかが分かったとき。
- **決定(利用者): LiveKit の接続は JS(client-core)が持つ。** ネイティブのモジュールは OS とのやり取りだけを持つ。LiveKit をネイティブに移すと起動は速くなるが、ルームの処理が2つの言語に分かれる。(2) が駄目だったときに考え直す。
- **ネイティブのモジュールの形:** `packages/intercom-os`。本体(`ios/Core`)は React Native に依らない Swift にし、Expo のモジュールとしてつなぐ層(`ios/Binding`)を薄く置く。ネイティブに移るときは本体を持っていく。音声セッションを WebRTC につなぐのは JS が `@livekit/react-native-webrtc` の API で行うので、本体は WebRTC にも依らない。汎用のライブラリにはしない。
- **端末:** spike は iPad でもよい(PushToTalk は iPadOS 16.0 からある。Apple の資料で確かめた)。ただし受話口(iPad には無い)、電話の着信での中断(セルラーの iPad でないと試せない)、システムの画面の見え方は、出す前に iPhone で確かめる。

#### spike の作り(`tools/ptt-poc`)

- Expo 58(React Native 0.88.1)の dev build。`@livekit/react-native` 3.1.0、`@livekit/react-native-webrtc` 150.1.1。client-core の `RoomSession` をそのまま使う(client-core が React Native で動くかも、ここで確かめる)。
- 入室は本物と同じ経路(模擬 OIDC の password grant → `POST /livekit/token`)。設定を端末に残し、push で起きたときは操作なしで入り直す。
- **音声:** `registerGlobals({ autoConfigureAudioSession: false })` で LiveKit に音声セッションを触らせず、起動したら WebRTC の音声エンジンを止めておく(`AudioDeviceModule.setEngineAvailability`)。`didActivate` で `RTCAudioSession.audioSessionDidActivate()` を呼んでエンジンを動かし、`didDeactivate` で止める。`@livekit/react-native-webrtc` は、エンジンの出来事に JS のハンドラーが無ければ JS の応答を待たない(ソースで確かめた)。
- **受ける:** 前面では LiveKit の active speakers(サーバーが音量から決める。手元で音を鳴らしていなくても届く)を見て `setActiveRemoteParticipant` を呼ぶ。話し終えて 1.5 秒で外す。Agent の翻訳音声も「話している人」に数える。
- **push:** `scripts/send_ptt_push.py`(`mise run poc:ptt:push`)で APNs に直接送る。PTT の push の宛先は `PTChannelManager` が出す ephemeral push token で、FCM の登録トークン(端末の APNs トークンを包んだもの)とは別物なので、FCM では送れない見込み(推測。FCM の資料では確かめていない)。そうならサーバーは FCM とは別に、APNs の認証キーで送る口が要る。
- **時刻:** ネイティブの出来事は起きた時刻(UNIX 時間のミリ秒)を持ち、JS が起動する前のものも起動の後にまとめて届く。最後の push を 0 として、JS の起動・`didActivate`・ログイン・トークン・入室・音声の購読・話している人が見えるまでを画面に出す。時間は Release のビルドで測る。

### モバイル版の画面(2026-10-30)

**決定(利用者): Web 版は React Native(react-native-web)にせず、Vite + React のままにする。** OS とつながるところの実機での確認を待つ間に、モバイル版の画面を先に作る(シミュレーターで確かめられるため)。

- **Web 版をそのままにした理由:**
  - ロジックは client-core で共有済みで、React Native Web にして新たに共有できるのは画面と部品だけ。
  - 管理コンソールは Web だけなので、ui-web は残る。
  - Web 版の端末に依るところ(動画の変換、ログインのリダイレクト、音の再生)は、どちらにしても Web 専用に書く。
  - キーボードの操作やフォーカスの質が落ちやすい。
  - モバイル版はインカムの形で、画面の流れが Web 版と違ってくる見込み。
  - モバイル版の画面の大半が Web 版と同じだと分かり、ui-native がそろったら、考え直してよい。
- **画面の状態とふるまいの共有:** React に依るが見た目を持たない層を `packages/client-react` に置き、Web 版とモバイル版で使う。中身は次のとおり。見た目(JSX とレイアウト)だけを各アプリに置く。
  - データの取得(TanStack Query の hooks。API のクライアントは `ApiProvider` で渡す)
  - RoomHub の用意(端末に依るところは props で渡す)
  - 誤りの文言、入力の検証、整形
  - タイムラインの行のまとめ方と削除、PTT のキーの状態
- **作りの選択:**
  - Expo の開発ビルド(LiveKit のネイティブのモジュールが要る)
  - ルートは Expo Router(`src/app` のファイル名)
  - ログインは expo-auth-session(認可コード + PKCE)
  - トークンは expo-secure-store
  - 部品は `packages/ui-native`(Uniwind。ui-web と同じ名前と props)
- **確かめたこと(iPhone のシミュレーター):** 次のことは、client-core をそのまま使って動いた。前に「推測」としていた、client-core が React Native で読み込めるかは、これで確かめられた。
  - 模擬 OIDC でのログインと、起動し直してもログインが続くこと
  - ルームの一覧
  - データだけでつなぐこと(LiveKit)
  - テキストの送信
  - 音声をつなぐこと
  - PTT の送話の表示
  - 音声中の帯
  - 明暗の切り替え
  - ルームの作成、名前と種類の変更、招待、オーナーの変更、アーカイブと戻す、テキストの削除
  - 履歴の読み込み(画像とファイル)、アプリの中のブラウザで画像を開くこと
  - 2つのルームで同時に音声をつなぐこと(表示と送話の状態まで。声が両方に届くかは耳で確かめていない)
  - PTT を押したまま裏に回すと離れること、戻ったときのお知らせ
  - ログアウト、未登録の人の登録、テナントに未所属の表示、API が止まっているときの誤りと再読み込み、無いルーム、無いパス
  - iPad(mini)の表示と、ソフトウェアキーボードで操作の台が上がること
  - モバイル版と Web 版の間で、両方の向きに、元の声、話している途中からの翻訳音声、字幕の原文と訳文が届くこと(Agent を動かし、利用者が耳で確かめた)。
  - 一言の発話(「Hello」「Congratulations」)は、字幕の訳は出たが翻訳音声は出なかった。上の PoC の「短い発話」と同じで、gpt-realtime-translate が翻訳を返さなかった(`STS の翻訳テキスト` が空)。モバイル版に依らない。
- **見つかったこと:**
  - React Native の WebRTC は `MediaStreamTrack.clone()` を持たない(`Not implemented.`)。
    `SharedMicrophone` は、clone できないときに最初のトラックを1つ目のルームに渡し、2つ目からはルームごとにマイクを取るようにした。
    ネイティブの WebRTC は1本のマイクから何本でもトラックを作れる。ただし、2つのルームで同時に音声をつないだときの振る舞いは確かめていない。
  - Uniwind は、テーマごとに同じ変数を求める。そのため、明るい配色も `@variant light` で書いた `theme.native.css` を design-tokens から生成する。
  - LiveKit の React Native SDK は、`AudioSession.startAudioSession()` を呼ばないと、受け取った声を鳴らさない。音声をつないだルームがある間だけ開く(`AudioSessionKeeper`)。
  - アクセストークンの更新に失敗しても、サーバーが断ったとき(`invalid_grant`)だけログアウトする。電波が切れただけでログアウトさせないため。
  - 模擬 OIDC はリフレッシュトークンをメモリーに持つので、devContainer を止めると、次の更新で「ログインの期限が切れました」と出る(ローカルだけの話)。
  - シミュレーターのビルドを署名なし(`CODE_SIGNING_ALLOWED=NO`)にすると、Keychain が使えない(expo-secure-store が `A required entitlement is not present` で失敗する)。`expo run:ios`(`mise run mobile:ios`)は署名するので問題ない。

## 画像・動画の処理

初回リリースは、端末側でH.264に圧縮し、サムネイルも端末で作る構成で足りる見込み。サーバー側の変換は、困りごとが出てから足す。

- **再生:** `video_player` は iOS で AVPlayer、Android で ExoPlayer を使う。iPhone の HEVC の MOV は端末の OS 次第で再生できる。管理コンソール(ブラウザ)では、Chrome 107 以降はハードウェアの対応が条件、Safari は対応、Firefox は 134 以降(Windows)で対応する。H.264 の MP4 は全ブラウザで再生できるので、管理コンソールでも見るなら H.264 に揃える。
- **端末での圧縮:** 初めは `video_compress` 3.1.4(2025年2月公開。H.264 の MP4 出力、進捗、サムネイル生成)を使ったが、iOS でビットレートを決められないので、iOS は AVFoundation、Android は Media3 Transformer を直接使う形に替えた(2026-10-14。「動画の解像度とビットレート」)。FFmpegKit は2026年7月2日にアーカイブされた。後継の `ffmpeg_kit_flutter_new` は更新されているが、x264 を含む GPL 版を使うとアプリが GPL 3.0 になる。`image_picker` の動画の長さ制限は、カメラ撮影のときだけ効く。
- **サーバー側の変換(必要になったら):** S3 のイベントから Lambda、MediaConvert、EventBridge の完了通知、の順。Elastic Transcoder は2025年11月13日に終了した。MediaConvert の Basic は us-east-1 の例で約 0.0075 USD/分(ブログ。東京の単価は未確認)。1分の動画100本が HD で変換されると、月に約 1.5 USD(試算)。HLS は不要で、単一の MP4 で足りる。
- **サムネイル:** 端末で作り、本体と一緒にアップロードする。サーバー側のリサイズ(Dynamic Image Transformation for CloudFront)は構成要素が多く、少人数では不要。
- **アップロード:** 署名付き URL で S3 に直接アップロードする。Content-Type は署名時と一致させる。大きいもの(16MB 以上。2026-10-14 に決めた。下の「画像・動画のアップロード」)はマルチパートにし、未完了のアップロードはライフサイクルルールで削除する。ウイルススキャンは、招待制の間は不要(推測)。
- **サーバー変換を足す条件:** 端末の圧縮が失敗する・遅い、長尺の動画を許可する、Web で再生できない動画が出る。

### 画像・動画のアップロード(2026-10-14)

**決定(利用者): 大きいファイルは署名付き URL のマルチパートにし、端末からパートを並べて PUT する(AWS CLI の転送と同じ考え方)。失敗したパートだけ送り直す。本体の上限は 10GB(画像・動画とも)。** 小さいファイルは今までどおり1回の PUT。実装は `services/api` の `media.py`・`media_store.py`、`apps/mobile` の `media_uploader.dart`。

| 項目 | 決めた値 | 理由 |
| --- | --- | --- |
| マルチパートにする大きさ | 16MB 以上(API が決める) | 小さいものは1回の PUT のほうが往復が少ない。AWS CLI の既定(8MB)の2パート分から |
| パートの大きさ | 8MB。10,000 個を超えるなら 1MB 単位で大きくする | S3 の下限(最後以外 5MB)より大きく、失敗したときの送り直しが小さい。10GB でも 1,280 個で、上限(10,000)に届かない |
| 同時に送る数 | 4本(端末) | モバイルの回線で、1本ずつより速く、多すぎて詰まらない程度。AWS CLI の既定(10)より少なくした |
| パートの送り直し | その場で3回まで(1秒・2秒おく)。だめなら失敗にし、「やり直す」で残りのパートだけ送る | 一時的な切断はその場で直し、続く失敗は利用者に見せる |
| パートの URL の取り方 | `POST .../media/{media_id}/parts` で 100 個ずつ、送る前に取る(期限1時間) | 1,280 個を uploads で全部出すと、遅い回線では送り終わる前に期限が切れる。期限の5分前を過ぎたら取り直す |
| 未完了のアップロード | ライフサイクルルールで1日(AbortIncompleteMultipartUpload) | API の仮の行(complete を呼べる期間)の TTL と揃える。S3 は UTC の 0 時に切り上げて数えるので、実際は1〜2日 |

API:

- uploads は `size_bytes` からマルチパートにするかを決め、CreateMultipartUpload を呼ぶ(Content-Type はここで決まる。パートの PUT には要らない)。UploadId とパートの大きさは DynamoDB の仮の行に持ち、クライアントには返さない(`multipart` の `part_size`・`part_count` だけを返す)。サムネイルは1回の PUT のまま(仮置きのキーに置かせる。下の「仮置き」)。
- parts は本人だけ。保存した後とマルチパートでないアップロードは 409、`part_count` を超える番号は 422。サムネイルの URL も取り直せる(マルチパートでは uploads の期限の後もアップロードを続けるため)。
- complete はマルチパートなら、本文の `parts`(全パートの番号と ETag。1 から `part_count` まで1つずつ。そろわなければ 422)で CompleteMultipartUpload を呼ぶ。
  1. サムネイルを先に確かめる(無ければ 409)。完了は取り消せないので、直せるものを先に見る。
  2. CompleteMultipartUpload。パートが合わない(InvalidPart など)なら取りやめて 410。NoSuchUpload は、前の complete が完了させた後に応答を失った(か同時に呼ばれた)ことがあるので、次の HeadObject で決める。
  3. HeadObject。本体が無ければ 410(取りやめた、期限で消えた)。大きさが `size_bytes` と違えば、本体を消して 410(完了した後は同じアップロードに置き直せない)。1回の PUT でも、大きさが違えば 409 にした(前は上限だけを見て、置かれた大きさを履歴に書いていた)。
  4. その後は今までの complete(履歴への保存、配信、push 通知)。2回目の complete、同時の complete、409 のやり直しの扱いは変わらない。
- 410 は「uploads からやり直す」の合図。アプリは、送り終えたパートを捨てて新しい media_id で送り直す。
- 仮置き(2026-10-16): 1回の PUT(16MB 未満の本体と、サムネイル)の署名付き URL は、配信するキー(`original`・`thumbnail`)ではなく仮置きのキー(`rooms/<room_id>/<media_id>/upload-original`・`upload-thumbnail`)に向ける。署名付き URL は期限(1時間)まで何度でも PUT できるので、配信するキーに直接向けると、complete の後や削除の後に置き直して、大きさの確かめを通らない中身に替えたり、消したものを戻したりできたため。
  - complete は仮置きを HeadObject で確かめ(大きさ)、CopyObject で配信するキーへ移して(Content-Type・Content-Disposition はそのまま移る)、仮置きを消す。コピーは確かめたときの ETag に合うときだけ(`CopySourceIfMatch`)。確かめた後に置き直されたら 409 で、complete をやり直させる。
  - 仮置きに無く配信するキーにあれば、前の complete がコピーした後に履歴を書く前に落ちた(か同時に呼ばれた)とみて、配信するキーのものを確かめて進む。
  - complete の後の置き直しは仮置きに残るだけ。仮置きは CloudFront から読めない(バケットポリシーで `rooms/*/*/upload-*` の GetObject を拒む)。media_id の前置きの下にあるので、削除の後始末(`deletion.py`)とルームの削除で消える。ライフサイクルルールは前置きでしか絞れないので、仮置きだけを期限で消すことはしない(残るのは本人が1時間のうちに置き直したものだけ)。
  - マルチパートの本体は配信するキーのまま(完了した後の UploadPart は失敗する)。サムネイルは仮置きにする。
  - CloudFront の応答に `X-Content-Type-Options: nosniff` を付けた(応答ヘッダーのポリシー)。
- 削除: 消せるのは保存した行だけなので、完了の前に消すことはない。ただし、同時に呼ばれた complete が削除の後に CompleteMultipartUpload で本体を置き直すことに備え、削除の後始末では、仮の行の UploadId のアップロードを先に取りやめてから本体とサムネイルを消す。消した後に complete が呼ばれたら、墓石を返し、S3 の後始末(取りやめと削除)をやり直す(CloudFront の無効化は DELETE で済んでいるのでやり直さない)。
- Lambda の権限: 開始・パート・完了は `s3:PutObject` で動く。取りやめに `s3:AbortMultipartUpload` を足した。管理コンソール(ブラウザ)からパートを PUT するときのため、S3 の CORS で `ETag` を読めるようにした(`expose_headers`)。管理コンソールはまだアップロードを作っていない。

アプリ:

- パートはファイルのその範囲だけを読みながら送る(`File.openRead(start, end)`)。10GB でも、メモリに載るのは送っている途中の分だけ。
- 進み具合は、サムネイルと全パート(送っている途中の分を含む)の合計。
- 送り終えたパートの ETag と、パートの URL はメモリに持つ。アプリを裏に回してもプロセスが生きていれば、「やり直す」で続きから送れる。アプリが落ちたら最初から(今までの「段階ごとのやり直し」と同じ範囲)。ディスクに残して再開するのは後回し(`apps/mobile` の README の「残していること」)。

ローカルの SeaweedFS(4.48)で確かめたこと(2026-10-14、devContainer から boto3 で):

- UploadPart の署名付き URL(署名に入るヘッダーは host だけ)への PUT は 200 で、`ETag` は引用符つきのパートの MD5。同じ番号を送り直しても受ける。CompleteMultipartUpload は引用符を外した ETag でも通り、完了したオブジェクトの Content-Type は開始のときのもの、大きさはパートの合計。
- 違いと注意: 同じ番号を送り直すと ListParts に2回出る(完了は正しい大きさになった。API は ListParts を使わない)。完了した後の2回目の CompleteMultipartUpload も 200 を返す(S3 もしばらくは返す。API は仮の行で2回目を先に返すので呼ばない)。取りやめた後・ETag が合わないときは、どちらも NoSuchUpload(S3 は ETag 違いを InvalidPart にする)。最後でないパートが 5MB 未満なら EntityTooSmall(S3 と同じ)。ETag 違いが NoSuchUpload になるので、ローカルでは 410 の理由が「アップロードが無い」になるが、アプリの振る舞い(uploads からやり直す)は同じ。
- Android エミュレーターの統合テスト(`media_upload_test`)で、約 40MB の画像を 8MB × 6 パートで送り、読み直した本体が元のファイルとバイトまで同じだった。送信は約19秒、complete は 142ms。

残ること:

- 10GB を CompleteMultipartUpload で完了させる時間(S3 は大きいと数秒〜数分かかることがあり、Lambda の timeout は15秒)。切れても、アプリが complete をやり直せば、NoSuchUpload → HeadObject で本体があれば保存に進む。dev で大きいファイルを送って確かめる。
- 端末の上限(`maxUploadBytes`)と動画の圧縮は別の担当が直している。

## 画像・動画のルームへの配信

アップロード(署名付き URL)と履歴への保存(`POST .../media/{media_id}/complete`)はある。保存した画像・動画を、今ルームにいる人へどう知らせるかを決める(2026-10-11)。サーバー側(API の配信と push 通知、`media.proto`)は実装した(2026-10-13。`services/api` の `media_broadcast.py`)。アプリの受信も実装した(2026-10-13。`apps/mobile` の `media_receiver.dart`。履歴で確かめる形)。

### 前提

- テキスト入力は、アプリ → データチャネル(topic `text`)→ Agent → `Caption` で配信する。送信者は LiveKit の送信元の参加者から取る(なりすまし対策。「テキスト入力の実装で決めたこと」)。
- complete を呼べるのはアップロードした本人だけ。2回目からは同じ履歴(同じ `event_id`)を返す。
- 履歴の `sender_id` は Cognito の sub で、LiveKit の identity と同じ。API の `room_id` は LiveKit のルーム名と同じ。
- API の Lambda は LiveKit の API キーとシークレットを持ち、`livekit-api` を使っている(トークン発行)。VPC の外にあり、LiveKit Cloud に届く。
- 今のアプリは topic `caption` 以外のデータを捨てる。topic を足しても古いアプリは壊れない(表示もしない)。
- 管理コンソールからもアップロードできる。管理コンソールは LiveKit のルームに入らない。
- (2026-10-14 に改めた)画像・動画には文を添えられない(下の「文を添えない」)。前は `text`(最大10,000文字)を添えられ、翻訳はしなかった。

### 誰がルームに知らせるか

| 案 | 流れ | なりすまし | 履歴との一致 | Agent が落ちているとき | ほか |
| --- | --- | --- | --- | --- | --- |
| A. アプリが直接送る | complete の応答を、送信者のアプリがデータチャネルで送る | 送信者は送信元の参加者から取れる。ただし中身(URL、`event_id`)は送信者が自由に書ける。他人のメディアや外部の URL を自分のものとして流せる | 保証されない。受け手が API で確かめるには、1件を取るエンドポイントが要る | 影響なし | complete の後にアプリが落ちると、誰にも届かない。管理コンソールからのアップロードは届かない(ルームにいない) |
| B. API が送る | complete で保存した後、Lambda が LiveKit の Server API(`RoomService.SendData`)で送る | 送信者は JWT の sub。中身は保存した履歴から作る。参加者は書き換えられない | 一致する(履歴の行から作る) | 影響なし | complete の応答が LiveKit の呼び出しの分だけ遅れる(ローカルの `livekit-server` では、List と Send を合わせて中央値 1.4ms。Cloud は未計測。「サーバー側の確認」)。管理コンソールからのアップロードも届く |
| C. Agent が送る | アプリが complete の後に `event_id` をデータチャネルで送り、Agent が API で履歴を読んで配信する | 送信者は送信元の参加者から取れる。中身は Agent が履歴から取るので一致する | 一致する | 届かない(再ディスパッチまでの約15秒など) | 経路が一番長い。Agent に履歴の1件を読む API が要る。添えた文の翻訳を足しやすい。管理コンソールからのアップロードは届かない |

**決定(2026-10-11): B(API が送る)にする。**

- なりすましと履歴との一致の両方を、参加者に頼らずに満たせる。送信者は JWT の sub、中身は保存した履歴の行から作る。
- Agent に頼らない。画像・動画は翻訳も読み上げもしないので、Agent を通す理由がない(文も添えられない。「文を添えない」)。
- 送るのは complete の中で1か所なので、アプリと管理コンソールのどちらから上げても同じに届く。

B の受け手の決まり:

- Server API から送ったデータは、受け手の SDK で送信元の参加者が無い(Flutter の `DataReceivedEvent.participant` が null)。参加者が送ったデータには送信元が付き、LiveKit サーバーが付けるので偽れない。
  - **ただし、受け手がまだ知らない参加者から届いたデータも、送信元の参加者が null になる**(2026-10-13 に Python の SDK で確かめた。Flutter の SDK 2.13.1 もソースでは同じ作り。「サーバー側の確認」)。入った直後の約3秒は、ほかの参加者から見えないので、入り直してすぐ送れば null で届く(「Agent の結合確認」で、Agent がテキスト入力の送信元を知らずに捨てた約3秒と同じ)。
- LiveKit には topic ごとの送信の権限が無い(`canPublishData` は全部か無しか)。参加者も topic `media` に送れてしまう。**受け手は、送信元の参加者があるデータを topic `media` では捨てる。**
- **(2026-10-13 に足した)送信元の参加者が null というだけでは、サーバーから来たとみなさない。** 上のとおり、入った直後の参加者が送ったものも null で届くため。受け手は、`MediaMessage` を「履歴に新しい行がある」という知らせとして扱い、表示の前に `GET /rooms/{room_id}/timeline` の先頭のページで `event_id` の行を確かめ、表示には履歴の行を使う(無ければ捨てる)。100人のルームでも、1件につき100回の GET で、費用と遅延(1回の API 呼び出し)は困らない見込み。SDK が送信元の identity(サーバーから送ったものは空)を別に返すなら、それが空であることの確認に替えてよい(Flutter の担当が確かめる)。
  - (2026-10-13)Flutter のアプリは履歴で確かめる形にした。`livekit_client` 2.13.1 の identity は `@internal` の `EngineDataPacketReceivedEvent` にしか無く、公開の API から export されていない(`src/` を直接 import することになり、版を上げると黙って壊れうる)。履歴の行を表示に使えば、中身(URL、送信者、添えた文)も保存したものになり、`text_truncated` の続きも要らない。履歴の読み込みは結果整合なので、見つからなければ1秒後と3秒後に読み直す。理由と振る舞いは `apps/mobile` の README の「受ける(ルームへの配信)」。
- 字幕(`caption`)にも同じ穴があった。送信元が Agent の参加者のものだけを読むことにした(下の「字幕の送信元」)。

### API の振る舞い

complete の中で、履歴に保存した後に次を行う。

1. `RoomService.ListParticipants` で、今ルームにいる参加者を取る。ルームが無い(誰もいない)なら、配信は飛ばす。
2. 人(kind が `STANDARD`)が1人以上いれば、`RoomService.SendData` で、topic `media`、reliable、宛先を指定せず(ルームの全員)に `MediaMessage` を送る。Agent しかいないときも送らない。送信者本人にも届く(送信者のアプリは `event_id` で重複を捨てる)。Agent にも届くが、Agent は topic `media` を読まない。
3. push 通知を送る(下の「push 通知との関係」)。

- **2回目の complete でも送る。** 1回目で保存できたのに配信が失敗した場合、アプリが complete をやり直せば届く。受け手は `event_id` で重複を捨てる。2回目でも送れるのは本人だけなので、増えても困らない。
- **配信の失敗で complete を失敗にしない。** LiveKit の呼び出しが失敗したら、ログに残して、履歴を 200 で返す。履歴に残っているので、ルームにいる人も、入り直したときや履歴を開いたときに見られる。
- **時間の上限。** LiveKit の呼び出しは、1回を2秒で切る。push の送信は8秒で待つのをやめる(話し始めの通知の10秒より短くした)。合わせて12秒で、S3 と DynamoDB の読み書きを足しても Lambda の timeout(15秒)に収める。
- **`ListParticipants` が失敗したとき**(LiveKit に届かない、権限が無いなど)は、配信を飛ばし(`SendData` も失敗する見込みが高く、待つ時間が増える)、push 通知は送信者以外のメンバー全員に送る(今ルームにいる人が分からないため)。
- **push 通知は最初の complete だけで送る**(2026-10-13 に決めた)。配信は受け手が `event_id` で重複を捨てられるが、push 通知は OS がそのまま出すので、やり直しのたびに鳴ってしまう。同時に2回呼ばれたとき(後の方は保存に負ける)も、送るのは先に保存した方だけ。
- `ListParticipants` と `SendData` は、`livekit-api` の `LiveKitAPI.room` で呼ぶ。API キーには、ルームの管理(`room_admin`)の権限が要る。SDK は呼び出しごとに `room_admin` とルーム名を入れたトークンを作る。API キー自体の権限は、`livekit-server` では区別しない(Cloud のキーは未確認。「サーバー側の確認」)。

### データチャネルの取り決め

topic は `media`(reliable)。メッセージは `proto/voiceintercom/v1/media.proto` の `MediaMessage` にする(2026-10-13 に作った)。

```proto
syntax = "proto3";

package voiceintercom.v1;

// 画像・動画。API が complete(POST /rooms/{room_id}/media/{media_id}/complete)で履歴に
// 保存した後に、LiveKit の Server API(RoomService.SendData)からデータチャネル
// (topic は "media"、reliable)でルームの全員に配信する。
//
// 中身は保存した履歴(GET /rooms/{room_id}/timeline の kind が media の行)と同じ。
// 送信者はメッセージの sender_identity で表す。LiveKit の送信元の参加者は無い(サーバーから送るため)。
// 受け手は、送信元の参加者があるもの(参加者が送ったもの)を捨てる。参加者は topic を偽れるため。
// 同じ event_id が2回以上届くことがある(complete のやり直し)。受け手は event_id で重複を捨てる。
//
// 項目を足すときは番号を足すだけにする。名前の変更と番号の使い回しはしない(消すときは reserved)。
message MediaMessage {
  // 履歴の event_id(`<occurred_at>#<source_id>`)。重複の排除と、履歴との突き合わせに使う
  string event_id = 1;
  // 送信者の LiveKit identity(履歴の sender_id。Cognito の sub)
  string sender_identity = 2;
  // 保存した時刻。ISO 8601(UTC、ミリ秒まで。例 2026-10-10T00:00:00.000Z)
  string occurred_at = 3;
  // uploads が返した media_id
  string media_id = 4;
  // MIME タイプ(当時は image/jpeg、image/png、image/webp、image/heic、video/mp4。
  // 2026-10-16 から何でも受け付ける。「ファイルの送信」)
  string content_type = 5;
  // 表示・再生の URL(CloudFront)
  string url = 6;
  // サムネイル(image/jpeg)の URL。なければ空
  string thumbnail_url = 7;
  // 本体のバイト数(実際に置かれた大きさ)
  uint64 size_bytes = 8;
  // 使わない(常に空)。画像・動画には文を添えられない(2026-10-13 に決めた。設計メモの
  // 「画像・動画のルームへの配信」)。古いアプリが読むので項目は残す
  string text = 9 [deprecated = true];
  // 使わない(常に false)。text と同じ
  bool text_truncated = 10 [deprecated = true];
  // 使わない(常に空)。添えた文の言語だったもの。text と同じ
  string language = 11 [deprecated = true];
  // 表示の幅と高さ(ピクセル。向きを反映した後の値。縦向きなら height が大きい)。
  // 送信者のアプリが整えた後の本体で測った値。分からなければ 0(古いアプリが上げたもの、
  // 管理コンソールから上げたものなど)。受け手は 0 なら決まった枠で表示する
  uint32 width = 12;
  uint32 height = 13;
  // 動画の長さ(ミリ秒)。画像と、分からないときは 0
  uint32 duration_ms = 14;
}
```

- **新しいファイルと新しい topic にする。** 既存の proto を変えないので、`buf breaking`(WIRE_JSON)に触れない。古いアプリは topic `media` を捨てるだけで、履歴を開けば見られる。
- **`Caption` や `TextMessage` を使い回さない。** `Caption` に URL を足すと、古いアプリは中身の無い字幕として表示してしまう。
- **後から足すときは、番号を足すだけにする。** 名前の変更と番号の使い回しはしない(WIRE_JSON は JSON の名前も見る)。消すときは `reserved` にする。幅・高さ・動画の長さなど、表示に使う項目は後から足せる(「決めていないこと」)。
- **大きさ。** LiveKit の reliable のデータは小さく保つ必要がある(公式は 15KiB 程度を推奨と読める。ローカルで測った上限は「サーバー側の確認」)。前は添えた文(最大10,000文字)を UTF-8 で 4096 バイトまでに切り詰めて入れていた(`text_truncated`)。文を添えなくなったので、メッセージは URL と ID が主で 1KB に満たない。
- **(2026-10-14)使わない項目。** `text`・`text_truncated`・`language` は常に空にし、`[deprecated = true]` を付けた。消すと `buf breaking`(WIRE_JSON)が通らない(「Previously present field "9" with name "text" ... was deleted」)。`deprecated` の付け外しとコメントだけの変更は、どちらも `buf breaking` を通る。生成するコードで使うと警告が出るので、`deprecated` にした。古いアプリは空の文として読む(表示は履歴の行)。
- **(2026-10-14)幅・高さ・長さ。** `width`(12)・`height`(13)・`duration_ms`(14)を足した。番号を足すだけなので `buf breaking` を通る。分からなければ 0。
- **時刻と URL は履歴と同じ書き方にする。** 受け手は、履歴で読んだ行と `MediaMessage` を同じ形で扱える。

### push 通知との関係

この節を決めるまでは、push 通知は「話し始め」だけで、チャットや画像・動画からは送らなかった(README の「push 通知」)。

**決定(2026-10-11): 画像・動画も、complete で API が push 通知を送る。** 宛先は、ルームのメンバーから、送信者と、今ルームにいる人を除いた人。

- 今ルームにいる人は、配信の前に呼ぶ `ListParticipants` の結果(kind が `STANDARD` の identity)を使う。話し始めの通知では Agent が `present_ids` を渡すが、画像・動画では API が自分で取れる。ルームが無ければ、メンバー全員(送信者を除く)に送る。
- 本文は「<送信者の表示名>さんが画像を送りました」「…動画を送りました」(プロフィールが無ければ「誰かが画像を送りました」)。前は添えた文の先頭50文字を足していたが、文を添えなくなったので外した(2026-10-14)。タイトルはルームの名前。data は `{"type": "media", "room_id": ..., "event_id": ...}`。通知を開いたアプリは、ルームの履歴を開き、`event_id` の行を見せる。
- 送信の失敗で complete を失敗にしない(`send_to_users` の例外を捕まえてログに残す)。
- 管理コンソールから上げたときも同じに送る。

間引きとテキスト入力の通知は、下の「push 通知の間引きとテキスト入力の通知」で決めた。

### push 通知の間引きとテキスト入力の通知

**決定(2026-10-13): ルームに何か届いたら(テキスト入力、音声の話し始め、画像、動画)、どれでも通知する。同じルーム × 同じ受け手には5分に1回まで。**

- **間引き:** 最初の1件はすぐ送り、そこから5分(`NOTIFY_INTERVAL_S`、既定 300 秒)以内は同じ受け手に同じルームの通知を送らない。種類(テキスト・話し始め・画像・動画)は分けずに数え、別のルームは別に数える。送信者本人と、今ルームにいる人には送らない(今までどおり)。それまでの話し始めの「10分に1回」はこれに置き換えた。
- **状態の置き場所:** Lambda をまたいで共有するので DynamoDB に持つ。新しいテーブルは作らず、timeline テーブルの別のパーティション(`room_id` が `notify#<room_id>`、`event_id` が受け手の sub)に `sent_at_epoch` を置く(話し始めの間引きの `notify-speaking#` を、種類を分けない名前に移した)。条件付きの UpdateItem で「前回が5分より前(か行がない)なら更新」し、更新できた受け手にだけ送る。同時に呼ばれても二重に送らない。`expires_at_epoch` の TTL で消える。テーブルの定義(Terraform とローカルの `mise run local:init`)は変えない。
  - テーブルを分けない理由は、話し始めの間引きを入れたときと同じ(メディアの仮の行と同じく TTL で消え、rooms や users の項目を取り合わない)。
  - 切り替えの直後は、`notify-speaking#` の行を見ないので、1回だけ多く届くことがある(行は TTL で消える)。
- **失敗:** FCM が使えない(サービスアカウントが未設定・読めない)なら時刻を取らない。送り終えなかった受け手(送信が例外で失敗したか、待ちきれなかった)は時刻を戻し、次の通知で送る。送り終えた受け手(FCM が失敗した人、端末を登録していない人も含む)の時刻は残す。
  - 待ちきれなかった送信は打ち切る(まだ始めていない端末への送信とアクセストークンの取得をしない)。Lambda は応答を返すと実行環境を止めるので、送信が続くとは見なせない。続くものとして時刻を残すと、通知が届かないまま5分送れなくなるうえ、次に実行環境が起きたときに古い通知として届くことがある。
  - 打ち切った時点で送っている最中の端末には後から届くことがあり、その受け手には次の通知でもう一度届く。まれで害が小さいので受け入れる。
  - 2026-10-16 に変えた。それまでは待ちきれなかった送信を続いているものとして時刻を戻さなかった。
- **テキスト入力の通知:** テキストはデータチャネルで Agent にだけ届き、API は履歴の保存(訳がそろってから。数秒遅れる)まで知らない。履歴の PUT は再送もあり、`present_ids` も持たない。そこで、話し始めと同じく Agent が受け付けたとき(空・長すぎで断ったもの、送り直しの重複は除く)に `POST /rooms/{room_id}/notifications/text` で API に知らせる(`{sender_id, present_ids, text}`)。本文は「<表示名>さん: <テキストの先頭50文字>…」(改行は空白にする。プロフィールが無ければ「誰か: …」)、data は `{"type": "text", "room_id": ...}`。原文のまま送り、受け手の言語には訳さない。
- **Agent の間引き:** API の呼び出しを減らすため、Agent は同じルームについて `NOTIFY_MIN_INTERVAL_S`(既定30秒)に1回だけ API を呼ぶ。話し始めとテキストで共通に数える。
- **時間:** 間引きの UpdateItem は受け手ごとに1回(同じリージョンで数 ms。テーブルの口は使い回す)。話し始め・テキストは送信を10秒、画像・動画は LiveKit の 2 秒 × 2 と push の 8 秒で待つのをやめるので、メンバーが数十人でも Lambda の timeout(15秒)に収まる。

### アプリの表示と再生

- **届いたら:** 送信者・時刻・サムネイル(無ければ画像は本体、動画は枠だけ)を、字幕と同じ時間の流れに `occurred_at` の順で並べる。タップで画像を全画面に、動画を再生する。
- **自分の送信:** complete の応答(履歴の行)ですぐ表示する。後から届く自分の `MediaMessage` は `event_id` で捨てる。complete が失敗したら、送信中の表示に「送れなかった」を出し、やり直せるようにする。
- **抜けを埋める:** データチャネルは、つながっている間しか届かない。入室したときと、つなぎ直したとき(`RoomReconnectedEvent` など)に、`GET /rooms/{room_id}/timeline` の新しい分を読み、`event_id` で重ねずに足す。
- **URL:** CloudFront の URL は署名なしで読める。`media_id` は推測できない乱数。キーは `media_id` ごとに変わり、同じキーの中身は変えないので、端末側で長くキャッシュしてよい。
- **サムネイル:** 動画はアプリが必ず作って上げる(`has_thumbnail: true`)。画像は、本体が大きい(例えば 1MB 超)ときに作る。一覧ではサムネイルだけを読み、本体はタップしてから読む(100人のルームで全員が本体を読むと、下りの転送が増えるため)。
- **動画の再生:** `video_player` に CloudFront の URL をそのまま渡し、読みながら再生する。MP4 の `moov` が先頭にないと、全部を読むまで再生が始まらない。アプリの出力は iOS・Android とも先頭に置く(「動画の解像度とビットレート」)。

### 端末での圧縮

「画像・動画の処理」の方針のまま、端末で圧縮してからアップロードする。配信の方式は圧縮に依らない(complete の後に送るので、受け手には圧縮とアップロードの時間は見えない)。

- **動画:** 元の解像度・フレームレートのまま、見合ったビットレートの H.264 の MP4 にし、サムネイルも作る(「動画の解像度とビットレート」)。圧縮が済んでから `uploads` を呼ぶ(`size_bytes` は圧縮後の大きさ)。長さの上限は設けず、10GB を超えるなら送らない。
- **画像:** HEIC は管理コンソール(Chrome、Firefox)で表示できない。アプリは JPEG にして送る(`image_picker` の `imageQuality` か `maxWidth` を指定すると JPEG になる。実機で確かめる)。API は `image/heic` を受け付けたままにする(古いアプリと管理コンソールのため)。
- **送信中の表示:** 圧縮とアップロードの間は、送信者の画面にだけ進み具合を出す。ほかの人には何も送らない(「送信中」を流すと、取り消しや失敗の扱いが増える)。

### 文を添えない(2026-10-14)

**決定: 画像・動画には文を添えられないようにする。** 利用者が決めた。添えた文の翻訳(API が gpt-6-luna を呼ぶか、Agent に頼むか)と、その配信の形を考えずに済むため。文を送りたいときはテキスト入力を使う(訳される)。

- REST API: complete の本文(`CompleteMediaUploadRequest` の `text`)を無くした。REST API はまだリリースしていない(README の項目と生成するクライアントは、どれもこのリポジトリの中)ので、項目を消してよいと判断した。ただし、作りかけのクライアントが送る `text` などの本文は 422 にせず無視する(Pydantic の既定で知らない項目を捨てる)。
- 履歴: media の行は `text` を空、`language` を null にする(`language` は添えた文の言語だった)。前に文を添えて保存した行も、読むときに空にする(dev の DynamoDB に残っていても返さない)。
- `MediaMessage`: `text`・`text_truncated`・`language` は残し、`deprecated` にした(「データチャネルの取り決め」)。古いアプリが使われ続けるため、消さない。
- push 通知の本文から、添えた文の先頭を外した。
- アプリ: `MediaUploader.submit` は文を受けない。全画面の表示(`MediaViewerScreen`)の文の欄も外した。

### 幅・高さ・動画の長さ(2026-10-14)

**決定: アプリが整えた後の本体で測った幅・高さ・動画の長さを uploads で送り、API は履歴と `MediaMessage` にそのまま入れる。** 受け手は、画像を読む前に縦横比の枠を取り、動画のカードに長さを出す。

- 項目: `CreateMediaUploadRequest` と履歴の `media` に `width`・`height`(ピクセル)・`duration_ms`(ミリ秒)。どれも任意(null)で、`MediaMessage` では 0 が「分からない」。
- 幅・高さは向きを反映した後の表示の大きさ(縦向きで撮ったものは高さが大きい)。動画は、整えた後の本体の幅・高さと回転のメタデータから出す(`apps/mobile` の README の「幅・高さ・長さ」)。
- API は本体を読んで確かめない(Lambda で画像や動画を開くと、時間とメモリが要る)。範囲だけを確かめる: `width`・`height` は 1〜65535(JPEG と HEIC の上限)で、両方送るか両方送らないか。`duration_ms` は 1〜86,400,000(24時間。アプリは長さに上限を設けないが、明らかにおかしい値を弾く)で、動画のときだけ。外れたら 422。値を偽っても、送信者が自分の画像・動画の枠を崩せるだけ。
- 足す前に保存した行、管理コンソールから上げたもの(測らない)、HEIC(アプリで読めない)は値が無い。アプリは決まった枠(200x150)で出し、長さを出さない。
- 測った値は uploads の仮の行に持たせ、complete で履歴に書く(complete で送り直させない。大きさと同じ)。

### 動画の解像度とビットレート(2026-10-14)

**決定: 動画は元の解像度とフレームレートのまま、それに見合ったビットレートの H.264 の MP4 にする。** 利用者が決めた。前は `video_compress` で 1280x720 まで縮めていた。容量は気にしないが、ビットレートが無駄に高くならないようにする。動画の長さの上限(仮の3分)はやめ、大きさの上限を 10GB にする(アップロードはマルチパート。API 側は別に作る)。

- 出力は今のとおり H.264 の MP4(「画像・動画の処理」の再生の条件)。`moov` を先頭に置き、読みながら再生できるようにする。音声は AAC で残す。回転(縦向き)は元の回転のメタデータのまま。HDR(iPhone の HLG・Dolby Vision)は BT.709 の SDR にする(H.264 の 8 ビットには HDR を入れない)。
- **ビットレートの決め方**(`apps/mobile` の `lib/media/video_plan.dart`):
  - 目標 = 幅 × 高さ × 実効のフレームレート × 0.1(bits per pixel)。実効のフレームレートは 30fps までをそのまま、30〜60fps を半分に数え、60fps を超える分は数えない(フレームが細かいほど前後が似ていて、1フレームあたりのビットが少なくて済む)。分からなければ 30fps。下限は 1Mbps。
  - 例: 720p30 で 2.8Mbps、1080p30 で 6.2Mbps、1080p60 で 9.3Mbps、4K30 で 24.9Mbps、4K60 で 37.3Mbps。YouTube の推奨のアップロードのビットレート(1080p30 で 8Mbps、4K60 で 53〜68Mbps。再圧縮される前提の高めの値)より少し低く、`AVAssetExportSession` の 1280x720 のプリセット(720p60 で 10.7Mbps)よりずっと低い。
  - 元の映像のビットレートは超えない(目標と元の小さいほう)。
  - 60fps は保つ(元に近づける方針)。
- **符号化し直さないとき**: 元が H.264 で、音声が AAC か無く、映像のビットレートが目標の 1.25 倍以下なら、符号化し直さない(画質を落として少し縮めても得が小さい)。`moov` が先頭の MP4 ならそのまま送り、MOV や `moov` が末尾の MP4(Android のカメラは MediaMuxer で末尾に置く)は、符号化せずに MP4 に入れ直す。HEVC は管理コンソール(ブラウザ)で再生できないことがあるので、ビットレートが低くても H.264 にする。
- **大きさの確かめ**: 符号化する前に、目標のビットレートと長さ(音声は 2 チャンネル分の 192kbps)で大きさを見積もり、10GB を超えそうなら符号化せずに止める(何十分も符号化した後で送れないと分かるのを避ける)。符号化した後も確かめる。

| --- | --- | --- | --- | --- |

- 自前を選んだ理由: パッケージは、iOS でビットレートを指定できるものが moov を末尾に置き、moov を先頭に置くものが iOS でビットレートを指定できなかった。どちらかを直して使うなら、フォークを持つことになり、自前と手間が変わらない。自前なら、ビットレートの決め方・符号化し直さないときの判断・HDR の扱い・moov の位置を、手元のコードで決めて確かめられる。

- `video_compress` を外したので、iOS の CocoaPods は要らなくなった(ほかのプラグインはどれも SwiftPM に対応している)。`Podfile` を消し、Swift Package Manager だけにした。

### 字幕の送信元(2026-10-13)

**決定: アプリは topic `caption` を、送信元が Agent の参加者(`DataReceivedEvent.participant` があり、その `kind` が `AGENT`)のものだけ読む。** 送信元が null のもの、Agent 以外の参加者が送ったものは捨てる。

- 普通の参加者も偽の字幕を送れた。API が発行するアプリ利用者のトークン(`services/api` の `create_livekit_token`)は `VideoGrants(room_join=True, room=...)` だけで、`can_publish_data` は既定の真になる。テキスト入力を topic `text` で送るので外せず、LiveKit には topic ごとの権限も無い。偽の字幕は話者(`speaker_identity`)も中身も自由に書け、`message_id` を合わせれば他人のテキストの送り直しも止められた。
- `kind` は、LiveKit サーバーが配る参加者の情報(`ParticipantInfo.kind`)から SDK が入れる(`livekit_client` 2.13.1 の `Participant.updateFromInfo`)。送信元の参加者も、サーバーが付けた identity で引く。Agent の kind はディスパッチで入った参加者にサーバーが付けるもので、利用者のトークン(API キーで署名する)では名乗れない。
- Agent は字幕を参加者として送る(Server API は使わない)ので、null を許す理由は無い。null を受け入れると、入った直後(約3秒)の参加者が偽の字幕を送れてしまう(「サーバー側の確認」)。

入室直後の欠け:

- **Agent が先にいるルーム**(2人目からの入室): 入室の応答に参加者の一覧があるので、アプリはすぐ Agent を知る。欠けない。つなぎ直しも同じ(入り直すときは同じ応答で知り、続きのつなぎ直しでは一覧を保つ)。
- **Agent が後から入るルーム**(最初の人がルームを作る。Agent の再ディスパッチ): アプリが Agent を知るまでの約3秒に届いた字幕は捨てる。Android エミュレーターの `room_flow_test` で確かめると、入室の直後に送ったテキストの字幕が返ってこず「届かなかった」になった。Agent は1回目を受け付けて字幕を返したが、アプリは Agent をまだ知らずに捨て、2回目からの送り直しは Agent が重複として捨てたため。
  - **対策: テキスト入力は、アプリが Agent を知ってから送る**(`TextSender.canSend`。Agent が入ったら待っていたものをすぐ送る)。待つ間も送り直しの回数に数え、12秒(4秒 × 3回)で Agent が来なければ「届かなかった」にする。直した後の `room_flow_test` は通り、Agent が入ってから約2.7秒でテキストが1回で届き、英語の話者の字幕と訳も欠けなかった。
  - 音声の字幕は、Agent が入ってから約3秒のうちに確定まで届くことは、まず無い(Agent が話者のトラックを購読し、話して離すまで書き起こせない)。途中の断片を捨てても、確定で置き換わる。欠けうるのは、Agent が入った瞬間に話していた発話の確定が3秒のうちに届いたときだけで、これは許す。
  - (2026-10-14 に追加)Agent は送り直しに字幕と状態を送り直すようにした(下の「テキスト入力の送り直しと送信者への知らせ」)。
  - 「送信元が null の字幕を少し保留して、Agent を知ったら出す」は採らない。公開の API では null の送信元の identity が分からず、Agent が送ったと確かめられないため(「誰がルームに知らせるか」と同じ理由)。

### テキスト入力の送り直しと送信者への知らせ(2026-10-14)

**決定 1: Agent は、同じ `(identity, message_id)` の送り直しに、処理をやり直さずに字幕と状態を送信者だけに送り直す。** これまでは2回目から捨てていたので、最初の字幕を送信者のアプリが捨てていた(Agent を知る前に届いた。上の「字幕の送信元」)と、字幕が二度と返らず、アプリは「届かなかった」になった。

- 1通ごとに、配信した字幕(原文と訳の確定)と最後の状態を10分覚えておく(`RecentMessages`)。送り直されたら、それを `destination_identities` で送信者にだけ送る。同じ `segment_id` なので、受け手は同じ字幕として置き換える。
- 処理中に送り直されたら、そこまでの字幕と `ACCEPTED` を送る。残りの訳はそろったときにルームに配信し、結果も送る。終わるまで待って送る案より簡単で、送り直しも早く止まる。
- 翻訳と読み上げはやり直さない(費用)。ほかの聞き手には送り直さない(送り直すのは送信者のアプリだけで、ほかの人は字幕を重ねて受けても得がない)。

**決定 2: Agent は、テキスト入力の受け付け・断り・結果を `TextStatus`(`proto/voiceintercom/v1/text_status.proto`。topic `text_status`)で送信者だけに送る。**

- `ACCEPTED`(原文の字幕より先)、`REJECTED`(`REASON_EMPTY`、`REASON_TOO_LONG` と `max_chars`)、終わったら `COMPLETED` か `FAILED`(訳せなかった言語、読み上げに失敗した言語)。
- 新しいファイルに新しいメッセージを足したので、既存のメッセージは変わらない(`buf breaking` を通した)。古いアプリは知らない topic を捨て、字幕で送り直しを止める。古い Agent は `TextStatus` を送らず、新しいアプリは字幕で止める。
- 受け手は、送信元が Agent の参加者のものだけを読む(字幕と同じ理由。参加者は topic と宛先を自由に選んで送れる)。
- 送り直しを止める合図にも使う。断られたテキストには字幕が出ないので、これまでは3回送り直して「届かなかった」になっていた。`REJECTED` で、送り直さずに理由を出せる。
- アプリの「Agent を知ってから送る」(`TextSender.canSend`)は残す。Agent を知る前の応答は字幕も `TextStatus` も捨てるので、知らないうちに送ると、送り直しの回数(3回)を使い切ることがある。決定 1 は、つなぎ直しや Agent の入れ替わりなどで、それでも最初の応答を捨てたときの備え。

統合テスト(`room_flow_test` など)と、LiveKit を通した確認はまだ。

## 送ったものの削除

**決定(2026-10-14): 送った本人は、テキスト入力・画像・動画を消せる。** 音声の字幕(発話)は対象外。通報は作らない。消したものは、その場所に「削除されたテキスト」「削除された画像」「削除された動画」と、ほかと区別できる形(斜体・薄い色・ごみ箱のアイコン)で出す。履歴の画面でも、ルームの表示でも同じ。実装は `services/api` の `timeline.py`・`deletion.py`、`proto/voiceintercom/v1/deletion.proto`、`apps/mobile` の `deletion_receiver.dart`。

### API

- `DELETE /rooms/{room_id}/timeline/event?event_id=...`。呼べるのは行の送信者だけ(他人は 403。管理者も 403。管理コンソールではルームの中身を扱わない方針のため)。音声の発話も 403、行が無ければ 404。2回目からは同じ墓石を返す(後始末はやり直す)。
- `GET /rooms/{room_id}/timeline/event?event_id=...` を足した。強い整合の読み取り(`ConsistentRead`)で1件を返す。受け手がデータチャネルの知らせを確かめるのに使う。
- event_id はパスではなくクエリにした。event_id には `#` が入り、生成した Dart のクライアントはパスの値をエンコードしない(`#` 以降が URL のフラグメントになる)。API Gateway(HTTP API)が `%23` を戻すかも確かめられていない。クエリはクライアントがエンコードし、`before` で実績がある。
- **墓石:** 行は消さずに `deleted_at` を書き、`text` と `translations` を DynamoDB からも消す(UpdateItem の REMOVE)。media の行は、本体を消し直すときと「画像か動画か」を出すために、`media_id`・`content_type` などを残す。応答の `TimelineEvent` には `deleted`(`deleted_at` と、media なら `media_type`: image / video)が付き、`text` は空、`translations` は空、`media` は null。送信者・時刻・event_id は残す(その場所に出すため)。
- テキスト入力の行は、Agent が原文と訳をそろえてから1件で書く(訳は同じ行の `translations`)。複数の行には分かれていないので、1件を墓石にすれば足りる。
- **アプリが自分のテキストの行を見つける:** 行に `message_id`(アプリが振った `TextMessage` の ID)を足した。Agent が保存のときに入れる(`PutTimelineEventRequest.message_id`、text のときだけ)。アプリは先頭のページで `message_id` と送信者の合う行を探す。Agent は訳がそろうまで(長くて30秒)保存しないので、無ければ1・2・4秒の間を置いて読み直し、それでも無ければ「まだ保存されていない」と出す。
- **Agent の PUT で戻さない:** `put_event` は `attribute_not_exists(deleted_at)` を条件に書き、消した行なら墓石を返す(5xx の後の再送が消した後に届いても戻らない)。
- 消した画像・動画の complete をやり直すと、墓石を返し、配信もしない。

### 画像・動画の本体と CloudFront

- **S3 の本体とサムネイルを消す。** 配信の URL は署名なしで、`media_id` を知っていれば誰でも読める(端末のキャッシュや転送で URL が残る)。消す人の意図に合わせ、物も消す。バケットにバージョニングは無いので、消せば戻らない。
- **CloudFront のキャッシュを無効にする。** キャッシュポリシーは Managed-CachingOptimized で、オブジェクトに Cache-Control が無いので既定の 24時間(最大1年)キャッシュされうる。無効にしないと、消した後も最大24時間はエッジから読める。無効化の料金は、アカウントで月1,000パスまで無料、超えると1パス 0.005 USD。ワイルドカード(`/rooms/<room_id>/<media_id>/*`)は1パスに数えるので、1件の削除で1パス(本体とサムネイルをまとめて)。少人数の利用なら無料の範囲に収まる見込み(dev と prod は同じアカウントなので枠を分け合う)。
- 順は、墓石 → 知らせ → S3 を消す → 消せたら無効化。S3 より先に無効化すると、その間に読まれてまたキャッシュされうる。CallerReference は `delete-<media_id>` で、2回目の DELETE で無効化を作り直さない(料金も増えない)。ローカル(CloudFront が無い)では無効化を飛ばす(`MEDIA_DISTRIBUTION_ID` が空)。
- 後始末の失敗では DELETE を失敗にしない(ログに残し、墓石を 200 で返す)。もう一度 DELETE すればやり直す。
- 残ること: 消す前に端末が読んだ画像(メモリのキャッシュ)、アップロードの署名付き URL の期限(1時間)の内に、本人がもう一度 PUT すれば同じキーに置ける(本人のことで、履歴からは URL を返さない)。

### データチャネルの知らせ

topic は `deletion`(reliable)。メッセージは `proto/voiceintercom/v1/deletion.proto` の `DeletionMessage`(`event_id`、`sender_identity`、`kind`、`message_id`、`deleted_at`)。新しいファイルと topic なので `buf breaking` に触れず、古いアプリは捨てるだけ(入り直すか履歴を開けば、墓石が `(本文なし)` として見える。本文は返らない)。

- 送るのは API で、画像・動画の配信と同じ仕組み(`ListParticipants` で人がいれば `SendData`。`media_broadcast.send_to_room`)。2回目の DELETE でも送る。push 通知は取り消さない(届いたものは消せない)。
- **受け手の確かめ方:** 送信元の参加者があるものは捨てる。送信元が null でも、入った直後の参加者が送ったものかもしれない(「サーバー側の確認」)ので信用しない。`GET .../timeline/event` で event_id の行を読み、`deleted` があるときだけ、その行(墓石)を表示に反映する。表示を変える相手(送信者・`message_id`)も行のものを使う。行を墓石にできるのは送った本人だけなので、偽の知らせで他人のものを消したように見せることはできない。1件の取得は強い整合なので、消されていなければ読み直さずに捨てる(読めなかったときだけ1秒・3秒で読み直す)。
- 字幕はこの知らせに頼らず、送信者と `message_id` が合うものを「削除されたテキスト」にする。消したものの組を覚えておき、後から届いた字幕(訳の途中、遅れた確定)でも本文を出さない。
- 入室とつなぎ直しで読む履歴の先頭のページ(画像・動画の抜けを埋めるもの)にある墓石も、同じく反映する。
- **送り直しへの応答で戻さない:** Agent は送信者の送り直しに、覚えておいた字幕(`RecentMessages`)を送信者だけに送り直す(上の「テキスト入力の送り直しと送信者への知らせ」)。消した後にこれが届いても、アプリは消した `(送信者, message_id)` を覚えているので、字幕を「削除されたテキスト」のまま保つ(字幕の区切りが新しく作られても同じ)。送り直しを受けるのは送信者のアプリだけで、そのアプリは自分の削除(応答の墓石)か topic `deletion` の知らせで消した組を覚えている(履歴の画面から消したときも、ルームにいれば知らせが届く)。入り直したときは、先頭のページの墓石で覚え直す。そのため、Agent 側で覚えた字幕を消す仕組みは足さない。

## コストの目安

OpenAI の音声処理は、話者が1分話すごとに、翻訳先が3言語で約 0.119 USD かかる。翻訳は 0.034 USD/分 × 言語数、原文の文字起こしは 0.017 USD/分(話者ごとに1本)で、公開料金からの単純計算。

| 翻訳先の言語数 | 翻訳(USD/分) | 原文の文字起こし(USD/分) | 合計(USD/分) |
| --- | --- | --- | --- |
| 1 | 0.034 | 0.017 | 0.051 |
| 2 | 0.068 | 0.017 | 0.085 |
| 3 | 0.102 | 0.017 | 0.119 |
| 4 | 0.136 | 0.017 | 0.153 |

翻訳先が3言語のとき、1時間話し続けると約 7.14 USD。次は含まれていない。

- テキスト入力の翻訳と読み上げの料金(PoC では、13言語と原文を読み上げて1通あたり約 0.02 USD。ほぼ読み上げの出力音声の分)
- LiveKit、AWS の料金
- 発話の途中の無音の課金(送った音声の長さで課金されるため、請求の分数はボタンを押していた時間になる。話していない間は送らない設計にする)
