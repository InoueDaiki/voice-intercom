# ボイスインカムアプリ 設計書

Oct 7, 2026 · @大樹

音声配信は LiveKit、翻訳と文字起こしは OpenAI、履歴とメディアは AWS サーバーレスで構築する。

## 概要と決定事項

ボイスインカムアプリを、Flutter(iOS / Android)のユーザー向けアプリと React の管理コンソールで構築する。ルーム内では、PTT または発話検知の間だけ音声を配信し、テキスト入力は読み上げ音声とテキストの両方で届ける。チャットでは画像と動画を送れる。音声のやり取りはリアルタイムに文字起こしし、ユーザーが希望する言語に翻訳して配信する。

| 前提 | 内容 |
| --- | --- |
| ルーム規模 | 基本は少人数、最大100人程度 |
| 遅延 | 元の音声は300ms程度。翻訳・字幕は数秒の遅れを許容 |
| 録音 | 必要 |

| 領域 | 決定 |
| --- | --- |
| 音声配信 | LiveKit。まず LiveKit Cloud で作り、運用が見えた段階でセルフホストを検討する |
| 翻訳音声 | OpenAI gpt-realtime-translate。話者ごと・翻訳先の言語ごとにセッションを作る |
| 原文の文字起こし | OpenAI gpt-realtime-whisper。話者ごとに1本 |
| バックエンド | AWS サーバーレス(API Gateway + Lambda、DynamoDB、S3 + CloudFront) |
| 録音 | LiveKit Egress から S3 へ |
| 比較検討の記録 | [技術選定メモ](https://claude.ai/code/artifact/800896cc-8702-467f-a745-5b8b40b62536)(Gemini など不採用の選択肢を含む) |

## 全体アーキテクチャ

音声・チャット・字幕の配信は LiveKit に集約し、履歴・メディア・トークン発行は AWS サーバーレス、翻訳と文字起こしは Agent から OpenAI に任せる。

Flutter アプリは LiveKit に音声とチャットを送り、Agent が各話者の音声を購読して OpenAI に渡す。翻訳音声と字幕は LiveKit に戻して配信し、履歴・画像・動画・録音は AWS 側で持つ。

## 採用技術

サーバーレスにするのは AWS 側の API・履歴・メディアで、常時接続が要る LiveKit と Agent はサーバーレスにならない。

| レイヤー | 採用 | 役割 |
| --- | --- | --- |
| ユーザー向けアプリ | Flutter + LiveKit Flutter SDK | PTT / 発話検知での音声送信、チャット、字幕・翻訳の表示 |
| 管理コンソール | React | 管理 API を通じた運用 |
| リアルタイム配信 | LiveKit | 音声、チャット、字幕、翻訳テキストをルーム内に配信(データチャネルを含む) |
| AI 中継 | LiveKit Agent | 各話者の音声を購読して OpenAI に渡し、結果を LiveKit に戻して配信する。実行環境は ECS Fargate を想定(常時接続のワーカーのため Lambda には向かない) |
| 翻訳音声・翻訳テキスト | OpenAI gpt-realtime-translate | `/v1/realtime/translations` に WebSocket で接続 |
| 原文の文字起こし | OpenAI gpt-realtime-whisper | 原文の字幕と、文字起こしの保存 |
| 読み上げ(テキスト入力用) | TTS(候補: OpenAI gpt-realtime-2.1-mini、Google。PoC で選定) | テキスト翻訳は OpenAI gpt-6-luna。読み上げは差し替え可能な構成にする(「テキスト入力の翻訳と読み上げ」を参照) |
| API | API Gateway + Lambda | LiveKit トークン発行、履歴取得、管理 API、メディアの署名付き URL 発行 |
| 履歴 | DynamoDB | チャット履歴、文字起こし、翻訳テキスト |
| メディア | S3 + CloudFront | 画像・動画の保存と配信 |
| 録音 | LiveKit Egress → S3 | 話者別トラックとルーム合成の録音 |
| push 通知 | FCM(Firebase Cloud Messaging)。Lambda から送る | アプリを閉じているユーザーへの通知 |

## 処理の流れ

入力は音声でもテキストでも LiveKit に送り、Agent が処理して、翻訳前と後のテキスト・音声を LiveKit で配信する。画像・動画だけは LiveKit を通さず、AWS 側で処理する。

&#91;embedded content: 処理の流れ · 音声とテキストの2経路\]

| 入力 | 翻訳前テキスト | 翻訳前音声 | 翻訳後テキスト | 翻訳後音声 |
| --- | --- | --- | --- | --- |
| 音声 | STT で作る | 入力した音声をそのまま使う | STS が音声と同時に作る | STS が作る |
| テキスト | 入力したテキストをそのまま使う | TTS で作る | テキスト翻訳で作る | 翻訳後のテキストを TTS で作る |

翻訳後のテキストと音声は、翻訳先の言語がルームにあるときだけ作る。

### 音声(PTT / 発話検知)

1. アプリが API Gateway + Lambda から LiveKit のトークンを取得し、ルームに入る。
2. 音声トラックは入室時に publish しておき、ボタンを押している間(または発話検知の間)だけミュートを外す。方式は PoC で確定する。
3. Agent が話者のトラックを1回だけ購読する。
4. 翻訳前のテキストを STT(gpt-realtime-whisper、話者ごとに1本)で作り、データチャネルで配信する。元の音声はそのまま配信する。
5. 翻訳先の言語がルームにあれば、言語ごとに STS セッション(gpt-realtime-translate)へ流し、翻訳後の音声(言語別のトラック)と翻訳後のテキスト(データチャネル)を配信する。
6. 聞き手は、自分の言語のトラックを購読する。話者と同じ言語の聞き手には翻訳を作らない。
7. 録音は Egress が S3 に出力する。テキストは、Agent が API 経由で DynamoDB に保存する。

### テキスト入力

1. アプリがテキストを LiveKit に送る(データチャネル)。
2. Agent が受け取り、翻訳前のテキストをそのまま配信する。
3. 翻訳前のテキストを TTS で読み上げ、翻訳前の音声として配信する。
4. 翻訳先の言語がルームにあれば、言語ごとにテキストを翻訳して配信し、翻訳後のテキストを TTS で読み上げて、翻訳後の音声として配信する。
5. テキストは、Agent が API 経由で DynamoDB に保存する。
6. 読み上げ音声(翻訳前・翻訳後)は、Agent が LiveKit のトラックとして配信する。言語ごとに別のトラックにして、聞き手は自分の言語のトラックを購読する。

### 画像・動画

1. アプリが Lambda に署名付き URL を要求し、S3 へ直接アップロードする。
2. アップロード後、メディアの URL をチャットメッセージとして DynamoDB に保存し、ルームに配信する。
3. 受信側は CloudFront の URL で表示・再生する。

## 翻訳・文字起こしの設計

翻訳セッションは「話者のトラック × 翻訳先の言語」ごとに1本作り、Agent が LiveKit と OpenAI の間を中継する。仕様は [OpenAI の公式ガイド](https://developers.openai.com/api/docs/guides/realtime-translation)に基づく。

| 項目 | 設計 |
| --- | --- |
| セッション数 | 同時に話している話者数 × 翻訳先の言語数。例: 2人が同時に話し、聞き手の言語が4種類なら8セッション |
| 接続 | Agent から WebSocket で `/v1/realtime/translations?model=gpt-realtime-translate` に接続する。API キーは Agent に置き、アプリには渡さない |
| 入力音声 | 24kHz、PCM16、モノラルを base64 にして `session.input_audio_buffer.append` で送る。LiveKit の 48kHz からリサンプリングする |
| 翻訳先の言語 | `session.update` で `session.audio.output.language` を指定する |
| 受信するイベント | `session.output_audio.delta`(翻訳音声)、`session.output_transcript.delta`(翻訳テキスト)。翻訳テキストは追記専用の断片で、連結時に空白を挟まない |
| 翻訳音声の形式 | 48kHz、PCM16、モノラル(公式に記載がなく、PoC の実測で判断)。200ms ごとに届き、話していない間も無音(ほぼ0)のチャンクが届き続ける。LiveKit の 48kHz にそのまま流せる |
| 原文のテキスト | 翻訳セッションとは別に、話者ごとに1本の gpt-realtime-whisper で作る。翻訳セッションごとに有効にすると、言語数ぶん重複して課金される可能性があるため。接続先は `/v1/realtime?intent=transcription` で、`session.update` に `type: "transcription"` を指定する(PoC で動作を確認) |
| 話者の分離 | 話者ごとに別トラックで渡す。混ぜない(OpenAI の公式推奨) |
| 話者と同じ言語の聞き手 | 翻訳セッションを作らない。話者の言語はユーザープロフィールで判定する |
| 遅延の扱い | 元音声はすぐ流し、翻訳音声と字幕は数秒遅れて届く別チャンネルとして扱う |

### 選べる翻訳言語

ユーザーが選べる翻訳言語は、OpenAI の出力言語13言語。スペイン語、ポルトガル語、フランス語、日本語、ロシア語、中国語、ドイツ語、韓国語、ヒンディー語、インドネシア語、ベトナム語、イタリア語、英語。入力は70以上の言語から自動で検出される。[OpenAI の公式クックブック](https://developers.openai.com/cookbook/examples/voice_solutions/realtime_translation_guide)で確認した。

### 公式に書かれている制約

- **翻訳先と同じ言語は訳されない。** 翻訳先の言語の音声は、翻訳されず無音になることがある。言語を混ぜて話す話者では、翻訳先に含まれる言語の部分が欠ける。元の音声は残し、翻訳音声が流れている間は小さくする(完全には消さない)。
- **用語集やプロンプトは使えない。** カスタムプロンプト、用語集、読みの指定、声の選択はできない。固有名詞や専門用語を誤ることがあるため、評価用の用語セットで確認する。
- **声は話者に追従する。** 翻訳音声は、話者の声の調子・高さ・話し方に合わせて作られる。話者ごとにセッションを分けるので、声はその話者のものになる。
- **ノイズ低減を選べる。** `near_field`(ヘッドセットなどの近接マイク)と `far_field`(ノート PC や会議室のマイク)から選ぶ。アプリの利用場面に合わせて PoC で決める。

### 利用上限

- 上限は「1分あたりに処理できる音声の分数」で決まり、利用ティアごとに Tier 1 が 50、Tier 2 が 200、Tier 3 が 400、Tier 4 が 650、Tier 5 が 850。無料枠では使えない。([モデルページ](https://developers.openai.com/api/docs/models/gpt-realtime-translate))
- 1つのセッションが毎分1分ぶんの音声を使うと考えると、Tier 5 で同時に850セッション。8セッションのルーム(2話者 × 4言語)なら、約100ルームが同時に使える目安(試算)。
- 無音を送り続ける分が上限と課金の対象になるかは、公式に記載がなく未確認。

### セッションの寿命と遅延(追加調査)

- **課金:** 公式は「音声の長さ」で課金されるとだけ書く。入力と出力のどちらを数えるか、無音、秒か分か、最低課金時間の記載はない。
- **接続時間:** 最大接続時間、アイドルタイムアウト、再接続の手順は記載がない。通常の Realtime には60分の上限があるという投稿があるが、翻訳に当てはまるかは不明。Agent 側で再接続し、長時間のルームではセッションを作り直す前提にする。
- **遅延:** 出力は200ms刻みで届く。公式の遅延の数値はない。第三者の計測(LiveLingo)では、日本語の音声で約3.3秒の遅れが一定だった。通訳型で文の動詞を待つため、語順が違う日英では長くなる可能性がある(推測)。
- **重なり・短い発話・末尾の欠け:** 記載がない。話者ごとの別ストリームは公式の推奨。末尾の欠けは、ボタンを離した後に数百ms の無音を送ってから `session.close` を送る案がある(推測)。PoC で確かめる。
- **セッションの使い回し:** 記載がない。話者が交代するたびに作り直すか、入室中は維持するかは、無音の課金が分かるまで決められない。

### 翻訳の PoC の結果(2026-10-08)

`services/agent/poc/translate_bench.py` で、WAV を実時間のペースで送って測った。入力は macOS の `say` で作った読み上げ音声(日本語5文、英語4文)で、人の声ではまだ試していない。

| 項目 | 結果 |
| --- | --- |
| 翻訳テキストの初回 | 発話の開始から 0.6〜5.0秒。多くは 1.2〜2.4秒 |
| 翻訳音声の初回 | 発話の開始から 1.4〜5.5秒。多くは 1.8〜2.5秒で、第三者の計測(約3.3秒)より短い。ただし回によって 3.5秒以上になる(同じ文の10回中4回) |
| 日→英と英→日 | 差は見えなかった |
| 翻訳音声の最後 | 発話の終了から 0.8〜4.3秒 |
| `session.closed` | `session.close` から 4〜6秒後。翻訳音声が終わった後も数秒待つ |
| 末尾の欠け | 無音を足さずに `session.close` を送っても、ほとんどの回で最後まで届いた(同じ文で5回中5回)。最初の1回だけ、翻訳音声が 0.4秒分しか届かなかった(原因は不明) |
| whisper | 最初の文字は発話の開始から約1.0〜1.3秒。`input_audio_buffer.commit` から約0.6秒で確定(`completed`) |
| 短い発話 | 「はい」「Copy that.」は、翻訳テキストも翻訳音声も出なかった(3回中3回)。whisper は文字にできた |

訳の誤り(数字・固有名詞・聞き間違い・付け足し)が目立った。

- 数字: 「250 units」を「200台」と訳した(同じ文の6回中4回)。元にない「1月17日」を足したこともある。
- 固有名詞: 「品川」が「Hina River」「Shinigawa」になった。「三番ゲート」が「BANG BANG GATE」になった。
- 聞き間違い: 「すみません」が「To Sumire」になった。
- 付け足し: 元の文にない「なんとか間に合わせましょう」「Got it?」「Yes」が付いた。
- 同じ文でも、回ごとに訳と遅延が変わる。

設計への反映(案):

- 翻訳音声は 48kHz のまま LiveKit のトラックに流す。翻訳音声の無音のチャンクも届き続けるので、遅延の計測やログでは無音を除いて扱う。
- 翻訳は誤りうる前提で、聞き手の画面では原文の字幕(whisper)を併記する。数字や固有名詞は原文を見れば確かめられるようにする。
- 「はい」のような短い応答は翻訳されないことがある。元の音声を小さくしすぎない(「公式に書かれている制約」の方針を保つ)。
- PTT を離したら `session.close` を送り、`session.closed` まで最大10秒ほど受信を続ける。無音を足すかは、人の声で再確認してから決める。

未確認のまま残っていること: 人の声と雑音のある録音での結果、無音を送り続けたときの課金、セッションの最大接続時間。

### PTT の運用

1. 発話中はセッションを維持し、無音も含めて連続して音声を送る。
2. ボタンを離してもすぐには閉じず、一定時間(PoC で決める)誰も話さなければ `session.close` を送る。
3. `session.close` を送ったら音声の送信を止め、`session.closed` が返るまで受信を続ける。途中で切ると、翻訳の末尾が欠ける。
4. 無音や待機中の課金は未確認。PoC で実測する。

## テキスト入力の翻訳と読み上げ

テキスト入力は音声と別の経路で、Agent がテキスト翻訳と TTS を呼ぶ。OpenAI の TTS に終了予定のモデルがあるため、TTS は差し替えられる構成にする。

| 項目 | 調査結果 |
| --- | --- |
| テキスト翻訳 | 候補は gpt-6-luna。入力 0.10 USD、出力 0.50 USD(100万トークンあたり)、速度は fast、Structured Outputs に対応([モデルページ](https://developers.openai.com/api/docs/models/gpt-6-luna))。翻訳先の全言語を JSON スキーマで1回の呼び出しにまとめる。200文字を13言語に訳しても出力は約2,000トークンで、1通あたり約 0.001 USD(試算)。品質が足りない言語だけ上位モデルに切り替える。上位の gpt-6.1-sol は 2 / 10 USD(調査担当の報告。未検証) |
| テキスト翻訳の遅延 | 公式の数値はない。出力量(言語数)に比例するので PoC で測る |
| TTS の終了予定 | tts-1、tts-1-hd、gpt-4o-mini-tts は、2027年1月6日に API から削除される。2026年10月1日の告知で、後継は gpt-realtime-2.1-mini([非推奨ページ](https://developers.openai.com/api/docs/deprecations))。一方、TTS ガイドには非推奨の記載がなく、ページ間で食い違っている |
| 後継の gpt-realtime-2.1-mini | 音声出力は 20 USD(100万トークンあたり。調査担当の報告)。会話向けのモデルで、渡した文を一字一句読み上げる使い方ができるか、出力形式、最初の音までの遅延は未確認 |
| 他社 | Google Cloud の Chirp 3 HD(30 USD / 100万文字)と Gemini 2.5 Flash TTS。Amazon Polly の Generative 音声は、日本語・ヒンディー語・インドネシア語・ベトナム語・ロシア語に非対応(いずれも調査担当の報告。公式ページは未確認) |
| 13言語での対応 | TTS ガイドは、Whisper 準拠の52言語に対応し、声は英語向けに最適化されていると書く。言語別の品質表はなく、試聴が必要 |

- TTS は Agent の中で窓口を1つに分け、OpenAI と Google を入れ替えられるようにする。
- PoC で、gpt-realtime-2.1-mini と Google を、日本語と英語を含む主要言語で試聴し、最初の音までの遅延を比べて決める。
- OpenAI は告知から約3か月で削除する例がある。translate と whisper のモデル名も設定で変えられるようにする。現時点の非推奨ページに、この2つは載っていない。

## LiveKit の設計

LiveKit の主な不安は解消した。Flutter には公式 SDK があり、100人の音声ルームは公式ベンチマークで余裕があり、録音は自動 egress で話者別に取れる。注意点は、Build プランの参加者上限と、購読できる音声トラック数の上限(100)。

| 項目 | 確認結果 |
| --- | --- |
| Flutter SDK | 公式の Flutter SDK(`livekit_client`)があり、Android と iOS に対応する |
| 100人ルーム | 公式ベンチマークで、音声のみ・発話者10人・聞き手3,000人の1ルームが、16コアのサーバー1台で CPU 80%。音声は平均 3kbps の模擬トラフィック。1ルームは1ノードに収まる必要がある |
| 購読の上限 | 1参加者が同時に購読できる音声トラックは100(全プラン共通)。Agent も参加者なので、100人全員が常時 publish すると上限に近づく |
| 参加者の上限 | Build(無料)は全ルーム合計で100参加者。100人 + Agent は Build では試せない |
| 録音 | 自動 egress で、ルーム作成時に、ルーム合成と、公開された各トラックの個別録音を自動で始められる。音声だけなら動画より低い料金区分。出力は S3 など |
| 録音の時間制限 | ファイル出力(MP4、OGG、WebM)は3時間で終了する。トラック単位の出力は12時間 |
| Egress の同時数 | Build は2、Ship は100、Scale は500(公式の料金ページ)。トラック録音は1トラックが1リクエストなので、この上限に効く |
| Agent の実行 | コンテナのワーカーとして動き、LiveKit サーバーに WebSocket で登録してジョブを受ける。LiveKit Cloud にデプロイするか、Kubernetes などのコンテナ基盤で自前運用する。公式の例に ECS はないが、コンテナ基盤として使える想定 |
| Agent の停止 | `SIGTERM` を受けると新しいジョブを断り、実行中のセッションが終わるまで動き続ける。ECS の停止待ち時間を長めにする |
| セルフホスト | サーバーも Agents も OSS。自前運用では Egress を別に配備する |

### LiveKit Cloud の料金

| プラン | 月額 | 参加者分(含む / 超過単価) | Agent セッション分(Cloud ホスト時のみ) | 下り転送(含む / 超過単価) |
| --- | --- | --- | --- | --- |
| Build | 0 USD | 5,000 分 | 1,000 分 | 50 GB |
| Ship | 50 USD | 150,000 分 / 0.0005 USD/分 | 5,000 分 / 0.01 USD/分 | 250 GB / 0.12 USD/GB |
| Scale | 500 USD | 1.5M 分 / 0.0004 USD/分 | 50,000 分 / 0.01 USD/分 | 3 TB / 0.10 USD/GB |

- Build の含まれる分は上限で、超えると新しいリクエストが失敗する。
- 同時参加者数は、Build が100、Ship が1,000、Scale が5,000(公式の料金ページ)。下り転送の Ship と Scale の数値は第三者記事による。
- 自前で動かす Agent は参加者分として計上され、Cloud にホストすると Agent セッション分(0.01 USD/分)になる。単価は20倍違うため、Agent は ECS で動かす想定にする。
- 例: 100人が1時間つながると 6,000 参加者分。含まれる分を超えた場合の Ship の単価(0.0005 USD/分)で 3 USD。

### 設計への反映

- PoC は Build で始め、100人ルームの負荷試験は Ship で行う(Build は100参加者まで)。
- 録音は自動 egress(ルーム合成と各トラック)にする。ルーム合成のファイルは3時間で終わるため、長いルームでは話者別トラックを正とし、合成は分割するか後から作る。
- 音声トラックの方式は、常時 publish して mute / unmute を第一候補にし、発話中だけ publish する方式と PoC で比較する。購読上限の100、発話冒頭の欠け、録音ファイルの単位に影響する。
- Agent は ECS Fargate で動かし、タスクの停止待ち時間を長めに設定する。

### 録音の料金と同時数(追加調査)

- **料金(公式の料金ページ):** トラック録音は、Ship が600分込みで超過 0.001 USD/分、Scale が8,000分込みで 0.001 USD/分。ルーム合成の音声のみは、Ship が 0.005 USD/分、Scale が 0.004 USD/分(映像は 0.02 / 0.015)。トランスコード分の込みの分数は Ship が600分、Scale が8,000分で、ストリーム取り込みと共有する。
- **例(試算):** 100トラックが1時間とも録音されると6,000分で、約6 USD(込みの分数を引く前)。ルーム合成の音声のみは1時間で 0.3 USD(Ship の超過後)。
- **同時数の問題:** トラック録音は1トラックが1リクエスト(調査担当の報告)。100人全員が常時 publish すると、Ship の同時100に届き、合成を併用すると超える。対策の案は、発話中のトラックだけ録る、1つのリクエストで参加者ごとにチャンネルを分けて録る(`AudioConfig`。1ルーム1リクエストにできるかは未確認)、Agent 側で話者ごとに録る、の3つ。PoC で決める。
- **自前運用:** Egress は1インスタンスあたり最低 4 CPU・4 GB で、Redis が必要。トラック録音は軽く1台で数百件を扱え、ルーム合成は 2〜6 CPU を使う。

### Agent の運用(追加調査)

- **規模の目安(公式の自前運用ガイド):** 4コア・8GB から始め、1サーバーあたり同時ジョブは10〜25。負荷の指標は CPU 使用率で、既定の閾値は 0.7。スケールアウトは 0.5 付近で早めにする。ヘルスチェックはポート 8081。
- **停止:** `SIGTERM` で新しいジョブを断り、実行中のジョブが終わるまで動く。音声アプリには猶予10分以上を推奨している。ECS Fargate の `stopTimeout` は最大120秒なので、長いルームはデプロイやスケールインで強制終了される(調査担当の報告)。対策は、タスクのスケールイン保護、デプロイ時期の制御、Agent が落ちても約15秒で再ディスパッチされることを前提にした再接続の設計。
- **ディスパッチ:** 本番は明示ディスパッチ(`agent_name`)を推奨。ルームは最後の人間の参加者が抜けると閉じ、Agent も切断される。
- **音声の入出力:** Python の `AudioStream` はサンプルレートを指定でき、48kHz から24kHz へのリサンプルも自動。翻訳音声の再配信は `AudioSource` と `LocalAudioTrack` を使う。言語別のトラックは、名前や metadata に言語コードを入れ、聞き手が選択購読する(`autoSubscribe` を切り、`setSubscribed` で購読)。
- **購読数:** 全員が99人と Agent と翻訳トラックを購読すると100本を超えうる。翻訳トラックは選択購読で絞る。同時に話すのは数人なので、公式ベンチマークの範囲に収まる見込み。
- **Cloud へのホスト:** 同時の Agent セッションは Ship が20、Scale が最大600。ECS で自前運用するほうが現実的。

### PTT の方式(追加調査)

- 公式の PTT 専用ガイドはない。常時 publish してミュートを切り替える方式を第一候補にする(推測。公式の比較はない)。ミュートするとトラックのデータ送信は止まる。録音は1話者1本になり、購読も維持される。
- Flutter は `setMicrophoneMuteMode` の `inputMixer` が最速の切り替え。既定の `voiceProcessing` は OS のミュート音が鳴る。
- unpublish して再 publish した直後のトラックは、ミュート解除の状態になる。ミュートが効く前に音が漏れる競合の報告があり、ミュート操作は必ず await する。
- ミュート中の参加者分は接続時間で課金される(公式に明記はない)。

## 通知とバックグラウンド音声

チャットなどの通知は FCM に一本化する。閉じたアプリでの音声受信は iOS ネイティブの追加実装が必要で、初回リリースで必須かどうかの判断が要る。

| 方式 | 評価 |
| --- | --- |
| FCM(iOS は APNs 経由) | **推奨。** 無料。Flutter は `firebase_messaging`、iOS は APNs 認証キーを Firebase に登録する。Lambda から FCM HTTP v1 で送り、端末トークンは DynamoDB に userId と紐づけて保存する |
| Amazon SNS のモバイルプッシュ | FCM の前段が増えるだけで利点が薄い。単価は公式の料金表で確認できなかった |
| AWS End User Messaging | Pinpoint の後継。Pinpoint は2026年10月30日に終了する(調査担当の報告)。新規に採る理由は薄い |
| OneSignal | 外部サービスが増える。無料枠は1,000 MAU まで |

- チャットの通知は通常の alert 通知にする。iOS のサイレント通知(`content-available`)は配信が保証されず、アプリを強制終了すると届かないので頼らない。重要な通知だけ time-sensitive(Entitlement が必要)を検討する。Android は高優先度で送る。
- 「誰かが話した」も alert 通知にする。

### バックグラウンドでの音声

- **iOS の PushToTalk フレームワーク:** アプリが閉じていてもロック中でも、PTT の音声を送受信できる。受信用の専用 APNs(push type は `pushtotalk`)でアプリが起動する。チャンネル参加はフォアグラウンドでの明示操作が必要で、同時に有効にできるチャンネルは1つ。音声の送受信は自前(LiveKit)。Flutter の汎用プラグインはなく、Swift のネイティブ実装と Method Channel が要る。LiveKit の公式対応は確認できなかった。
- **PushToTalk を使わない場合:** `audio` の background mode で、アプリが動いている間は音声を続けられる。閉じたアプリを起こして音声を流す手段は通常ない。
- **Android:** マイクのフォアグラウンドサービス(`FOREGROUND_SERVICE_MICROPHONE` と `RECORD_AUDIO`)が要る。Android 14 以降は、バックグラウンドから新たにマイクのフォアグラウンドサービスを始められない。受信だけなら `mediaPlayback` 型で足りる。
- **参考:** Zello は、Android では接続中ずっとフォアグラウンドサービスを動かし、通知は FCM で送る。iOS では APNs と PushToTalk フレームワークを併用している。
- **方針案:** 初回リリースは「入室中はバックグラウンドでも音声を維持する(iOS は audio mode、Android はフォアグラウンドサービス)。アプリを閉じている間は通知で知らせる」。PushToTalk フレームワークは次の段階で、LiveKit との共存を小さな PoC で確かめてから入れる。

## 画像・動画の処理

初回リリースは、端末側でH.264に圧縮し、サムネイルも端末で作る構成で足りる見込み。サーバー側の変換は、困りごとが出てから足す。

- **再生:** `video_player` は iOS で AVPlayer、Android で ExoPlayer を使う。iPhone の HEVC の MOV は端末の OS 次第で再生できる。管理コンソール(ブラウザ)では、Chrome 107 以降はハードウェアの対応が条件、Safari は対応、Firefox は 134 以降(Windows)で対応する。H.264 の MP4 は全ブラウザで再生できるので、管理コンソールでも見るなら H.264 に揃える。
- **端末での圧縮:** `video_compress` 3.1.4(2025年2月公開)が、H.264 の MP4 出力、進捗、サムネイル生成に対応する。FFmpegKit は2026年7月2日にアーカイブされた。後継の `ffmpeg_kit_flutter_new` は更新されているが、x264 を含む GPL 版を使うとアプリが GPL 3.0 になる。`image_picker` の動画の長さ制限は、カメラ撮影のときだけ効く。
- **サーバー側の変換(必要になったら):** S3 のイベントから Lambda、MediaConvert、EventBridge の完了通知、の順。Elastic Transcoder は2025年11月13日に終了した。MediaConvert の Basic は us-east-1 の例で約 0.0075 USD/分(ブログ。東京の単価は未確認)。1分の動画100本が HD で変換されると、月に約 1.5 USD(試算)。HLS は不要で、単一の MP4 で足りる。
- **サムネイル:** 端末で作り、本体と一緒にアップロードする。サーバー側のリサイズ(Dynamic Image Transformation for CloudFront)は構成要素が多く、少人数では不要。
- **アップロード:** 署名付き URL で S3 に直接アップロードする。Content-Type は署名時と一致させる。100MB 以上はマルチパートにし、未完了のアップロードはライフサイクルルールで削除する。ウイルススキャンは、招待制の間は不要(推測)。
- **サーバー変換を足す条件:** 端末の圧縮が失敗する・遅い、長尺の動画を許可する、Web で再生できない動画が出る。

## コストの目安

OpenAI の音声処理は、話者が1分話すごとに、翻訳先が3言語で約 0.119 USD かかる。翻訳は 0.034 USD/分 × 言語数、原文の文字起こしは 0.017 USD/分(話者ごとに1本)で、公開料金からの単純計算。

| 翻訳先の言語数 | 翻訳(USD/分) | 原文の文字起こし(USD/分) | 合計(USD/分) |
| --- | --- | --- | --- |
| 1 | 0.034 | 0.017 | 0.051 |
| 2 | 0.068 | 0.017 | 0.085 |
| 3 | 0.102 | 0.017 | 0.119 |
| 4 | 0.136 | 0.017 | 0.153 |

翻訳先が3言語のとき、1時間話し続けると約 7.14 USD。次は含まれていない。

- テキスト入力の読み上げ(TTS)の料金(テキスト翻訳は1通あたり約 0.001 USD の試算)
- LiveKit、AWS の料金
- 無音や待機中のセッションの課金(未確認のため、実際の請求分数は発話時間より長くなる可能性がある)
